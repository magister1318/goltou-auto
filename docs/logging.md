# 블로그·밴드 작업 추적 로그

## 진단 순서

1. `jobId`로 한 실행을 찾는다. `summary`의 결과, 사유, 마지막 단계, 기기에서 만든 대상 해시, 단계별 소요 시간 상위 10개를 확인한다. 같은 등록 번호의 게시와 삭제는 각각의 `jobId`를 갖는다. 발행 주소를 확보했어도 상세 판독이 끝나지 않은 실행은 `incomplete`다.
2. `summary.checks`에서 실패한 검사와 기대·관측 값을 비교한다. 검사마다 마지막 확정 결과가 들어간다. 같은 개수를 관측했어도 순서·식별·내용 불일치로 실패할 수 있으니 사유도 함께 읽는다. 공개 범위 값은 미확인 0, 비공개 1, 전체공개 2다. `summary.photos`에서 실제 대조에 사용한 출처와 API, 캐시된 피드, 복구 피드, DOM 시도 결과를 확인한다.
3. JSONL의 `event: "decision"` 줄에서 판정에 쓴 수치와 `choice`를 읽는다. `t`는 작업 시작부터 경과한 밀리초, `duration`은 해당 줄이 측정한 소요 시간이다. 같은 검사 이름으로 앞선 시도와 마지막 판정을 비교할 수 있다.
4. 전후의 요청에서 HTTP 방법, 허용 호스트, 경로 모양, 관측한 응답 상태와 허용·차단 사유를 확인한다. 화면에서는 고정 선택자, 요소 수, 적중·가림 여부, 대화상자 종류를 확인한다. `truncated`와 `droppedLines`는 전송본에서 묶거나 뺀 줄을 뜻한다. 상세 확인에는 앱의 [로그 내보내기](job-logs.md)를 사용한다.

## 기기와 서버

- 앱은 등록·삭제 시도 종료 시 final을 보낸다. 실행이 3분을 넘기면 사진 입력 종료, 저장·발행·삭제 제출 직전, 읽기 확인 종료 시점에 partial을 보낸다. partial과 final은 같은 `jobId`로 전송한다.
- 보낼 기록은 기기 전용 폴더에 최장 7일, 최대 20건 보관한다. 재전송 본문은 기기 로그에서 읽으며 전체 로그에 기기 보존 한도 50MB가 적용된다. 앱에서 세션을 복구하거나 다음 작업을 시작하면 같은 사용자 기록을 다시 보낸다. 종료 줄 없이 앱이 꺼진 기록은 다시 시작할 때 `incomplete / INTERRUPTED`로 전송한다. 전송 결과와 재시도 사유는 기기의 `runner.log_upload`에서 본다.
- `/auto/posts/trace`가 HTTP 404 또는 405를 응답하면 `/auto/posts/log`를 사용한다. 구 서버에서 글 번호가 같은 여러 로그는 서버의 기존 보관 방식에 따른다. 기록 시작 요청이 실패해 유효한 글 번호를 받지 못하면 `record` 진단을 기기에 남긴다.
- 전송 JSONL은 UTF-8 512KiB 이하, 요약은 64KiB 이하다. 용량을 넘기면 CDP·요청·폴링의 반복 줄부터 묶거나 뺀다. 결정·실패·비교 줄을 우선한다. 그 줄들만으로 한도를 초과하면 중복부터 줄이고 마지막 확인 근거를 우선한다.

## 허용 목록 수정

- 새 단계와 사유는 `packages/surface/src/telemetry-catalog.ts`의 고정 목록에 등록한다. 보내는 진단 값은 `TraceDetail`에 타입을 추가하고 `sanitizeDetail`에서 허용 필드를 하나씩 재구성한다. 기기 JSONL과 서버 전송본은 이 공통 투영을 사용한다.
- 값은 비교 수치·길이·개수, 고정 사유와 화면 선택자, 식별자를 마스킹한 경로 모양만 사용한다. 본문·이름·인증값·URL 쿼리는 기록하지 않는다. 네트워크 진단에는 고정 허용 목록에 있는 필드 이름만 넣는다.
- 테스트에서 새 단계와 필드가 업로드에도 보이는지 확인한다. `verification` 실패 호출에는 두 비교값을 제공한다. 로그 저장소는 같은 비교값을 결정 줄에 함께 남긴다. 브라우저 합성 재현에서 요약과 결정·검사 줄까지 검사한다.

# WP18 전달 메모 — 블로그 굵기와 링크

WP17에서는 미리보기의 굵기와 링크를 유지했고, 블로그 입력 엔진 및 변환 결과는 변경하지 않았다. 아래 내용은 코드 조사 결과이며 실제 네이버 편집기에서 시험하지 않았다.

## 현재 경로

- `packages/core/src/convert/types.ts`의 `Run`은 `text`, `bold`, `href`를 가진다. 변환 계획의 본문 `runs`에는 원문의 서식이 남아 있다.
- `packages/sites/src/naver-blog/plan.ts`의 `BlogPlan` 구조에는 runs가 없고, `BlogExecution.write`는 단계의 `text`를 기존 `Surface.typeText`와 키 입력으로 쓴다. 따라서 현재 실제 입력에는 부분 굵기·링크 적용이 없다.
- `readBlogDocument`는 제목, 텍스트/사진 토큰, 태그를 읽는다. 본문 내부 굵기와 링크 주소는 검증하지 않는다. 글자 수나 미리보기만으로 실제 서식 적용 성공을 판단할 수 없다.

## 기존 surface로 가능한 입력

1. **굵기**: 읽기 전용 스크립트로 현재 편집기와 선택/커서, 굵게 툴바의 `aria-pressed` 또는 동등한 상태를 확인한다. 실제 툴바 버튼 클릭 또는 `pressKey({ key: 'b', modifiers: 2 })`를 사용하고, 각 run을 사람이 입력하는 속도로 `typeText` 한다. 다음 run 전에 굵기 상태를 원래대로 돌린다. 운영 편집기의 실제 단축키·버튼 선택자·재초점 규칙은 미확인이다.
2. **링크**: 링크 글자를 입력하고 키보드로 해당 범위를 선택한 뒤 링크 도구 또는 확인된 단축키로 서비스의 링크 대화상자를 연다. 주소칸은 클릭·글자 입력으로 채우고 확인 버튼을 누른다. run.href와 표시 글자가 모두 보존됐는지 읽는다. 주소를 본문에 새로 덧붙이는 변환 변경으로 대체하지 않는다. URL 자동 인식은 명명된 링크 글자에 대한 증거가 아니다.
3. **선택과 복구**: 키보드 선택은 UTF-16/한글 조합·이모지 경계를 고려한다. 클릭 후 서식 상태와 커서를 다시 읽는다. 이미 입력한 run의 서식이 맞으면 재입력하지 않는다. 내용이나 커서가 불확실하면 기존 복구 동의 흐름으로 멈춘다. DOM setter, innerHTML 수정, evaluate로 Selection을 변경하는 코드는 사용하지 않는다.
4. **서식 있는 붙여넣기**: 현재 공통 surface에는 clipboard write나 HTML paste 기능이 없다. `typeText`는 일반 문자열 입력이며 HTML을 전달해도 rich text가 되지 않는다. 필요하면 플랫폼별 구현을 먼저 설계하고, 최소 공통 계약을 별도 검토해야 한다. 기존 계약 안에서는 툴바·키보드·링크 대화상자 경로가 우선이다.

## 저장 후 재검증

- 새로 연 실제 저장 글의 `.se-text-paragraph`/`.__se-node` 자식들을 문서 순서대로 읽는다. 각 text node의 텍스트, 굵기(semantic strong/b 및 computed font-weight), 가장 가까운 링크의 href를 정규화한 run 목록을 만든다.
- 원문 run과 텍스트·굵기·href·순서를 대조한다. 서비스가 span을 쪼개거나 합치는 경우 동일한 서식의 인접 run만 합친다. 임의의 공백·주소·숫자를 버려서 일치로 만들지 않는다.
- 저장 전 편집기 및 저장 후 새 문서 양쪽에서 확인한다. 임시저장 식별, 사진 수·순서, 표/태그, 가격·날짜 검증은 기존대로 유지한다.
- 단축키, 툴바 상태 전환, 링크 확인창의 취소/실패, 부분 입력 후 재개, 한글/이모지 경계, 끊어진 링크, 서식 누락을 먼저 합성 편집기 fixture로 시험한다. 실제 서비스 시험과 저장·발행은 WP18의 별도 승인 범위에서만 수행한다.

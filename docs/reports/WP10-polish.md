## 확인한 원인

WP4의 실패 기록만으로 당시 두 번의 서비스 상태를 복원할 수는 없다. 이번에는 같은 SM-S928N, 앱의 `goltou-ai` 프로필, 기존 PC UA와 1280×900 숨김 화면에서 직접 재현했다.

1. Google AI 화면에는 입력창이 있었고, 로그인·동의·지역·연령 제한 화면은 나타나지 않았다. `로그인` 링크가 있다는 사실을 로그인 필수로 판정하지 않았다. Google 자격 증명 입력·조회는 하지 않았다.
2. 숨김 화면에서 사람이 쓰는 속도의 `Input.insertText`와 보내기 버튼 입력이 정상 동작했다. 새 질문을 보내고 응답 생성 중지 표시가 사라진 뒤에도 기존 읽기 결과는 `ready=true`, `receipts=0`, `answer.length=0`이었다. 실제 응답은 화면에 있었다.
3. 현재 페이지는 질문 수신을 `AI 모드 대화:` 제목에 표시한다. 종전 코드가 요구하던 질문별 `복사/수정 + 전체 질문` aria 레이블은 없었다. 이 조건 때문에 응답이 있어도 제한 시간까지 기다렸다.
4. 답변은 `data-container-id` 안의 `<ol><li>`로 표시되며 `.markdown`, `pre`, `data-answer-text`가 없었다. 기존 추출기는 답변을 비워 두었다. `innerText`만 읽으면 목록 번호도 빠진다.
5. 보이는 화면에서의 초기 진단 입력은 소프트 키보드로 배치가 바뀌어 전송을 확인하지 못했다. 이를 서비스 장애로 세지 않고 숨김 화면에서 입력 일치·버튼 hit test·새 응답을 확인했다. UA 변경이나 로그인 우회는 필요하지 않았다.

이번 관측에서 `unavailable`의 구체적인 원인은 **현재 페이지와 맞지 않는 수신 확인·응답 추출 규칙**이다. 모든 과거 실패를 같은 원인으로 단정하거나 다른 국가·계정에서도 로그인 없이 된다고 일반화하지 않는다.

## 구현

- `sites/src/ai-mode`: 새 질문의 전체 텍스트가 맞는 제목을 수신 증거로 사용하고, 새 답변 영역의 목록 번호를 읽어서 복원한다. 복사·피드백 도구 영역만 제외하며 추가 설명은 남겨 형식 검증에서 거부한다. 전체 본문 차이를 답변으로 채택하는 경로는 제거했다. 이전 답·질문 반향·입력창 잔류 텍스트를 답으로 쓰지 않는다.
- 새 질문 수신, 입력창 비움, 생성 종료, 답변 준비, 연속 세 번의 동일한 읽기가 모두 맞아야 응답을 반환한다. 질문 재전송은 없다. 호스트별 단일 요청 잠금, 요청 사이 최소 1.8초, 입력 후 0.9초, 응답 읽기 1초 간격을 적용했다. 실제 글자 입력은 기존 Surface의 글자당 60ms 이상 입력 명령을 그대로 사용한다.
- 로그인·동의·접근 제한은 입력 값과 본문을 읽기 전에 판정한다. 지역·연령 안내, 입력 불일치, 수신 미확인, 응답·페이지 열기 시간 초과, 읽기 실패를 고정 코드로 구분한다. `Runtime.evaluate.throwOnSideEffect=true`를 유지하며 DOM 쓰기·스크립트 클릭은 없다.
- `core/src/polish`: 한 번에 한 문단만 보내고 결과를 검증한 뒤 다음 문단으로 간다. 모든 Unicode Number 문자가 든 문단, 서식·일정·요금 문단은 전송하지 않는다. 기존 숫자·주소·골프장·고유명사·길이·번호·문단 수 검증은 유지했다. 검증 실패는 해당 문단만 원문으로 복구하며 사용 불가·로그인 요구·불명확한 요청 실패는 후속 요청도 중단한다.
- 모든 문단에 전송 여부, 채택 여부, 원문 유지 사유, 경과 시간과 고정 실패 코드를 남긴다. 확인 화면은 원문과 사용할 글을 나란히 보여 주고 `다듬음`, `유지 · 숫자 포함`, `유지 · 서식·일정·요금`, `원문으로 복구`, 수동 되돌림을 구분한다. 옵션이 꺼져 있으면 요청하지 않는다.
- 기존 홈 AI 버튼이 실제 화면을 열지 않던 연결을 고쳤다. 홈 `AI` 또는 설정·비교 화면의 `AI 화면 열기`로 `goltou-ai`의 실제 페이지를 보여 준다. 로그인·동의는 사용자가 직접 한다. 돌아온 뒤 `다듬기 다시 시도`를 명시적으로 눌러야 다시 요청한다. 다른 선택 옵션 변경은 검토 결과를 재사용한다. 버튼을 눌렀다는 이유로 로그인 상태를 확인됨으로 바꾸지 않는다.

## 허용 범위 이탈과 중단

**좌표 입력 실수로 블로그 작업을 한 번 시작했다. “네이버·밴드 작업을 시작하지 않기” 조건을 완전히 지키지 못했다.** 문장 다듬기 스위치를 누르려던 좌표가 등록 시작 버튼에 전달됐다. 20:10:24 KST 이후 블로그 임시저장 작업이 만들어졌으며, 1단계의 기존 작성 글 복구 확인에서 멈췄다. 이를 20:11:31 KST에 `job.stop`으로 즉시 중단했다.

관측 상태는 `recovery_paused → user_paused`, `step=1`, `completedSteps=[]`, 진행 0/34였다. `AUTO_RECOVER_CONSENT_REQUIRED` 경로는 복구 창의 취소·삭제보다 앞에서 멈추며, 본문 입력은 4단계, 저장은 5단계다. 기존 글 버리기·계속 쓰기를 선택하지 않았고 새 본문·사진 입력, 저장·발행 단계에 도달하지 않았다. 골투에는 시작 후 중단한 등록 기록이 남는다. 이 기록을 삭제하거나 숨기지 않았다. 밴드는 열지 않았다.

이후 기기 좌표 입력은 중단했다. UI 이동과 스위치는 `Tab`으로 이동한 활성 요소가 정확히 대상인지 두 번 읽어 확인한 뒤 `Enter`만 사용했다. 미리보기 전용 요청은 등록 명령과 분리되어 있으며, 최종 비교 화면에서 등록 시작은 누르지 않았다. 기존 중단 작업은 `user_paused`로 남겼고 재개하지 않았다. [개인 자료를 제외한 이탈 기록](wp10/incident.json)에 상태 전후를 남겼다. 따라서 이 세션 전체를 “네이버를 열지 않음” 또는 “등록 작업 0건”으로 보고하지 않는다.

## 남은 확인

- 실상품 채택 두 문단이 원문과 같았다. 이번 결과는 실응답 수신·형식 및 사실 검증·복구·확인 화면을 입증하며 긴 소개 문장이 실제로 개선되는 품질까지 입증하지 않는다.
- 현재 계정 없는 페이지와 기존 UA에서 성공했다. 다른 지역·계정·추가 동의 화면의 실제 수동 로그인은 시험하지 않았으며 해당 분기는 로컬 페이지로만 확인했다. Google이 화면을 바꾸면 원문 유지와 고정 실패 사유로 돌아온다.
- API 날짜·가격 배열이 비어 있지 않은 실상품에서의 문장 다듬기 대조는 추가 확인 대상이다. 이번에는 본문에 있는 날짜·금액 보존을 확인했다.
- 등록 단계·실제 저장·발행의 성공 시험은 범위 밖이다. 위 이탈 기록과 중단된 작업은 검토자에게 그대로 넘긴다.

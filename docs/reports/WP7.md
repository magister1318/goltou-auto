# WP7 실제 API 연결과 상품 변환 점검 보고서

작업일: 2026-11-13 KST. 지시서 `docs/wp/WP7-real-api.md`, 계약 `docs/api-contract.md`, AGENTS.md와 WP5·WP6의 기기 절차를 확인했다. 깨끗한 작업 트리에서 origin을 fetch하고 최신 `origin/main`의 `99dba34`에서 `codex/wp7-real-api`를 만들었다. GitHub는 기존 gh 인증 도우미를 사용했고 로그인·계정 선택 창은 열지 않았다.

## 구현

- Android 기본 API를 실제 HTTP 클라이언트로 바꿨다. 주소는 `scripts/app-config.mjs` 한 곳의 빌드 설정이다. 코어의 가짜 API 기본값과 Android 합성 세션 인텐트를 제거했다. 시험·PC 시뮬레이터는 가짜 API를 명시적으로 주입한다. 기존 예시 글 실험은 디버그 실험 화면에만 연결한다.
- 사용자가 직접 입력한 로그인 정보를 `/auto/login`에 한 번 보낸다. 중복 로그인 요청을 막고 성공·실패 모두 요청 입력의 비밀번호와 아이디 참조를 비운다. 화면 입력은 전송 직후 비우고, 수신 전송 버퍼도 파싱 직후 지운다. 기기 정보는 껍데기가 제공하는 Android 종류·모델·앱 버전 세 칸만 쓴다. 자격 증명을 로그나 저장소에 쓰지 않는다.
- 접속 토큰만 Android Keystore의 내보낼 수 없는 AES 키로 GCM 암호화해 앱 전용 저장소에 둔다. UI 스냅샷에는 보내지 않는다. 시작 시 보관된 세션을 한 번 확인하며, API의 `auth`·`forbidden`이면 실행을 중단하고 토큰·화면 세션을 지운다. 로그아웃은 API 요청 뒤 로컬 토큰을 지우며 네트워크 실패 때도 삭제한다.
- HTTP 요청은 응답 본문까지 포함해 15초 제한을 적용하고 취소한다. 연결 오류·시간 초과·서버 오류를 한국어로 알린다. 자동 재요청·리다이렉트·쿠키 전송은 없다. 상품 목록에 사용자 새로고침 버튼을 추가했다. 결과가 모호한 기록 시작은 다시 시작하지 못하게 하고, 동일한 기록 갱신은 전송 전에 표시해 재전송을 막는다.
- 사진 준비는 실제 fetch를 사용한다. API가 제공한 원본 URL 중 HTTPS `goltou.kr` 및 하위 호스트만 허용하고 외부 호스트·다른 포트·인증정보 포함 URL·리다이렉트는 거부한다. 허용하지 않는 호스트와 내려받기 실패는 한국어 이유를 표시한다. 원본 바이트·순서·기존 사진 대조는 유지한다.
- 디버그 실험에 **변환 점검**을 추가했다. 로그인 세션으로 최신순 목록 두 페이지(각 30개)와 상세를 읽으며 모든 점검 요청 사이에 직전 응답 완료 후 최소 1초를 둔다. 최대 60개, 한 번에 한 점검이며 실패를 자동 반복하지 않는다. 등록 기록 생성·수정과 사이트 열기는 하지 않는다.
- 점검은 블로그·밴드 InputPlan을 만들고 상품 번호, 블록 종류별 개수, 원문 표/사진 포함 표 개수, 사진 수, 글자로 풀린 요소 종류, 고정 실패 코드, 공백 정리한 원문 본문 글자 수, 채널별 입력 글자·사진 수와 숫자·API 가격·날짜 보존 여부만 투영한다. 결과는 앱 내부 `files/wp7/conversion.json`이다. 제목·본문·사진 주소·상품 주소·내용 해시·계정 정보·원시 오류는 저장하지 않는다. 원문 대조 불일치도 실패 코드로 남긴다.
- 실제 상품으로 등록할 때 메모리의 제목 앞에 `[골투오토 실험] `을 붙인다. API 원본 가격·날짜·골프장·주소·내용 해시는 바꾸지 않는다. 옵션 기본 꺼짐, 발행 차단, 한 건씩 등록을 유지하고 Android 실행기의 네이버 저장 시도 한도를 1회로 낮췄다. 밴드 기본 선택은 꺼져 있으며 선택하지 않으면 목록/작성기를 열지 않는다.

## 로컬 확인

로컬 계약 HTTP 서버와 외부 요청을 차단한 편집기 시험만 사용했다. 새 시험은 로그인 1회·입력 폐기·실제 기기 정보 주입, 세션 만료/권한 오류 뒤 삭제와 수동 재로그인, 연결 끊김·응답/본문 시간 초과·서버 오류·리다이렉트 차단, 정확한 기본 15초, 로그아웃 실패 시 삭제, 기록 시작/갱신 중복 방지, 제목 접두사와 API 사실 보존을 확인한다. 점검의 60개 상한·최신순·61번의 1초 간격·읽기 전용 경로·본문 없는 결과와 외부 사진 차단도 확인했다.

실제 Android 엔트리를 릴리스 빌드 설정으로 번들해 가짜 API·가짜 계정·합성 세션·디버그 점검 및 예시 글 코드가 없음을 검사했다. 최초 검사에서 미제거 디버그 참조와 사이트 전체 동적 가져오기가 발견돼, 빌드 시 분기 제거와 정적 가져오기로 수정한 뒤 통과했다. Gradle 릴리스 변형과 서명은 기존처럼 비활성화 상태다. 실제 릴리스 APK를 만들었다는 뜻이 아니다.

### 수정과 로컬 재현

- 공통 `click()`은 호출자가 고정 컨트롤 ID를 반드시 넘기도록 바꿨다. 블로그 제목·본문·사진·개별사진 선택·태그·표 행 추가·저장·임시글 목록/항목·복구·도움말 제어를 구별한다. 같은 함수를 쓰는 밴드 호출도 ID만 연결했다. 클릭·키 입력·파일 첨부 방식과 선택자는 바꾸지 않았다.
- `ControlNotFoundError`는 `CONTROL_NOT_FOUND:컨트롤ID:계획종류:순번`을 만든다. 작성 중에는 `TEXT_HASHTAGS`, `PHOTOS` 등의 종류와 **1부터 시작하는 InputPlan 순번**이 붙는다. 계획 밖 조회는 `NONE:0`이다. 순번은 화면의 1~7 작업 단계와 별개다. ID·종류는 고정 허용 목록, 순번은 정수만 허용하며 선택자·정확한 제목·본문·URL은 코드에 넣지 않는다.
- 단독 블로그 실행기와 Android가 사용하는 통합 실행기 모두 이 코드를 `job.failureCode`, 채널 실패 이유, 기존 `recordFailure` JSON에 보존한다. 앱 실패 화면의 **실패 상세**에서 작업 단계와 코드를 펼쳐 읽는다. 일반 페이지 오류를 이 형식으로 위장해 저장하지 않는 검사와 내용 없는 화면 렌더링 시험을 추가했다.
- 실제 자료를 복사하지 않은 합성 상품으로 첫 사진 1장 → 링크·`font/del/u/i`를 포함한 본문 → 사진 7장 → 짧은 끝 글자 구조를 만들었다. 해시태그 없는 경로는 임시저장·새 편집기 재열람 대조를 검사한다. 기본 태그 3자가 추가되고 편집기에 태그칸이 없는 경로는 두 실행기 모두 사진 **8/8**, 글자 **1,509/1,512**에서 멈추고 저장·발행 0회임을 검사한다. 이 구조는 가설 시험용이며 실패 상품 원문이나 당시 계획을 복원한 것이 아니다.
- 진단 수정 전 두 회귀시험을 실행해 같은 수치에서 기존 `CONTROL_NOT_FOUND`만 나와 실패함을 확인했다. 수정 후 기대 코드는 합성 계획의 `CONTROL_NOT_FOUND:BLOG_TAG_INPUT:TEXT_HASHTAGS:97`이다. **이는 진단 결함의 회귀시험이며 실제 네이버 입력 성공을 증명하지 않는다.**
- Android bridge의 `experimentTitle: true`, `draftSaveLimit: 1`을 모두 `__GOLTOU_DEBUG__` 분기로 제한했다. 실제 Android 엔트리를 디버그/릴리스로 각각 번들해 디버그에만 두 설정이 있는지 검사한다. 릴리스의 기존 실험 코드 제외 검사도 유지한다. 실제 서비스 발행 차단과 Gradle 릴리스 변형·서명 비활성화는 유지한다.

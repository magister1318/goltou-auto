# WP16 UX v2 검토 수정

사용자는 네이버에 쓰다 만 글이 있으면 앱 안내에서 그만두거나, 버리기에 동의하고 같은 작업을 이어갈 수 있습니다. 연결된 밴드의 목록을 읽고 대상을 고를 수 있으며, 마지막 선택과 글 옵션은 앱을 다시 실행해도 남습니다. 이번 수정에서 실제 블로그 임시저장 1건을 완료하고 다시 읽어 확인했습니다. 작업 중에는 골투오토 화면만 보였습니다.

**실제 밴드 게시, 블로그 발행·삭제는 실행하지 않았습니다.** 밴드 제출·응답 검증은 합성 화면 시험 범위이며 시험 APK의 실제 게시 차단을 유지합니다. 진행 화면은 실제 실행에서 찾은 계산·표시 후퇴를 고친 뒤 추가 실행하지 않았으므로, 그 수정의 기기상 최종 동작은 아직 확인하지 못했습니다. 로그인·재로그인·오류·삭제 안내 등 계정 상태를 바꿔야 하는 화면은 시뮬레이터로 확인했습니다. 시뮬레이터 상품과 사진은 합성 예시입니다.


## 진행 화면 후속 기기 검증 — 선택 대기 중

이번 후속 요청에서는 이전 측정 파일의 잘못된 진행률 표기 47개 표본, 글자 수 후퇴 11회, 확인 표시 후퇴 2회를 다시 대조했습니다. 이전의 약 54초에는 쓰다 만 글 선택 대기가 들어 있으므로 전부를 작업 정체로 세지 않습니다. 기존 보고서의 “최장 약 2.1초”는 경과 시간 변화까지 포함했던 값이며 작업 변화의 증거로 사용하지 않습니다.

- 열기 신호를 네이버 열기·편집기 준비·빈 글 확인으로 구분하고, 응답 대기 안내를 2초마다 갱신합니다. 진행률은 글자 길이와 사진별 측정 시간으로 나누며 저장·재열람 몫을 남깁니다. 첫 사진의 측정값이 0이어도 유한한 수를 유지하고 이전 진행률 아래로 내려가지 않습니다.
- 쓰다 만 글 선택 대기는 작업 시간에서 빼고 화면에 “선택을 기다리는 중”이라고 표시합니다. 선택을 기다린 시간을 포함하지 않는 시계는 작업 상태에 보관합니다.
- 재열람 검증을 시작할 때 기존 확인 기록을 지우지 않습니다. 이미 확인된 항목과 표시된 글을 유지합니다. 재검증 중 확인 표시가 5개에서 1개로 줄어드는 회귀를 시험에서 재현하고 고쳤습니다.
- 화면 켜짐·앱 창 포커스·최상단 실행 앱을 읽기 전용으로 확인하고 `adb install -r`로 설치했습니다. 깨우거나 잠금을 풀지 않았습니다. 이전 첫 상품 대신 목록의 두 번째 상품에서 **run2 시작 버튼을 한 번만** 눌렀습니다.
- **run2는 네이버의 쓰다 만 글 안내에서 사용자 선택을 기다리는 중입니다.** 기존 쓰다 만 글을 버리는 입력은 하지 않았습니다. 선택 대기 중 진행률과 작업 시간이 고정된 것은 실제 표본으로 확인했습니다. 완료까지의 진행률·최장 정체·총 소요 시간과 최종 모음 그림은 아직 확인하거나 만들지 못했습니다. run3는 시작하지 않았습니다.
- 원본은 저장소 밖 `..\runs\wp16-shots\progress-metrics-2.json`, `run2-XX.png`에 계속 기록합니다. 측정 도구는 실제 앱 화면의 글자·사진·확인 표시 개수만 읽습니다. 상품 원문, 계정 정보와 게시글 주소는 측정 JSON이나 저장소에 넣지 않습니다. 기기 입력은 골투오토 안에서만 했고 발행·밴드 게시·저장된 글 삭제는 하지 않았습니다.

후속 확인 명령은 `pnpm install`, `pnpm typecheck`, `pnpm test --reporter=verbose --reporter=json --outputFile=tmp/wp16-progress-tests.json`, `pnpm build`, Android의 `./gradlew.bat assembleDebug --console=plain`, `git diff --check`입니다. 모두 통과했습니다. 전체 시험은 **607개 통과·0개 실패·0개 건너뜀(55개 파일)**입니다. 기기 완료 검증은 이 자동 시험 수에 포함하지 않습니다.

남은 일은 같은 run2에서 소유자의 선택 후 임시저장을 끝까지 관찰하고, 전체 측정값을 분석하여 최종 8장 모음 `run-contact.png`를 만드는 것입니다. 결함이 나타날 때만 허용된 run3를 한 번 사용할 수 있습니다. 완료 근거가 없는 상태를 정상 완료로 보고하지 않습니다.

## 쓰다 만 글의 범위

네이버가 실제로 불러온 정적 편집기 코드의 확인창 처리와 요청 경로를 읽었습니다. 확인창 취소는 자동복구용 글을 지우는 `RabbitAutoSaveDelete.naver`를 호출합니다. 임시저장함 글 삭제인 `RabbitTempPostDelete` / `RabbitTempPostDeleteAll`과는 별도이며, 이 확인창은 발행한 글 삭제도 호출하지 않습니다. 따라서 시트에는 편집기에 남은 쓰다 만 글이며 임시저장함의 글이나 발행한 글은 지워지지 않는다고 안내합니다. 복구할 수 있는 범위에 대한 추가 약속은 하지 않습니다.

임시저장함 글은 별도 목록과 삭제 동작을 가진다는 점을 [네이버 고객센터 안내](https://help.naver.com/service/5593/contents/15543?osType=PC)와도 대조했습니다. 정적 코드 조각은 저장소 밖에만 보관했습니다. 로그인 필드·쿠키·비밀번호는 읽지 않았습니다.

## 밴드 진단

- 기기에서 `api-kr.band.us`의 `POST /v2.3.0/get_band_list`가 막히는 것을 확인했습니다. 정확한 호스트·경로·메서드만 허용하고 다른 쓰기는 계속 차단합니다.
- 브라우저가 이미 취소한 요청의 만료된 번호 응답을 전체 차단 실패로 잘못 처리하던 것도 고쳤습니다. 정확한 취소 응답만 구분하며, 이후 요청의 차단 규칙이나 게시 응답 증명은 바꾸지 않습니다. 목록·업로드 응답의 본문은 게시 증명에 필요하지 않습니다. 응답 본문 수집은 실제 제출 경로에만 적용합니다. 제출 응답을 읽지 못하면 계속 닫힌 상태로 멈추는 회귀 시험을 추가했습니다.
- 현재 모바일 밴드의 “전체보기”는 주소가 바뀌지 않는 펼침 목록입니다. 밴드 주소와 글쓰기 가능 여부를 읽고 돌아오면 목록을 다시 펼칩니다. 광고·폴더를 제외하며, 펼침 목록이 실제로 보일 때까지 기다리고 이름으로 대상을 다시 찾습니다. 글쓰기 버튼을 누르거나 내용을 입력하지 않습니다.
- 읽기 화면이 실패하면 닫습니다. 취소된 요청·화면 준비 지연으로 조회에 실패한 읽기 화면은 같은 차단 규칙을 새 화면에 설치한 뒤 한 번만 자동으로 다시 읽습니다. 글쓰기 화면은 이 경로에 들어가지 않으며 게시를 재시도하지 않습니다. “다시 확인”도 손상된 화면을 재사용하지 않습니다. 하나면 자동 선택하고 여러 개면 지난 선택이 유효할 때 복원합니다.

## 실제 임시저장 관찰

시작 버튼 입력은 한 번입니다. 저장소 밖에 시작 표식을 먼저 남겨 같은 스크립트가 다시 시작하지 못하게 했습니다. 이전 회차의 중단 실행과 이번 회차의 완료 실행을 합쳐 쓰지 않습니다.

- 약 153초 동안 상태 표본 119개와 진행 PNG 30장을 남겼습니다. 약 5초 간격과 단계 변경 때 찍었습니다. 제목 입력, 본문 입력, 사진별 진행·실제 썸네일, 확인 표시, 진행률·경과/남은 시간, 완료 화면을 포함합니다.
- 앞부분에는 쓰다 만 글 안내와 정적 코드 확인을 위한 동의 대기가 있습니다. 약 56초부터 제목, 59초부터 본문, 92~124초에 사진 13장, 이후 일정·골프장·해시태그, 138초부터 검증·저장·재열람, 약 153초에 완료를 확인했습니다. 상품 문구·계정·게시글 주소는 보고서에 넣지 않았습니다.
- 입력 중 뒤로가기로 중단 확인 시트를 열고 “계속 옮기기”로 닫았습니다. 작업은 계속됐습니다. 실제 네이버 화면은 표시하지 않았습니다.
- 관측 표본에서 글·사진·확인 표시·경과 시간 중 하나가 바뀌기까지의 가장 긴 간격은 약 2.1초였습니다. 다만 사진 첫 구간부터 전체 진행률이 잘못된 숫자로 표시됐고, 본문 구간에서 0.1% 후퇴도 있었습니다. 이를 정상이라고 판정하지 않았습니다.
- 첫 사진의 측정 시간이 0일 때 0으로 나누던 계산을 고쳤습니다. 전체 진행률은 반올림하기 전 값을 유지하고, 이미 표시한 글은 새 측정 신호가 와도 짧아지지 않습니다. 열기 단계도 시간에 따라 움직입니다. 수치 시험과 실제 React 갱신 시험으로 확인했습니다. **추가 실제 임시저장은 하지 않았으므로 수정 뒤 진행 화면의 기기 검증은 남아 있습니다.** 수정 APK 설치 후에는 목록·시트만 확인했습니다.

## 화면과 기기 범위

원본과 목업 비교 PNG도 같은 저장소 밖 폴더의 `compare-*.png`에 둡니다. 상품 목록, 두 미리보기, 임시저장·발행·확인 시트, 계정 연결, 기록, 설정, 진행, 완료를 비교했습니다. 실제 상품은 원문 순서를 유지하므로 사진 앞의 긴 설명과 제목 줄 수는 예시 상품과 다릅니다. 목록의 실제 썸네일·76px 칸과 행 구분선을 확인했습니다.

기기 너비는 384 CSS px입니다. 상·하단 시스템 영역을 제외한 웹 화면을 기준으로 비교했습니다. 네이티브가 여백을 확보한 뒤 같은 인셋을 웹 화면에 또 전달하던 문제를 고쳤으며, 하단 고정 바 안쪽 여백이 48px에서 의도한 12px로 돌아온 것을 읽어 확인했습니다. 아래 버튼과 시스템 내비게이션 영역은 겹치지 않습니다. 시뮬레이터는 360·390·412px 너비와 긴 제목을 검사합니다.

실제 화면으로 확인한 것은 로그인된 상품 목록·미리보기·임시저장/발행/발행 확인·계정 연결·등록 기록·설정, 쓰다 만 글 안내·작업 중 중단 확인·진행·완료입니다. 로그인·재로그인·오류·삭제 확인의 기기 시험을 위해 계정을 끊거나 글 삭제를 시도하지 않았습니다. 이 화면의 배치와 뒤로가기는 합성 화면으로 확인했습니다. 작업 중 앱 배경 전환과 외부 앱 글 보기도 이번 기기 범위에 넣지 않았습니다.

설치·입력 전에는 화면 켜짐, 앱 창 포커스, 최상단 실행 앱을 읽기 전용으로 확인했습니다. 설치는 `adb install -r`만 사용했습니다. 깨우기·잠금 해제·다른 앱 입력·실제 게시·기존 글 삭제는 하지 않았습니다.

# WP17 — UX v3 구현 보고서

## 결과와 범위

`codex/ux-v3`에서 UX v3의 화면 상태, 앱 밴드 선택창, 서비스별 미리보기, 결과 화면, 설정 편집과 이탈 처리, 밴드 기록 삭제 및 디버그 일회 게시 허용을 구현했다. 상품 변환 코드는 변경하지 않았다. M05·M07은 소유자 결정대로 유지했다. 블로그 미리보기의 굵기와 실제 링크 요소를 유지했으며 실제 블로그 서식 입력은 WP18로 남겼다. 조사 내용은 [WP18-notes.md](../wp/WP18-notes.md)에 있다.

구현 전에 Chromium에서 목업의 화면 바로가기 10개, 상태 버튼 34개, 시트 16개를 실제 클릭하고 60개 캡처를 확인했다. 브라우저/Windows 제어 연결은 사용할 수 없어 기존 저장소 방식의 Playwright Chromium을 사용했다. 로컬 감사는 읽기만 했고 저장소에 복사하지 않았다.

구현 종료 당시 휴대폰은 읽기 전용 두 신호 점검 중 화면이 Dozing으로 확인돼 APK 설치와 실기기 캡처를 생략했다. 아래의 후속 기기 점검에서 설치 결과를 갱신했다. 실제 네이버 저장/발행, 밴드 게시/삭제, 자격 증명 입력과 게시 허용 파일 생성은 수행하지 않았다.

## 밴드 삭제와 게시 허용

API에서 소유가 확인된 이 앱의 발행 기록만 삭제 준비가 가능하다. 기록을 다시 읽어 주소·상품·제목·채널·대상이 그대로인지 확인한다. 숨김 surface에서 기록 주소를 열고 신원을 읽은 다음 그 글의 메뉴와 삭제 확인 버튼을 누른다. 클릭 직전에도 신원·버튼 위치·실제 hit target 및 확인창 내용을 다시 검사한다. 마지막 확인 이후 해당 글의 삭제 요청 한 건만 허용한다. 원래 주소를 다시 열어 삭제 상태를 읽은 경우에만 `BAND_POST_DELETED`로 기록한다.

결과는 `deleted` / `not_started` / `uncertain`이며, 뒤의 두 상태에서는 API 기록을 삭제함으로 바꾸지 않는다. 게시가 불명확한 글, 다른 사용자의 기록, 전체 범위 목록, 주소 없는 글, 바뀐 상품은 삭제하지 않는다. 삭제에는 게시 허용 게이트를 사용하지 않는다.

디버그의 실제 밴드 게시 차단은 기본 유지된다. 운영자가 PC에서 앱 전용 `files/one-band-post.allow` 파일을 만들면 정확히 한 번의 제출 시도에만 사용한다. 시작 시에는 존재만 확인하고, 검증된 제출 버튼을 누르기 직전에 배타 잠금을 잡아 파일을 소비한다. 응답 실패도 허용을 되돌리지 않는다. 파일 내용은 읽지 않는다. 충돌 또는 소비 실패는 차단한다. 앱 종료로 `.lock`이 남은 경우에도 자동으로 허용하지 않는다. 이번 작업에서는 휴대폰의 허용 파일을 만들지 않았다.

- `pnpm build` 및 `node scripts/simulate-ux-v3.mjs`: 비교 PNG 59장, 화면 검사 68건, 목업 진입 항목 60개와 추가 장면 6개를 확인했다. 브라우저 오류 0건, 허용된 외부 요청 0건. 최종 교정한 목록 실패·태그 편집·범위 오류 3장은 재촬영했고 같은 흐름의 검사 12건을 다시 통과했다. [checks.json](wp17-ux-v3/checks.json)에 기록.
- 구현/목업 나란히 비교 PNG는 [wp17-ux-v3](wp17-ux-v3/)에 있다. 상품·회원·밴드·기록은 합성 자료이며 외부 통신은 차단한다. 실제 서비스 엔진이 없는 로컬 Core만 연결한다.

실제 Android 키보드·스크롤·뒤로가기, 실제 계정 연결 페이지 상단 안내, 외부 앱의 글 보기, 실서비스 저장/발행/삭제는 미검증이다. 후속 점검에서 APK 설치와 실행은 통과했으나 수동 골투 로그인 필요 상태로 나머지 기기 검증은 차단됐다. 기존 키보드 캡처는 높이 480px로 줄인 시뮬레이션이며 실제 키보드가 아니다.

사진의 원문 width/height가 있으면 그 비율을 예약한다. 치수가 없는 API 전용 사진은 안정된 16:10 틀 안에 원래 비율로 맞춰 보여 주므로 로딩 후 본문이 밀리지 않는다. 밴드 사진은 정사각 격자로 표시한다. 실서비스 사진 묶음의 최종 모습은 다음 실제 게시 시험에서 확인해야 한다.

기존 API에는 블로그 공개 범위 필드가 없으므로 새 기록의 범위는 기기 내부 metadata로 보존한다. 이 설치에서 정보를 남기지 않은 과거 기록/다른 기기의 기록에는 `공개 범위 확인 필요`를 표시하며 추정하지 않는다. 서버/DB 변경은 하지 않았다.

WP18에서는 별도 지시 범위에서 실제 블로그 굵기·링크 입력과 저장 후 run 검증을 진행해야 한다. WP17에서는 해당 입력 엔진을 변경하지 않았다.

# WP27 게시 후 안정화 판독과 공개 한 건 왕복

진행 중. 이번 공개 발행 한 건에서 실제 앱 성공 화면을 확인했다. 서비스 글은 삭제됐으며, 앱의 목록 검증 실패를 수정해 삭제 기록을 복구 중이다. 원래 첫 삭제 job을 성공으로 바꾸지 않는다. 기존 브랜치와 초안 PR #27에서 이어서 작업한다. 사용자 2026-11-17 13:57 KST 승인: 최대 세 건, 한 번에 한 건, 매번 삭제 확인 후 다음 건, 성공 화면이 나오면 즉시 종료. 17:30 KST 마감이다.

## STEP A

- 첫 읽기 전용 점검에서 기기 깨어 있음·잠금 해제·골투오토 전면을 확인했다. 기기 깨우기·설정 변경·로그인 입력은 하지 않았다. 기존 동일 상품의 해시·계획과 사진 29장을 대조했다. 밴드는 미확인 상태이며 이번 기기 밴드 조작은 0회다.
- `pull-logs.ps1`로 원래 로그를 저장소 밖에 추출하고 세 블로그 발행 작업을 읽었다. 첫 작업은 요청 차단/결과 불확실 때문에 게시 후 검증까지 도달하지 않았다. 나머지 두 작업은 각각 뷰어의 빈 채움 문단과 태그 렌더링 지연 때문에 엄격한 판독이 실패했다. 이전 기록을 성공으로 고치지 않는다.

- 공통 `settledReadback`은 매번 살아 있는 DOM에서 새 스냅샷을 얻는다. 750ms 간격, 기본 90초 이상, 사진 수에 따라 사진당 4초까지 늘린다. 29장은 116초다. 같은 불완전 스냅샷 두 번으로 일찍 끝내지 않는다. 마감에도 안정적이지 않으면 정확 비교를 실행하지 않고 화면 로딩 상태를 확인 항목으로 남긴다.
- 항목마다 고정 `READBACK_*` 사유와 expected/observed 개수 및 경과 ms를 로그에 남긴다. 제목·문단·본문·굵기·링크·사진·태그·공개 범위·안정성을 구분한다. 실제 글자·주소·태그 값은 로그에 쓰지 않는다.
- 공개 영수증이 있는 결과는 기존 WP23의 중립 확인 화면과 저장 링크를 유지하며, 블로그 제목을 **발행됨, 확인할 점 있음**으로 명시했다. 항목별 차이를 보이고 재시도·이어하기를 제공하지 않는다. 비교 조건을 완화하거나 실패를 성공 terminal로 바꾸지 않는다.
- 밴드 코드도 전체 본문·줄바꿈·태그·링크·로드된 사진을 같은 공통 대기에서 안정화하도록 바꿨다. 주소 저장은 내용 검증보다 먼저이며, 로컬 브라우저 회귀시험으로만 확인한다. 기기 밴드 탐색·로그인 확인·입력은 하지 않는다.
- 합성 로컬 서비스의 실제 Chromium `throwOnSideEffect` 경로로 99개 문단·58개 단독 U+200B 채움 문단·29개 사진·지연 태그·지연 사진·키 탐색 지연 로드·늦은 굵기/링크·독립 모바일 공개 범위를 재현했다. DOM을 고치는 것은 합성 서비스 자체뿐이다. 실행 코드의 실제 서비스 DOM 수정은 없다.
- 새 읽기 코드의 object spread가 Chromium의 읽기 전용 검사에서 거절되는 것을 시험이 잡아냈다. 로컬 결과 객체 속성 대입으로 바꾸고 동일 검사 경로를 통과했다. 실제 발행 전 발견·수정한 결함이다.
- 첫 수정 APK는 내장 Node 시작에 실패했다. 이번에 추가한 밴드 태그 개수용 Unicode 속성 정규식이 ICU 없는 모바일 런타임에서 지원되지 않아, 밴드 조작 없이도 엔진을 파싱할 때 `SyntaxError`가 났다. APK와 앱 내부 번들 세 파일의 바이트/해시가 같고 데스크톱 Node 18.20.4 문법 검사는 통과함을 확인해 파일 손상과 구분했다. 기존 명시적 문자 범위 패턴으로 교체했다. 기존 `runtime-compatibility.test.ts`의 공유 엔진 AST 검사와 실제 앱 재기동으로 회귀를 검증한다. 중간 전체 시험은 소스 변경 전에 중단했으며 최종 통과로 세지 않는다.

### 실제 첫 발행과 삭제 목록 판독

- 실제 발행 확인은 한 번이며 전체공개 글 한 건만 만들었다. 앱의 **발행했습니다** 화면과 글 보기 링크를 직접 확인하고 `e4-result-success.png`를 저장했다. 성공 작업의 링크는 블로그 target 결과와 등록 기록에 있다. 검사 스크립트의 과거 실패 작업 전용 최상위 URL 가정만 고쳤으며, 앱 상태나 기록·로그를 고치지 않았다.
- 실제 게시글에서 제목·본문 99문단·굵기 구간·링크 두 개의 표시 글자와 href·사진 29장의 순서와 로드·태그·모바일 `openType=2`를 대조해 차이 0을 확인했다. 표는 native table 0개이며 셀 두 개를 ` | `로 잇는 일반 텍스트 세 줄이다. 원문 그대로의 세 줄은 저장소 밖 `e4-table-private.txt`에 보관했다.
- 미리보기 본문 폭은 약 314.6 CSS px, 실제 글과 사진 폭은 500 CSS px다. 링크는 미리보기 14px/22.4px, 실제 15px/27px와 밑줄이며 블로그 스킨을 따른다. 본문 첫 선택자는 빈 뷰어 문단일 수 있어 그 스타일을 의미 있는 본문의 글꼴로 단정하지 않았다. 표시 차이 때문에 문구를 바꾸지 않았다.
- 앱 등록 기록에서 이번 URL·상품·제목이 맞는 유일한 삭제 가능 기록만 대상으로 확인을 한 번 눌렀다. 실제 삭제 입력·네이티브 확인 뒤 원래 주소의 삭제 안내는 확인했으나, 목록 marker 직후 한 번만 비교해 **BLOG_POST_DELETE_LIST_UNCONFIRMED**로 첫 삭제 job이 실패했다. 첫 삭제 전체 성공으로 보고하지 않는다.
- 새 읽기 전용 목록 점검에서 같은 블로그의 게시물 링크 19개와 이번 URL·제목 부재를 12회 확인했다. 원래 첫 목록의 원시 링크/제목 배열은 보존되지 않아 어느 predicate가 최초 실패했는지는 직접 보존 증거와 구분한다. 로그의 593ms 단발 목록 검사와 나중의 완성된 목록을 근거로 조기 판독 경로를 수정했다.
- 목록도 같은 공통 안정화 판독으로 바꿨다. 완료된 목록 문서·해당 블로그의 게시물 링크·이번 URL와 제목 부재를 반복 확인하고 연속 두 번 동일할 때만 완료한다. 90초 한도와 목록/링크/부재 항목별 개수·시간·사유를 남긴다. 초점·확인창·로그인 문제는 통과시키지 않는다. 빈 목록을 삭제 증거로 삼지 않는 기존 조건을 유지한다.
- 실제 코어의 이미 삭제된 URL 복구 경로로, marker가 먼저 뜨고 링크가 1.5초 뒤에 나타나는 Chromium 회귀를 추가했다. 수정 전 737ms에 같은 목록 미확인 오류가 났고, 수정 후 입력·추가 삭제 요청 없이 통과했다. 글이 계속 목록에 있으면 완료하지 않는 시험도 통과했다. 관련 46개 시험과 타입 검사를 통과했다.
- 발행 성공 화면을 이미 확보했으므로 추가 공개 발행은 하지 않는다. 삭제 확인·기록 복구와 최종 검증 결과를 완료 후 추가한다.

# WP14 발행 방식 확인

2026-11-14 KST, `codex/publish-mode`, 초안 PR #17. 기존 비공개 시험 글 한 건의 앱 삭제만 진행했다. 새 발행·밴드·임시저장·다른 글 조작은 하지 않았다.

## 현재 상태

이전 11:11 중단을 포함해 총 3회로 보수적으로 세었다. 이번 두 시도도 삭제 버튼을 누르기 전에 멈췄다. 마지막 단계는 `identified`, `before-delete`, 오류는 `BLOG_TEST_DELETE_CONTROL_UNCONFIRMED`다. 실제 삭제 요청과 `Page.javascriptDialogOpening`은 관측되지 않았다.

중단 뒤 읽기 전용으로 제목 접두사·이번 실행 표식·비공개·사진 13장·글 URL에서 얻은 식별자를 다시 확인했다. 글은 그대로 있다. API는 기존 `failed` / `BLOG_PUBLISH_RESPONSE_UNCONFIRMED`이며 `BLOG_TEST_POST_DELETED` 갱신은 보내지 않았다. 추가 기기 입력과 삭제 재시도는 중단했다.

## 진단과 수정

- 이전 설치본의 포커스 검사 `activeElement.matches(...)`가 같은 글에서 `throwOnSideEffect`에 거부되는 것을 재현했다. `hasFocus()`만 읽으면 통과하고 `matches()`만 읽으면 거부된다. 네이티브 메서드임도 확인했다. 현재 `tagName`, `isContentEditable` 검사는 통과한다. 읽기 보호는 유지했다.
- 화면은 바깥 `/N/N`과 `mainFrame`의 PC `/PostView.naver`다. 삭제는 더보기 메뉴가 아니라 글 아래 `.area_btn_postedit a._deletePost`에 직접 있다. 태그는 `A`, 별도 role·data 속성은 없고 `href`, `class`만 있다. 이 전용 선택자로 범위를 좁혔다.
- 이번 첫 시도는 스크롤 뒤 적중 검사에서 멈췄다. CDP 화면 지표가 내부 프레임의 스크롤을 반환해 바깥 좌표에 중복으로 더하고 있었다. 바깥 문서의 스크롤을 읽도록 고쳤다. 같은 화면에서 수정 전 `No node found at given location`, 수정 후 같은 위치의 적중 검사 통과를 읽기 전용으로 확인했다.
- 마지막 시도는 삭제 직전 검사에서 멈췄다. 좌표 일치·적중 대상·포커스·기존 확인창 중 당시 어느 항목이 달라졌는지는 분리하지 못했다. 중단 뒤에는 같은 삭제 링크의 적중 검사와 포커스 읽기가 통과했다. 보호를 낮추거나 네 번째 시도를 하지 않았다.
- 빠졌던 해시태그 한 개는 본문 밖 `.wrap_tag a.itemTagfont`에 있었다. 리더에 추가하고 사이드바 태그와 태그 수정 입력은 제외했다. 같은 글에서 태그 1개를 읽었고 API 원문과의 전체 글자·숫자·사진 13장 대조가 일치했다.
- 삭제 처리 소스에는 네이티브 `confirm`과 고정 안내문 “삭제된 글은 복구할 수 없습니다. 삭제하시겠습니까?”가 있다. 실제 확인창은 열지 못했으므로 런타임 관측으로 기록하지 않는다. 같은 글에서 이번 삭제로 열린 이 문구의 확인창만 허용하며 기존 확인창은 거부한다.

디버그 화면에 기존 복구 문맥을 쓰는 삭제 진입점을 추가했다. 문맥은 사용 전에 한 번만 소비한다. 단계별로 수치와 고정 UI 문구만 누적 기록한다. 글 주소와 목록의 부재를 모두 확인해야 삭제 완료로 기록한다. 같은 API 기록을 갱신한 뒤 다시 읽어 확인하도록 했다. 이번에는 이 경로에 도달하지 않았다. 삭제 기능과 복구 문맥은 릴리스에서 제외한다.

구조 증거는 저장소 밖 `../runs/wp14-delete-probe.json`, `wp14-delete-attempt2.json`, `wp14-delete-attempt3.json`에 있다. 상품 원문·계정·블로그 식별자·글 주소·쿠키·토큰은 보고서와 저장소에 넣지 않았다. 기기에서는 앱 내부 복구 문맥만 썼다.

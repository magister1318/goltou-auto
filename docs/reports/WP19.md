# WP19 여섯 번째 실밴드 시험: 게시 1건, 삭제 미완료

## 현재 상태

**시험 글은 승인된 밴드에 남아 있다. 삭제 완료가 아니다.**

2026-11-16 23:31 KST부터 기존 브랜치에서 진행했다. 이번 실행의 실제 생성 제출은 정확히 1회이고 생성 성공은 1건이다. 이전 실행의 차단된 클릭은 이번 한도에 포함하지 않았다. 실제 생성 이후 허용 파일을 다시 만들거나 게시를 다시 누르지 않았다.

앱의 등록 기록에서 삭제를 5회 시작했다. 앞의 4회는 서비스 삭제 전 not_started, 마지막은 단일 글 삭제 요청이 클라이언트에서 차단된 뒤 uncertain이었다. 삭제 수정 3회차까지 설치·시험한 뒤 소유자가 정한 한도에 따라 추가 수정·삭제 시도를 중단했다. 다른 경로로 삭제하지 않았다.

2026-11-17 00:53 KST 승인된 게시용 피드를 새로 읽었고 시험 제목이 여전히 있었다. 피드는 로드 완료, 작성기 없음, 글쓰기 버튼 있음, 기존 글 옵션 20개였다. 원래 등록 기록도 게시 상태와 저장된 글 주소를 유지하며 삭제 완료로 바꾸지 않았다.

## 승인 범위와 실기기 확인

- 휴대폰이 깨어 있고 잠금 해제 상태이며 앱이 전면임을 읽기 전용으로 확인했다. 깨우기·잠금 해제·전화기 설정 변경·다른 앱 입력을 하지 않았다. APK 교체 뒤에는 이 앱만 재시작했다.
- 승인된 이전 상품과 본문 일치를 확인했다. 밴드만 선택하고 블로그를 해제했다. 선택기에서 승인된 정확한 접미사와 이모지 접두사가 있는 항목 하나를 확인했다. 다른 밴드를 선택하지 않았다.
- 문장 다듬기·글 끝 문구·링크 카드는 모두 꺼짐이었다. 앱이 계획한 글에 문구를 추가하거나 바꾸지 않았다.
- 피드는 앱의 BandDirectory 게시용 WebView에서만 열었다. 기록 복구·삭제 화면도 앱이 만든 같은 밴드 프로필을 사용했다. 로그인 확인용 WebView로 피드를 열지 않았다.
- 생성 직전 일회성 허용 파일을 한 번 만들었고 실제 서비스 클릭 직전에 소비됐다. 생성 요청은 CREATE_ALLOWED, HTTP 200, result_code: 1이었다. 생성 시각은 23:39 KST다.
- 네이버 블로그의 입력·저장·발행·삭제를 수행하지 않았다. 로그인 페이지 조작과 자격증명 입력을 하지 않았다.

## 실제 게시 모습과 미리보기 차이

전체 게시글을 읽기 전용으로 열어 확인했다. 요청 형태·DOM 구조·사진 식별 경로와 캡처는 외부 증거 폴더에만 보관했다.

| 항목 | 확인한 사실 |

| 본문 | 공백을 정규화하면 계획과 완전히 일치한다. 문구·숫자 잘림은 확인되지 않았다. |
| 줄바꿈 | 실제 렌더링된 본문과 계획 모두 158개다. 일반 공백은 화면에서 일부 합쳐져 코드 포인트가 11개 줄었다. |
| 사진 | 상세 DOM에 29장 모두 로드됐고 원래 첨부 경로 29개와 순서가 정확히 일치한다. |
| 사진 배치 | 전체 본문 뒤에 한 장씩 들어간 세로 이미지 블록 29개다. 미리보기의 격자와 다르다. |
| 피드 접힘 | 긴 본문은 더보기로 접히고 사진은 콜라주로 표시된다. 피드 응답의 사진 10개는 전체 수가 아니라 앞부분이었다. |
| 해시태그 | 2개가 버튼으로 렌더링된다. |

| 글꼴 | 상세 본문에서 관측한 CSS는 15px, 줄 높이 20px, white-space: normal이다. |
| 화면 잘림 | 현재 숨김 WebView 캡처에서는 긴 줄과 큰 이미지의 오른쪽이 잘린다. DOM에는 전체 본문과 사진이 남아 있다. |

초기 관찰에서 피드 응답의 사진 수를 전체 수처럼 판단했으나, 상세 DOM에서 29장을 확인한 뒤 정정했다. 원시 응답의 줄바꿈 수와 실제 렌더링의 줄바꿈 수도 구분했다. 복구 코드 역시 피드 사진을 일부 목록으로 표시하도록 수정했다.

다음 미리보기 작업에는 세로 사진 배치, 피드 접힘과 상세 보기의 구분, 게시자·시각 등의 메타 행, 공백 처리, 해시태그 버튼과 URL 링크 스타일을 반영해야 한다. 이번에는 미리보기를 바꾸지 않았다.

## 코드 변경

기존 앱은 생성 응답에서 기대한 글 식별값을 확인하지 못했고, 실제 모바일 상세 DOM도 기존 읽기 선택자와 달랐다. 이 때문에 글이 실제로 존재해도 등록 기록이 확인 필요 상태였고 삭제 버튼이 없었다.

디버그 전용 단발 기록 복구를 추가했다. 원래 실패 기록 한 건, 현재 상품 해시, 전체 정규화 본문, 본인 글 여부, 생성 시각, 원래 업로드 사진 경로의 접두 순서를 확인한 뒤 그 기록에만 주소를 저장한다. 작성·재제출·글 수정·삭제 기능은 복구 절차에 없다. 피드에 일부 사진만 직렬화되는 경우는 전체 사진 손실로 판단하지 않는다.

읽기 장벽은 관측된 세션 부트스트랩 GET과 동일한 글에 대한 정확한 두 GET 묶음만 추가 허용한다. 묶음은 경로·메서드·인코딩·대상·키 중복을 검사한다. 생성 승인이나 일회성 허용 파일을 소비하지 않는다. 인증 값은 읽기 결과나 로그에 남기지 않는다.

실제 모바일 카드의 제목과 고유 주소, 본인 글 수신 결과, 앱의 저장된 주소가 모두 일치해야 삭제를 진행하도록 했다. 키 입력 직전 재검사 콜백을 공통 Surface에 추가했다. 현재 서비스 코드에 정의된 단일 글 삭제 경로와 두 대상 필드만 허용하며 일괄 삭제·댓글 삭제·다른 대상·중복 및 추가 필드는 거절한다.

삭제 수정 회차는 다음과 같다.

1. 좌표 입력 대신 검증된 컨트롤에 키보드로 이동하도록 수정했다. 메뉴가 문서 끝에 있어 앞으로 135회가 필요했고 기존 100회 제한에서 멈췄다.
2. 가까운 방향을 택하도록 수정했으나, 실제 숨김 WebView는 문서 맨 앞에서 Shift+Tab으로 순환하지 않아 다시 멈췄다. 관측된 포커스 이동은 외부에 보존했다.
3. 순환을 가정하지 않는 이동과 충분한 유한 횟수를 적용했다. 포커스 이동 중 과거 글이 계속 추가되지 않도록 초기 피드를 고정하고, 현재 서비스의 단일 글 삭제 요청 계약과 확인창 검증을 적용했다. UI 요청 대기도 삭제 절차의 길이에 맞춰 늘렸다. 실제 요청은 장벽에서 다시 차단됐다.

마지막 요청은 정확한 삭제 경로와 band_no, post_no 필드 이름까지 관측됐다. preflight는 200이었지만 삭제 XHR 성공 응답은 없었고 클라이언트 차단이 관측됐다. 세부 내부 거절 조건은 포착하지 못했다. 성공으로 표시하거나 네 번째 수정으로 우회하지 않았다.

## 남은 작업과 증거

시험 글은 아직 남아 있다. 앱 삭제·삭제 후 재읽기·등록 기록의 삭제 완료를 검증하지 못했다. 삭제 성공 캡처도 만들지 않았다. 소유자의 한도에 따라 더 이상의 삭제 수정·시도는 하지 않는다.

일반 발행의 응답 식별값과 모바일 게시 완료 읽기는 이번 한 번의 제출로 정상화·재검증하지 못했다. 이번 기록은 엄격한 단발 복구로만 게시 존재를 확인했다. 다음 작업은 외부에 남긴 마지막 요청 형태와 거절 조건부터 검토해야 한다. 새 글을 만들어 원인을 재현해서는 안 된다.

외부 summary.txt에 생성 횟수, 현재 노출, 삭제 여부와 진행 시간을 계속 갱신했다. 새 캡처는 모두 g-*.png이며 기존 파일은 보존했다. 실제 밴드 이름·글 주소/번호·계정 이름·상품 문구·요청 값은 이 보고서·코드·커밋·PR에 넣지 않는다.

# WP19 밴드 생성 요청 차단 진단

## 결론과 실행 범위

**저장 증거는 생성 경로의 클라이언트 차단을 증명하지만, 차단기 내부의 개별 거절 조건은 증명하지 못한다. 실제 요청이 통과하도록 고쳤다고 주장하지 않는다.**

지정한 `codex/band-real-test`, 기준 `af1e1b2`, 초안 PR #23을 유지했다. 이번 작업은 진단·오류 표시·회귀시험이다. 실제 서비스 접속, 밴드 작성기 열기·입력·제출, 허용 파일 생성, 네이버 조작을 하지 않았다. 휴대폰 화면을 깨우거나 잠금 해제하거나 설정을 바꾸지 않았다. 요청한 APK 교체 설치만 수행했고 앱을 실행하지 않았다.

이전 두 제출 시각은 2026-11-16 20:53 및 21:58 KST이며 이번 제출은 0회다. 원시 증거와 실행 로그는 저장소 밖 `../runs/band-shots/`에 보존한다.

## 증거의 범위

- `network-errors.json`, `e-fourth-network-errors.json`: 공개 API 호스트의 `/v2.0.2/create_post`에서 네트워크 오류와 클라이언트 차단을 관측했다.
- `e-fourth-after-submit-job.json`: `BAND_POST_UNCONFIRMED`, `publicationUncertain: true`인 실패다. 어느 요청 검사 조건이 실패했는지 역산할 수 없다.
- `e-fourth-blocked-request-shape.json`: 내용이 `[]`다. 실제 메서드·본문·Content-Type·본문 완전성·대상 필드·전송 순서가 없다.
- 이전 `d-*`는 화면 캡처다. 저장 JSON 전체의 요청 메타데이터 키 점검에서도 본문·헤더·네트워크/요청 식별자를 발견하지 못했다. 결과는 외부 `diag-evidence-audit.json`에 있다.
- 외부 `summary.txt`는 허용 파일 소비, 재제출 없음, 글 부재 관측과 요청 본문이 없다는 제한을 명시한다.

대상 불일치, 인코딩, 본문 누락, sent 선점, 사전 생성 요청 중 어느 것을 과거 두 차단의 확정 원인으로 적을 근거가 없다. 실제 필드를 추측해 허용 범위를 넓히지 않았다.

## 차단 계층 추적

| 계층 | 코드에서 확인한 동작과 한계 |
| --- | --- |
| UI 네이티브 필터 | `MainActivity.kt`는 로컬 UI와 허용 사진만 처리한다. 별도 밴드 Surface WebView의 XHR 경로가 아니다. |
| CSP | `core/src/server.ts`는 로컬 `/ui/` 응답에만 앱 CSP를 설정한다. 밴드 문서에 삽입하지 않는다. 당시 원격 문서 자체 CSP는 저장돼 있지 않다. |
| Surface 네이티브 필터 | `SurfaceHost.kt`는 정책이 있을 때 주 프레임 이동만 제한한다. 나머지 요청은 통과한다. 거절 응답은 빈 WebResourceResponse이며 CDP의 BlockedByClient 명령이 아니다. |
| DevTools 중계 | `DevtoolsRelay.kt`는 바이트 중계다. AndroidSurfaceHost는 공통 CdpSurface를 사용한다. |
| 페이지 JS | 밴드 문서의 fetch/XHR를 덮어쓰는 앱 코드는 없다. JS 요청 정책은 BandDirectory가 CDP inspector로 제공한다. |
| CDP 정적 차단 | blockedRequests가 inspector보다 우선한다. 밴드 Directory에는 별도 정적 차단 설치 호출이 없다. 새 진단은 이 계층을 SURFACE_STATIC_BLOCK으로 구분한다. |
| CDP 본문 복구 | 인라인 본문이 없거나 Content-Length와 다르면 networkId로 조회한다. 조회 실패·식별자 부재·최종 길이 불일치는 승인 근거가 되지 않는다. 이전에는 조건별 기록이 없었다. |
| 요청 정책 | HTTPS 출처, POST, 생성 경로, armed, 미전송, 완전한 본문, 최상위 band_key 하나와 선택 대상 일치를 모두 요구한다. 경로 추가만으로 나머지 조건이 증명되지 않는다. |
| JSON/폼 | JSON, URL 인코딩 폼, 파일 없는 multipart를 메모리에서 파싱하며 중복 키를 유지한다. 실제 인코딩·필드 위치는 저장 증거에 없다. |
| 호스트/경로/쿼리/버전 | 관측된 생성 버전·경로는 허용돼 있다. 쿼리는 원래 경로 판정에 사용하지 않는다. 다른 호스트·버전·추가 경로는 거절한다. 이번에 다른 포트의 생성 출처도 거절하도록 좁혔다. |
| OPTIONS/사전 호출 | OPTIONS·지정 조회 POST·사진 업로드는 sent를 바꾸지 않는다. 알 수 없는 쓰기는 차단하며 생성 슬롯을 소비하지 않는다. 실제 사전 호출 전체 순서는 저장되지 않았다. |
| 일회성 상태/리다이렉트 | sent는 대상 검사를 통과한 생성 요청에서만 동기적으로 설정된다. 응답 실패나 리다이렉트 뒤에도 초기화하지 않는다. 일치하는 선행 생성이 있었는지는 당시 증거로 알 수 없다. |
| 허용 파일 | consume은 버튼 마지막 재확인 뒤 mousePressed 직전, arm 직전에 실행된다. 이후 차단돼도 복구하지 않는다. 소비 시점은 바꾸지 않았다. |
| 결과 표시 | 확인된 결함: BandExecution과 runner가 제출 뒤 실패를 BAND_POST_UNCONFIRMED로 덮었고 UI는 모두 “확인 필요”로 표시했다. 차단 사유가 보존되지 않았다. |

앱 소스에서 BlockedByClient를 명시적으로 보내는 곳은 CdpSurface의 Fetch.failRequest다. 이는 차단 계층을 설명하지만 당시 어떤 inspector 조건이 false였는지 증명하지는 않는다.

## 수정

- 본문 없음/조회 식별자 없음/조회 실패/길이 불일치, 인코딩/파싱 실패, 대상 없음/중복/타입/불일치, 미승인/기전송, 출처/메서드/경로, 정적 차단/inspector 예외를 고정 코드로 구분한다. 본문·필드 값·헤더·쿠키·토큰·대상/계정/상품 정보·주소·임의 예외 문구를 기록하지 않는다.
- 디버그 Android 빌드는 앱 전용 `wp19/barrier-codes.jsonl`에 코드만 순서대로 남긴다. 작업에는 최대 128개 코드와 첫 거절 사유를 남긴다. 로그 실패가 승인이나 재시도를 유발하지 않는다.
- 생성 요청이 거절되면 해당 승인을 닫아 편집기의 후속 생성 재시도도 거절한다. OPTIONS·조회·업로드와 무관한 차단된 쓰기는 생성 슬롯을 소비하지 않는다.
- 생성 요청을 하나도 허용하지 않았고 Fetch.failRequest 응답까지 확인한 경우만 `BAND_POST_BLOCKED:<고정 코드>`로 기록한다. 결과와 등록 기록은 “게시 요청 차단 · 게시되지 않음”, 승인은 소진됐으며 자동 재제출하지 않는다고 알린다.
- 이미 생성을 허용했거나 차단 명령 응답을 확인하지 못했으면 “확인 필요”를 유지한다. 중복 차단을 앞선 요청의 미전송 증거로 오인하지 않는다. 과거의 모호한 실패 기록을 소급해서 미게시로 바꾸지 않는다.
- 같은 작업의 resume/재제출을 막고 기록 재시도는 기록만 반복한다. 파일 재생성·자동 재승인·자동 재제출은 추가하지 않았다. 생성 경로·필드 형식을 추측해 확장하지 않았다.

## 실서비스 없이 입증한 범위

`band-barrier-replay.test.ts`는 루프백 WebSocket CDP 서버로 실제 CdpSurface.intercept → BandDirectory 코드를 실행한다. AndroidSurfaceHost가 사용하는 동일 코드이며 실제 서비스 통신은 없다.

- 증거의 정확한 생성 호스트/경로를 사용하되 대상·본문·순서는 합성이다. OPTIONS → 조회 → 사진 업로드 → 생성 → 중복 생성 순서에서 JSON·폼·multipart 및 인라인 본문 누락/복구를 통해 생성이 정확히 한 번 통과한다.
- 알 수 없는 합성 사전 쓰기는 차단하면서 뒤의 정상 생성 슬롯은 보존한다. 동시 생성, 리다이렉트 재전송, 정적 차단, 변경된 출처/버전/경로와 본문·대상 오류를 구분한다.
- 실제 Chromium 루프백 작성기는 버튼 1회 입력 뒤 미게시 결과·정확한 기록 사유·기록 실패/재시도 뒤 사유 보존과 추가 제출 없음을 확인한다. 기존 허용 소비 시험도 소비 1회와 재제출 방지를 확인한다.
- 실제 본문과 전체 순서가 없으므로 실제 편집기의 완전한 녹화 재생이라고 부르지 않는다. 실제 본문 허용 여부나 실서비스 성공은 입증되지 않았다. 폰에서 로컬 작성기를 열지도 않았다.

## 다음 실제 제출의 위험

개별 거절 조건과 실제 페이로드/응답 규격은 미확정이며 다음 별도 승인 실행에서도 차단될 수 있다. 새 `ALLOWANCE_CONSUMED → ARMED → 거절 사유 → BLOCK_CONFIRMED` 코드로 당시 실패 조건을 payload 저장 없이 특정할 수 있다. 요청이 허용되더라도 성공 응답 식별값과 게시 문서 재열람 전에는 완료가 아니다. 이번에는 다음 실서비스 제출이나 허용 파일 생성을 승인받거나 수행하지 않았다.

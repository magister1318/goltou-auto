- 처음 등록 기록의 삭제 준비는 종료된 `failed` 작업을 진행 중으로 취급해 확인창을 열지 못했다. 삭제 대상의 소유권·저장 주소·상품 변경 검사는 유지하고 terminal `failed` 상태를 허용했다. 실행 중·기록 실패·각종 대기 상태는 계속 거절하는 회귀시험을 추가했다.

최종 설치 APK는 커밋 전 작업 트리에서 빌드했으므로 앱 로그의 commit 표시는 기반 커밋이다. APK의 SHA-256은 저장소 밖 `c2-apk-final-sha256.json`에 보관했다.

1차 종료 당시 새 공개 글은 없었다. 실제 발행 확인 한 번은 앱 요청 차단기에서 거절됐으며 공개 발행·게시 페이지 검증·삭제 왕복을 완료하지 못했다. 당시 재발행하지 않았다. 아래의 새 승인 필요·미실행 설명은 1차 시점의 기록이며 현재 결과는 위 2차를 기준으로 한다.

## 준비와 Phase 0

- 읽기 전용 최초 기기 점검에서 깨어 있음·잠금 해제·골투오토 전면을 확인했다. 깨우기·잠금 해제·설정 변경 없이 앱만 조작한다.
- `gh` 인증 helper와 비대화 Git 환경변수를 확인하고 `main`을 `f98b7c8`로 갱신했다. 최초 디버그 빌드와 `adb install -r`가 통과했다. 필요한 코드 수정이 확인돼 `origin/main`에서 `codex/blog-publish-verify`를 만들었다.

- 이전 밴드 전용 디버그 점검 파일이 남아 있었다. 블로그 전용 파일이 우선하도록 추가한 뒤 다시 설치했다. 블로그 전용 설정 뒤에는 밴드 상태를 미확인으로 유지했다. 단, 최초 main APK 설치 직후 앱이 자동 재시작하면서 남아 있던 밴드 전용 설정으로 10:35:29.650 KST에 밴드 자동 연결 확인 1회가 실행됐다. 이 사실은 사이트 필드를 재점검해 발견했으며 앞선 무접근 설명을 정정한다. 사용자의 밴드 무접근 지시에서 벗어난 동작이다. 밴드 목록·편집기 입력·게시·삭제는 하지 않았다.
- 별도 앱 읽기 점검 창은 저장·수정·발행·자동저장과 로그인 redirect를 차단한 상태로 열었다. 기존 미완성 글 안내를 읽었으나 Phase 0에서 처리하지 않았다. 이 안내 때문에 발행 계층을 비파괴적으로 열어 현재 radio를 읽을 수 없었다. 기존 실제 차단 프로브의 radio 매핑과 발행 직전 엔진의 독립된 label·wire 검사를 유지했다.
- 같은 블로그의 기존 공개 글과 목록을 읽기만 했다. PC canonical 주소는 `mainFrame`의 `PostView.naver`로 이어졌고 제목 `.se-documentTitle .se-text-paragraph`, 본문 `.se-main-container`/`.se-viewer`, 사진 `.se-component.se-image .se-image-resource`, PC 태그 `.wrap_tag a.itemTagfont` 구조를 확인했다. 모바일 태그는 별도의 서비스 class를 쓰므로 PC 검증 선택자와 혼동하지 않는다. 모바일 공개 글의 plain `openType` 값은 2였다.
- 삭제 링크 `.area_btn_postedit a._deletePost`, 수정·삭제 소유자 도구 각 한 개와 실제 위치 판독을 확인했다. 기존 글의 삭제 링크나 확인창은 누르지 않았다.
- 로드된 서비스 정적 코드에서 고정 native confirm 문구와 `deletePostFrm`의 POST `/PostDelete.naver`를 확인했다. 필드는 `blogId`, `cpage`, `categoryNo`, `parentCategoryNo`, `viewDate`, `sourceCode`, `logNo`, `currentPage`다.

## 수정과 회귀 검증

- 실제 공개 페이지에서 `String.prototype.trim` 호출이 CDP `throwOnSideEffect`에 거절됐다. 본문·제목·태그·삭제 좌표의 공백 처리에 `trimStart().trimEnd()`를 사용한다. 읽기 전용 제한은 유지한다. 서비스가 `trim`을 감싼 합성 브라우저에서도 기존 판독이 거절되고 수정 판독·삭제는 통과하는 회귀 시험을 추가했다.
- 전체공개 요청에도 기존 비공개와 같은 엄격한 전송 형태 검사를 적용했다. 잘못된 값·문자열 값·중복·충돌 공개 필드와 UI 증거 없는 요청을 거절한다.
- 등록 기록 삭제는 새 Surface에서 실제 확인된 요청 형태와 저장된 신원을 검사한다. 두 번째 요청, 불완전·중복·추가·누락 필드와 다른 대상은 거절한다. redirect 응답은 페이지 읽기로 확인한다.
- 발행·삭제 필드 이름과 삭제 고정 경로를 로그 허용 목록에 추가했다. 정적 차단과 inspector 예외도 사유·살균한 요청 형태를 기록한다. 본문 값·인증 헤더·쿠키를 남기지 않는 회귀 시험을 추가했다.
- 초기 브라우저 회귀 시험에서 공통 좌표 함수에도 `trim`이 남아 실패해 수정했다. 초기 발행 회귀 실행은 이미 발행 guard가 있는 진단 Surface에 삭제 guard를 중복 설치해 2개가 실패했다. 삭제 guard를 등록 기록의 새 Surface 경계로 옮겼다. 실패를 성공으로 계산하지 않는다.

## 실제 실행과 최종 확인

### 실제 실행 결과

- 원래 블로그 작업은 10:52:41.304 KST에 시작해 11:04:42.903에 단일 `uncertain:BLOG_PUBLISH_UNCONFIRMED`로 끝났다. 앱의 job 상태는 `failed`, 결과 화면과 등록 기록은 `확인 필요`이며 저장된 공개 글 주소는 없다. 성공이나 발행됨으로 바꾸지 않았다.
- API 상품과 이전 승인 상품의 제목·내용 해시를 앱 경로에서 대조했다. 블로그만·전체공개·선택 옵션 모두 꺼짐이며 실행 중 `job.preview`의 계획이 미리보기 계획과 정확히 같았다. 문구를 더하지 않았다. 발행용 작업 시작과 실제 최종 발행 확인은 각각 한 번이다.
- 수동 임시저장 요청은 한 번 허용·응답 확인됐고 새 편집기에서 같은 새 임시글의 신원과 원문 대조가 통과했다. 이번 목록 변화 신원은 `existingSameTitle=0`, `source=list-change`다. 앞선 소유자 임시글이나 다른 글을 삭제하지 않았다. 작업 중 미완성 글의 추가 선택은 나타나지 않았다.
- 11:04:40.043의 `RabbitWrite.naver` POST는 **이번에 추가한 공개 요청 검사**가 `BLOG_PUBLIC_REQUEST_UNCONFIRMED`로 거절했다. 직후 `Fetch.failRequest`의 정상 응답도 원래 작업 로그에 있다. 네이버 발행 응답이나 결과 글 주소는 없었다. 별도 수동 관측의 요청 형태에서는 `openType` 숫자 2였다. 인증 값이나 요청 본문을 보관하지 않았다.
- 앱 읽기 점검 창에서 자기 블로그의 게시물 링크 20개가 있는 목록을 읽어 같은 제목이 없음을 확인했다. 요청 단계의 거절과 목록 부재를 함께 근거로 **새 공개 글이 생성되지 않았음**을 확인했다. 삭제 대상이 없어 글 삭제나 다른 임시글 정리를 누르지 않았다.

### 차단 원인과 수정의 한계

입증된 원인은 서비스 오류가 아니라 앱의 새 공개 요청 검사 거절이다. 당시 고정 로그는 어떤 세부 조건이 실패했는지 구분하지 않았다. 따라서 실제 payload의 정확한 실패 분기를 입증한 것으로 보고하지 않는다.

검사에는 일반 JSON 순회기의 기본 깊이 8 제한을 그대로 적용한 결함이 있었다. 합성 rich document에서 서식 속성이 9단계에 있을 때 거절을 재현해, 문서 순회 제한을 32로 늘리고 JSON parser의 기존 32단계 상한은 유지하도록 수정했다. 깊은 위치의 중복·다른 공개 범위 값은 계속 거절하고 과도한 깊이도 거절한다. **이번 실제 요청이 이 깊이 분기로 거절됐는지는 미확정**이다.

최종 코드는 UI 근거·메서드·본문 완전성·인코딩·필드 목록·JSON·중복·공개 범위·깊이를 각각 고정 사유로 기록한다. 자동저장 고정 경로도 보존한다. 이 수정 뒤 실제 발행 확인이나 차단 프로브 클릭을 다시 하지 않았다. 새 실제 발행은 새 소유자 승인이 필요하다.

### 보관한 증거와 미검증

`../runs/blog-shots/`에 앱만 adb 캡처한 `b-preview.png`, `b-confirm.png`, 실제 확인 필요 결과 `b-result.png`, `b-history-failed.png`, `b-job-logs.png`를 보관하고 직접 확인했다. `wp25-log.txt`는 원래 작업의 시작·저장·차단·원문 비교·단일 종료 줄을 살균해 발췌했다. 진행 요약은 40줄 이내다.

실제 게시 상태와 삭제 상태가 없으므로 `b-history-posted.png`, `b-deleted.png`를 만들지 않았다. 게시글 제목·본문·굵기·링크 두 개·사진 29장·태그·전체공개, 게시됨 성공 화면과 주소 있는 기록, 원래 주소와 목록에서 삭제 확인은 모두 **미실행**이다. 기존 공개 글을 읽은 Phase 0 결과로 이번 게시 검증을 대신하지 않는다.

마지막 저장 편집기를 추가 입력 없이 읽은 결과, 본문 99문단·사진 29장과 계획의 정확한 text/bold/href 비교 차이 0을 확인했다. 표는 native table 0개이며 97~99번 문단에 각 2개 셀을 ` | `로 나눈 일반 줄 3개로 나타났다. 원문 날짜·가격과 순서가 같은 줄이며 실제 문자열은 외부 증거에만 있다. 앱 미리보기 표와 실제 **공개 게시글**의 외관 차이는 게시글이 없어 확인하지 못했다. 이 임시글 관찰을 공개 게시글 비교로 주장하지 않는다.

## 인계

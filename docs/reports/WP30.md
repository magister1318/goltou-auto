# WP30 영구 배포 서명과 전환 준비

2026-11-17. PR #29 병합 `5c549eb`의 main을 `gh repo sync --branch main`으로 갱신하고
`codex/release-signing`을 만들었다. [지시서](../wp/WP30-release-signing.md)의 범위다.

**휴대폰은 변경하지 않았다. 인증서가 DIFFERENT여서 설치하지 않는다. release는 WebView
원격 디버깅을 끈 현재 드라이버로 자동 등록을 할 수 없어 배포 준비 완료가 아니다.**

## 기존 상태와 보완

WP12에 외부 properties 검증·release signingConfig·버전 단일화·debug 실험 제거가 있었다.
빠진 것은 영구 키, 비밀 파일 추적 검사, v3 서명 명시, release용 WP28 게이트,
설정의 버전 표시와 데이터 전환 경로다. WP12의 release 원격 디버깅 예외는 이번 요구와 맞지 않았다.

- 외부에 RSA 4096·30년·일반 DN의 영구 키를 생성했다. 강한 무작위 비밀번호는 외부 properties에만
  쓰고 keytool 인자는 자식 프로세스 전용 환경 변수 참조를 사용했다. ACL 상속을 끄고 현재 Windows
  사용자 한 명만 FullControl을 갖게 했다. 한국어 보관 안내를 작성했다. 두 번째 장소 복사는 소유자 몫이다.
- ignore에 키·keystore.properties·release-key를 포함했다. `pnpm check:secrets`와 게이트는 Git index를
  검사해 staged 비밀도 거부한다. 값과 내용은 출력하지 않는다. 기존 외부 서명 설정과 누락 오류는 유지한다.
- release v2/v3를 명시했다. 패키지는 `kr.goltou.auto`, 버전은 1.0.0 (2)이며 설정에 표시한다.
- WP28 게이트의 `-Variant release`는 실제 APK의 변형·인증서·서명·내장 번들과 소스 커밋을 검사한다.
  설치 모드에는 설치 인증서 비교를 추가했고 SAME이 아니면 설치 전에 거부한다. clean HEAD와 해시 대조,
  검증한 동일 사본의 `install -r`만 허용하는 규칙은 유지한다.

공개 배포 인증서 SHA-256:
`B8EA4A8C931A8C711B2D4538ED8618045ABC202A3CF58B35639CCDACE5950665`.

## release의 발행 조건과 CDP 한계

| 경로 | 확인한 코드 |
| --- | --- |
| 앱 UI | 발행 선택과 최종 확인. `AppCore.start`와 `ChannelRegistrationRunner.start` 모두 작업별 `publishConfirmed` 요구. 임시저장은 블로그만 허용 |
| 블로그 | bridge의 `publishEnabled: true`. 로그인·계획·본문/사진/표 검증, 공개 범위와 신원을 확인한 단발 요청만 허용. `localPublish`/publishProbe는 배포 구성에 없음 |
| 밴드 | bridge의 `publishEnabled: !__GOLTOU_DEBUG__`로 release는 true. `publishAllowance`는 debug에만 주입하며 release에 `one-band-post.allow`/run-as 불필요 |
| 밴드 전송 | 소속 밴드·본문·사진 검증, 클릭 대상 재확인, 대상별 arm, 요청 allowlist·단발 전송, 응답 신원과 게시 페이지 재판독 |
| 시험 경로 | release 자산에서 허용 파일 이름·blog-only/band-only 파일·실험 명령과 복구 우회 코드 제외 검사. 공통 allowance 인터페이스/고정 사유 문자열은 남아도 파일 구현을 release에 연결하지 않음 |

허용 파일 없이 소유자 발행 경로를 선택해도 요청 차단기가 전송을 막는 것을 loopback fixture로
시험했다. 이는 Android release 실서비스 게시 성공 증거가 아니다.

블로그 draft 모드는 RabbitWrite/RabbitUpdate를 차단한다. publish 모드는 최종 UI 공개 범위를
읽고 publishArmed를 한 번 소비한 POST `/RabbitWrite.naver`만 허용한다. 완전한 본문·관측된 인코딩과
필드 집합·JSON 구조, 중복/충돌 공개 범위 부재와 openType(공개 2/비공개 0)를 검사한다.
`publishAttempted`는 클릭 전에 잠가 stop/resume나 불명확한 응답에서 재클릭하지 않는다.
밴드 create는 HTTPS의 정확한 create 경로, 한 개의 band_key/band_no와 선택한 소속 밴드 일치,
완전한 요청 본문과 armed/sent 상태를 요구하며, 허용 즉시 arm을 소비한다.

release는 debuggable/JNI debug false, `setWebContentsDebuggingEnabled(BuildConfig.DEBUG)`다.
현재 AndroidSurfaceHost는 DevtoolsRelay → WebView `/json/list` → CDP에 의존한다.
요청 allowlist도 CDP `Fetch.enable`과 POST 본문·응답 관찰로 동작한다. 디버깅을 끄면 상위 서버가
없으므로 **현재 release는 블로그 임시저장도 끝까지 실행할 수 없다. 발행·밴드 게시·서비스 연결 창도 같다.**
surface 생성 전에 `RELEASE_AUTOMATION_UNAVAILABLE`로 거부하고 알려진 로그 사유를 남긴다.
차단기 생략·디버깅 재활성화·DOM 쓰기로 우회하지 않았다. ‘원격 디버깅 off + 일반 자동 등록’은
미완료이며 별도 드라이버 작업이 필요하다. [공식 API](https://developer.android.com/reference/android/webkit/WebView#setWebContentsDebuggingEnabled(boolean))와
[배포 안내](../release.md)에 제약을 적었다.

WP20 JobLogStore와 logs.export는 release에도 연결한다. 네이티브 FileProvider/공유 chooser는
adb/CDP 없이 로그 ZIP만 내보내고 salt·세션을 제외한다. release 자산 시험은 로그 UI와 내보내기,
오프라인 코어 시작을 확인한다. 실제 release 기기의 부팅·공유 chooser는 미검증이다.

## 휴대폰과 데이터

읽기 전용 dumpsys에서 켜짐·잠금 해제·앱 전면, 설치 버전 0.1.0 (1), DEBUGGABLE을 확인했다.
dumpsys package의 짧은 signatures 값은 SHA-256이 아니므로 사용하지 않았다. pm path와 adb pull로
**공개 설치 APK만** 읽고 apksigner로 인증서를 확인했다. 설치 인증서 SHA-256은
`0B36F13C248D2E5EE9A73D9088828BE4DB7D470E9ECB6E66F35432DCF80DC75E`이며 배포 키와 **DIFFERENT**다.
설치·재시작·설정 변경·로그인 확인·앱 private 데이터 읽기/쓰기·백업·삭제는 하지 않았다.
네이버 저장 0, 공개 발행 0, 실제 밴드 동작 0, 서비스 삭제 0이다.

| 데이터 | 저장 위치와 전환 영향 |
| --- | --- |
| 등록 내역 본체 | AppCore → `/auto/posts/list`, 생성/결과는 `/auto/posts/start`, `/auto/posts/update`. 계약상 서버 `gf_auto_post`. 같은 계정 재로그인 후 읽음. 운영 API/DB에는 접속하지 않아 현재 동기화 완료 여부는 미확인 |
| 공통 설정 | `/auto/me`, `/auto/settings/save`, 계약상 `gf_auto_setting`. 앱 삭제로 서버 설정이 지워지지 않음 |
| 로컬 보조 기록 | post-metadata.json의 postNo별 공개 범위·표 폴백 표시. 백업 없으면 손실 |
| 개인 옵션 | preferences.json의 선택 옵션/최근 밴드 키와 polish-strength.txt. 백업 없으면 기본값 복귀 |
| 작업 로그 | private logs 폴더. 삭제 시 손실, 기존 ‘로그 내보내기’ ZIP으로 외부 보관 가능. salt는 옮기지 않아 새 앱의 기록 연결에 재사용하지 않음 |
| 로그인 | 골투 암호화 세션과 WebView 로그인 저장소. 전환 시 소유자가 세 서비스에 직접 재로그인. 쿠키·토큰·비밀번호는 이전하지 않음 |
| 진행 중 작업·복구 | 메모리 job·debug 복구 문맥·마지막 입력 제목·미완료 편집기 상태는 이전하지 않음. 전환 전에 작업과 결과 기록을 완료해야 하며 서버 저장 실패를 자동 복구한다고 주장하지 않음 |

설정에 ‘데이터 내보내기/가져오기’를 추가했다. 사용자가 Android 문서 선택기로 파일을 고른다.
고정 세 파일의 허용 필드만 JSON으로 옮기며 폴더를 순회하지 않는다. 스키마·버전·크기·기록 키·필드를
모두 검증한 뒤 쓰고, 기존 메타데이터를 합치되 공개 범위 충돌은 쓰기 전에 거부한다. 입출력 동안
다른 명령을 잠그고 취소 시 바꾸지 않는다. 쓰기 실패는 기존 파일로 복구를 시도한다.
강제 종료/전원 손실까지 세 파일 전체의 원자성을 보장하지 않으므로 원본 백업은 보관해야 한다.
로그는 별도 ZIP 보관이며 앱으로 다시 가져오지는 않는다. 휴대폰에서 백업 UI를 실행하지 않았다.

### 안전한 전환 제안 — 실행하지 않음

1. 현재 debug 앱을 유지한다. 원격 디버깅 off에서도 입력과 POST 본문·응답 통제를 보장하는 드라이버를
   먼저 검증하고 별도 기기/시험 계정에서 release 시작·연결·임시저장 재열람·로그 공유를 확인한다.
2. 별도 승인 작업에서 현재 앱과 **같은 인증서**의 백업 지원 debug APK를 WP28 게이트로 install -r
   업데이트한다. 백업 UI는 구현했지만 현재 휴대폰에는 설치하지 않았다.
3. 진행 작업·서버 기록 실패를 마치고 같은 계정의 등록 내역을 확인한다. 데이터 JSON과 로그 ZIP을
   앱 밖과 두 번째 안전한 장소에 보관하고 다른 시험 설치에서 가져오기를 대조한다.
4. 백업·서버 내역·새 release 동작이 확인된 뒤 소유자가 기존 앱 삭제가 필요한 전환 시점을 결정한다.
   삭제/재설치는 별도 명시적 승인 작업이며 이 WP에서는 실행하지 않는다.
5. 새 앱에서 세 서비스에 직접 로그인하고 서버 내역/공통 설정을 읽고 로컬 백업을 가져와 대조한다.
   로그 ZIP은 외부 보관한다. 이후 같은 배포 키로 업데이트한다.

## 검증 결과

최종 게이트·APK 검사 후 이 절을 갱신한다. 현재 타입 검사·assembleDebug,
Android 단위시험 5개와 buildSrc 10개를 통과했다.
초기 자산 시험은 공통 라이브러리 고정 사유까지 제거돼야 한다는 잘못된 단언으로 실패했다.
release에 파일 구현이 주입되지 않는 검사로 고친 뒤 자산 시험은 통과했다.

실기기 release 설치·부팅·임시저장·발행·문서 선택기 백업/복원은 미검증이다.
별도 드라이버 미구현과 서명 불일치 때문에 자동 등록 배포 완료로 볼 수 없다.

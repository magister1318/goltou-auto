# WP49 블로그 태그 입력칸 스크롤 수정

## 실기기 근거

- 2026-11-20 13:10, S24(SM-S928N)의 1.1.4(19), post 78, trace 20, 상품 1387에서 태그 창에 칩 13개가 있었다. `clientHeight=71`, `scrollHeight=156`이었고, 휠 0~8회 내내 `scrollTop=0`과 `DIV.set_option_detail`이 관측됐다. `observe()`와 `closeTagLayer()`가 `BLOG_TAG_FOCUS_LOST` 및 `BLOG_TAG_LAYER_NOT_CLOSED`로 끝났다.
- 숨은 WebView의 바깥 크기는 456×320이고 CDP 에뮬레이션 크기는 1280×900이었다. 실제 마우스 클릭은 동작했다. 직접 보낸 CDP 휠 3회 동안에도 `scrollTop=0`이 유지됐고, `Input.synthesizeScrollGesture`는 `Position out of bounds`를 반환했다.
- 사용자 실기기 확인에서 iframe 안 `#tag-input`에 `scrollIntoView({block:'nearest',inline:'nearest'})`를 보냈을 때 태그 상자의 `scrollTop`이 68.3이 됐다. 윈도우 `scrollY=0`과 칩 13개가 유지됐다. 입력칸 중심의 hit는 입력칸 자체였고, 그 위치로 실제 마우스를 클릭했을 때 `activeElement`가 `#tag-input`이었다.

## 변경

- `codex/v114`의 `3657a75`에서 작업했다. 첫 태그 입력, `observe()` 재열기, `closeTagLayer()`가 공통으로 사용하는 입력칸 클릭 경로를 수정했다.
- 입력칸 중심이 가려지면 `scrollIntoView`를 한 번 호출하고 위치와 hit를 다시 읽는다. 계속 가려져 있으면 태그 상자의 `scrollTop`을 `scrollHeight`에 한 번 맞추고 다시 확인한다. Surface의 스크립트는 스크롤 위치만 움직인다. 스크롤 단계마다 칩 개수와 입력칸이 속한 창 및 상위 창의 `scrollY`를 비교한다. 값이 달라지거나 두 번의 위치 조정 후에도 입력칸이 가려져 있으면 `BLOG_TAG_FOCUS_LOST`로 중단한다.
- CDP 마우스 클릭 직전에 입력칸 자체가 hit인지 재확인하고 클릭 후 포커스를 읽는다. 닫기는 포커스 확인 후 Escape를 누르는 기존 경로를 쓴다. `CdpSurface.wheel`은 회귀 시험에서 기존 휠 동작을 재현할 때 사용한다.
- `blogTag` 결정 로그에 단계, 방식(`none`, `scrollIntoView`, `scrollTop`), 상자 높이, 스크롤 위치·칩 수·편집기 창 `scrollY`의 전후 값, hit를 남긴다. 성공과 실패 모두 전송용 trace 허용 목록을 통과한다. 이 로그는 태그 개수와 허용된 hit 이름을 사용한다.
- Android 버전을 1.1.4(20)으로 올렸다.

## 구현한 내용

1. `core/src/convert`: parse5 7.3.0으로 HTML을 문단(굵게·줄바꿈·인라인 링크), 원본 사진, 표, 구분선, 단독 링크로 나눈다. 스크립트·스타일·추적 요소·빈 문단·불필요한 속성은 제거 사유와 소스 위치를 기록한다. 깨진 태그, 표 제목과 중첩 표의 글자도 처리한다.
2. 블로그와 밴드의 순서 있는 입력 계획을 만든다. 제목은 그대로, 출발일·가격·골프장은 API 배열 그대로 사용한다. HTML에 없는 대표 사진은 앞에, 본문 사진은 원래 커서 위치에 둔다. 인접 사진만 묶는다. 밴드 표는 행별 글자 목록으로, 링크 서식은 주소가 있는 글자로 푼다. 끝 문구·링크 카드는 선택한 경우에만, 해시태그는 설정값으로 조립한다.
3. `core/src/verify`: 공백을 정리한 글자 수·글자 내용·문단 수와 순서·사진 수와 순서·가격·출발일·골프장을 비교하고 불일치 항목을 돌려준다. UI의 대조 문구와 실행 막대가 실제 결과를 사용한다. 코어도 기록 생성 전에 불일치를 차단한다. `Observation`과 `compareDocuments`를 저장 후 재열람에도 쓸 수 있게 공개했다.
4. `core/src/media`: 껍데기가 준 앱 전용 경로에 원본 바이트를 기록하고 완료·실패·종료 때 정리한다. API가 준 정확한 http/https 주소만 허용하며 자격 증명 포함 주소와 리다이렉트를 거부한다. 한 장이라도 실패하면 중단한다. 내려받는 중 멈춤·재개와 정리 실패의 실패 기록도 시험했다.
5. `core/src/polish`, `sites/src/ai-mode`: DAF의 입력 확인·응답 수신 확인·응답 추출 규칙 중 필요한 부분을 Surface 공통 API로 옮겼고 파일 위에 출처를 적었다. 숨김 `ai` 세션(`goltou-ai`)에서 입력 명령으로만 요청한다. 새 요청의 수신 표시와 새 응답을 확인하며, 이전 응답이나 입력창에 남은 원문을 답으로 쓰지 않는다. 로그인·동의·차단 화면은 조작하지 않는다.
6. 숫자·날짜·금액·주소·골프장 이름의 보존과 추가 숫자·길이 70~130%·번호와 문단 수를 검사한다. 어긴 문단은 원문을 유지한다. 숫자가 하나라도 든 문단, 표·가격·출발일 줄은 보내지 않는다. 링크·굵게 등 서식이 있는 문단도 서식을 지키기 위해 원문을 유지한다. 사용 불가·로그인 요구·잘못된 형식은 실패 대신 원문 유지 안내로 돌아온다.
7. 확인 화면에 문단별 원문/다듬은 글과 개별 되돌리기를 추가했다. 다른 선택 옵션만 바꿀 때는 검증 결과와 되돌린 선택을 재사용한다. 다듬기 전 입력 계획을 HTML 원문과 독립 대조한 뒤 검증된 문장 수정만 적용하므로, 다듬기를 켜도 원래 자료의 누락을 숨길 수 없다. 기존 B안의 색·얇은 줄·실행 막대를 사용했다.
8. Android 껍데기가 실제 준비 의존성을 주입해 기존 등록 작업의 사진 내려받기(2단계)와 본문 정리(3단계)를 수행한다. 뒤의 사이트 단계는 가짜다. 현재 앱의 가짜 상품 사진 URL은 번들 예시 사진의 원본 바이트로만 매핑하고 실제 골투 주소는 연결하지 않는다. HTTP 다운로드 자체는 로컬 서버로 시험했다.
9. `protocol.ts`에 `stopped_before_post` 이름만 추가했다. 실험 화면에는 예시 소개 문단 3개를 한 번 보내는 `AI 다듬기 실험`을 추가했다. 밴드 게시 전 멈춤 동작의 구현은 WP6에 남긴다.

## 확인하지 못한 것과 다음 작업

- 실제 Google AI 응답을 최종 문단으로 읽고 채택하는 과정은 아직 검증하지 못했다. 이번에 허용된 실기기 시도 2회를 모두 사용했으므로 추가 실행은 하지 않았다. `unavailable`의 정확한 서비스 측 원인과 로그인 후 동작·프로필 유지 여부는 미확인이다.
- 링크·강조·줄바꿈이 있는 소개 문단은 서식 보존을 위해 다듬지 않는다. 사진이 든 표는 글자 행과 사진으로 풀어 쓰며, 원래 표의 폭·병합·테두리는 보존하지 않는다. 글자·사진의 순서를 독립 대조할 수 없으면 등록을 차단한다.
- WP5·WP6은 `InputPlan`의 사진 묶음 위치를 따라 입력하고 `PreparationWork.prepared`의 파일 매핑을 사용해야 한다. 저장 뒤 새로 읽은 내용은 `Observation`으로 맞춰 공통 비교 함수를 호출해야 한다. 업로드 후 사진 주소와 원본 사진을 대응시키는 실제 식별·대조는 아직 구현하지 않았다.
- 준비 단계 이후의 사이트 입력·저장·기록 완료는 여전히 모의 동작이다. 실제 네이버 임시저장이나 밴드 게시 전 멈춤을 이번 결과로 주장하지 않는다. 앱 강제 종료 뒤 잔여 임시 폴더 회수와 실제 기기 파일 전달도 별도 확인이 남는다.
- 운영 반영이나 main 푸시는 하지 않는다. 커밋·브랜치 푸시·초안 PR은 기존 gh 인증과 `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`를 사용한다. 계정 선택·로그인 창을 실행하지 않았다.

## 검토 1차 반영

1. **HTML 원문 독립 관측**: `verify/source.ts`가 원래 `contentsHtml`을 parse5로 별도 순회해 보이는 글자, 사진 원본 URL 순서, 중첩 표를 포함한 셀 글자, 글자와 사진의 배치 순서를 읽는다. 블록 빌더·조립기·파서의 제거 기록을 관측 기준으로 재사용하지 않는다. 입력 계획의 실제 글자를 대조하며, 밴드 링크 주소와 행 구분자는 실제 입력 글자가 그 생성 규칙과 정확히 맞는 경우에만 빼고 비교한다. API 대표 사진과 API 사실 대조도 유지했다.
2. **제거 허용 범위**: 주석, `script/style/iframe/object/embed/noscript/template/input/meta/link` 하위 내용, 주소가 없거나 1×1 또는 알려진 추적 주소인 사진, 공백이다. 속성 제거는 본문 글자 제거를 허용하지 않는다. 이 범위 밖 글자 누락·변경이나 글자/사진 순서 변경은 `sourceText/sourcePhotos/sourceTableCells/sourceOrder` 불일치가 되어 미리보기와 실행을 막는다. 잘못된 블록에 `empty-paragraph` 제거 기록을 덧붙여도 통과하지 않는다.
3. **순환 검사 회귀 시험**: 파싱된 블록을 일부러 변조해 문단 누락, run 누락, 문단 순서 변경, 표 셀 누락·순서 변경, 셀 글자를 일반 문단으로 이동, 사진 누락·위치 변경을 만들었다. 같은 잘못된 블록으로 조립한 두 계획의 기존 비교는 일치하지만, 두 채널의 독립 원문 검사와 미리보기는 모두 불일치가 된다. 8개 기존 HTML 예시도 모두 통과했다.
4. **사진이 든 표**: 해당 위치에서 셀 안 글자 앞/뒤, 옆 셀, 다음 행, 중첩 표 사진 순서를 유지해 글자 행과 사진 첨부로 푼다. 표 제목이 행 뒤에 있는 경우도 원래 순서에 둔다. `notices`에 배치 단순화를 기록하며 대조 줄에 `안내: 사진이 든 표를 원문 순서의 글자 행과 사진으로 풀어 썼습니다.`를 표시한다. 이 안내만으로 실행을 막지 않는다. 블로그·밴드의 중첩 표 사진 회귀 시험과 [로컬 미리보기](wp4/preview-table-notice.png)에서 확인했다.
5. **숫자 문단 전송 제외**: 금액·날짜뿐 아니라 모든 유니코드 Number 문자가 포함된 문단을 AI 대상에서 뺀다. ASCII·전각·아라비아 숫자·위첨자·로마 숫자·원문자·보충 평면 숫자를 시험했고, 대상이 숫자 문단뿐이면 AI를 호출하지 않는다. 기존 응답 검증기는 새 숫자를 거부하는 두 번째 방어선으로 유지했다.
6. **실기기 호환 보완**: 첫 실패 뒤 앱 진단으로 내장 Node `v18.20.4`의 유니코드 속성 정규식 미지원을 확인했다([device-runtime.json](wp4/device-runtime.json)). 전송 제외와 응답 검증 모두 Unicode 17.0 Number의 명시적인 146개 범위를 사용하도록 바꿨다. PC 시험에서 전체 코드포인트를 대조했고, 실제 Node 18.20.4에서도 숫자 문단 제외·응답 검증을 확인했다. 진단 필드는 지원 여부만 기록한다.

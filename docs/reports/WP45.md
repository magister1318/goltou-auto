# WP45 밴드 게시 사진 확인

## 원인과 근거

- **확정.** 1.1.1 실기기 제보에서 2026-11-19 16:05에 게시한 밴드 글 5268(운영 기록 69)은 본문, 줄바꿈, 해시태그, 링크를 통과했다. 77KB 전송 로그의 사진 검사에서 첫 상세 판독은 66/0, 두 번째 판독은 66/66 실패였고, 결과는 `PUBLISHED_READBACK_INCOMPLETE`였다. 두 번째 판독에는 `UPLOAD_PATH_MISMATCH`와 `DOM_ORDER_MISMATCH`가 없었다. WP44의 `verifyFullBandPost`에서 같은 사진 수로 이 두 사유 없이 실패하는 조건은 API 목록이 없는 콜라주를 일괄적으로 불완전하다고 본 경우다. 같은 글을 삭제하기 전에 읽기 전용 WebView에서 `ul.uCollage`의 `li.collageItem` 이미지 66장과 `?type=w520` 크기 쿼리를 관찰했다는 제보도 이 경로와 일치한다.
- **미확정.** 운영 DB 로그 원문과 당시의 상세 API 응답 및 작성기 피드 응답은 제공된 제보에 포함되지 않았다. 66/66 실패 당시 검증기에 전달된 API 목록이 없었다는 점은 위 분기로 확인할 수 있다. 각 출처가 비었던 구체적 이유와 실기기의 업로드 대 DOM 경로 일치는 다음 관측이 필요하다. `bapi-kr.band.us`의 배치 허용 줄은 요청이 통과했다는 증거다. `[other]` POST 차단 줄은 알려진 배치 또는 피드 경로와 연결되지 않아 당시 사진 목록 부재의 원인을 확정할 수 없다.

| 사진 출처 | 코드에서 사용하는 근거 | 5268번 글에서 확인할 수 있는 범위 |
| --- | --- | --- |
| 상세 API | `openPublishedView`의 상세 WebView. 읽기 전용 배치에 포함된 대상 글 조회의 응답에서 성공 결과, 정확한 밴드·글 식별, 단일 일치, `photo_count`와 `attachment.photo` 수 및 경로를 확인한다. | 배치 허용 줄이 있었다. HTTP 결과, 응답 본문 캡처, 대상 글과 첨부 목록 파싱 결과는 미확정이다. |
| 작성기 피드 캐시 | `getSurface`가 작성기 WebView에서 관찰한 피드 GET의 최신 목록. 같은 글, 작성자 본인, 게시 시각 범위, 업로드 수와 같은 `photo_count`, 전체 첨부 경로가 필요하다. | 피드 응답 유무, 대상 글의 포함 여부, 응답이 일부 사진만 제공했는지는 미확정이다. |

| 상세 DOM | 대상 글 경로에서 단일 본문과 미디어 슬롯을 읽는다. 콜라주 이미지의 상대 순서는 DOM 슬롯 순서에서 얻는다. | 첫 판독은 0장, 두 번째 판독은 66장이었다. 삭제 전 읽기 전용 확인에서도 66장을 관찰했다. |

## 변경

- API 증거가 없을 때 콜라주의 각 슬롯에서 읽은 경로가 업로드 목록의 같은 위치와 모두 일치하면 사진 검증을 통과한다. 기존 경로 비교가 크기 쿼리를 제외하고 경로를 대조한다. 65장, 주소가 비어 있는 슬롯, 순서 변경, 다른 사진 경로는 검증 실패로 남는다.
- 첫 상세 화면이 66/0이면 제한 시간까지 읽기 전용 재판독으로 사진 슬롯을 기다린다. 화면이 끝까지 66/0이면 `PHOTO_SOURCE_MISSING`을 남기고 기존 모바일 상세 재시도를 실행한다. 모바일 화면에서도 본문, 태그, 링크, 사진 경로와 순서를 다시 대조한다.
- 사진 출처마다 시도와 결과를 기록한다. 배치 차단 사유는 같은 엔드포인트의 차단이 확인된 경우에 기록한다. 요청 미관찰, 허용 뒤 응답 미관찰, HTTP·서비스 거절, 파싱 실패, 식별 불일치, 사진 수 불일치, 읽을 수 없는 경로를 구분한다. API 후보를 사용할 수 없는 경우에도 DOM 대조가 성공하면 작업은 확인 완료로 처리된다.
- 출처 로그는 `band.photo.detail_api`, `band.photo.cached_feed`, `band.photo.recovery_feed`, `band.photo.detail_dom`에서 찾을 수 있다. 상세 화면의 `attempt`는 데스크톱 1, 모바일 2다.
- 기존 로그 전송 제한 512KB를 적용한다. 새 진단에는 고정 사유, 개수, 슬롯 위치, HTTP 상태, 일치 여부를 사용한다. 사진 경로 대조에는 기존의 허용된 CDN 호스트, 파일명 끝 8자, 크기 접미사 유무를 사용한다.
- Android 앱 버전을 1.1.2(versionCode 16)로 올렸다.

## 검증

- `pnpm install --frozen-lockfile`, `pnpm typecheck`, `pnpm build`, `pnpm check:secrets`를 통과했다.
- Node 18.20.4에서 실행 소스 113개와 번들 2개의 호환 검사를 통과했다. 밴드 판독·식별·로그와 런타임 호환성 관련 시험 103개도 같은 버전에서 통과했다.
- `apps/android`의 `gradlew.bat assembleDebug --console=plain --no-daemon --offline`이 성공했다. `aapt dump badging`에서 `kr.goltou.auto`의 버전 1.1.2 및 versionCode 16을 확인했다.
- 새 브라우저 재현의 첫 실행은 66장 입력과 첫 상세 화면의 제한 시간 대기를 포함해 합성 시험의 시간 제한에 도달했다. 새 시나리오에만 더 긴 시험 시간 예산을 적용했다.
- `pnpm test --maxWorkers=4`에서 109개 파일의 1,346개 시험을 모두 통과했다. `scripts/check-test-report.mjs`로 필수 런타임 시험 6개를 포함하고 건너뜀과 TODO가 각각 0개임을 확인했다.
- 브라우저 재현은 첫 상세 화면의 66/0과 `PHOTO_SOURCE_MISSING`, 모바일 재시도, API 목록이 없을 때 `?type=w520`가 붙은 DOM 66장으로 확인 완료되는 흐름을 검증했다. 작성기 피드가 10장만 제공한 경우와 생성 응답으로 글을 식별해 복구 피드가 생략된 경우의 출처 로그도 확인했다. API로 확인한 66장과 API에서 한 장이 누락된 기존 사례도 통과했다. 콜라주 세 사례의 전송 로그는 각각 64,000바이트 미만이었고 잘림 표식이 없었다. 새 재현에서는 원래 사진 경로, 크기 쿼리, 게시 주소, 합성 토큰 값이 전송 로그에 남지 않음을 확인했다.

## 다음 확인

- 검증은 로컬 재현과 디버그 APK 빌드로 수행했다. 실제 게시, 휴대폰 설치, 운영 서버·DB 접속은 수행하지 않았다.

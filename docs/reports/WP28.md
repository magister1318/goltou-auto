# WP28 블로그 새 공개 글의 첫 삭제 성공 확인

현재 공개 시험 글은 없다. 새 글 한 건을 전체공개로 발행해 앱의 **발행했습니다** 화면을 확인했고, 앱의 첫 삭제 작업도 단일 `succeeded`로 끝났다. 서비스 발행 요청 1회, 삭제 요청 1회이며 복구 삭제 요청은 0회다. 이번 잔여 임시글은 0개다.

## 기준과 범위

- `gh repo sync --branch main`으로 main을 갱신하고 병합 커밋 `5118a2f`의 `origin/main`에서 `codex/blog-delete-verify`를 만들었다. 네트워크 Git 작업과 PR 작성에는 `gh`를 사용하고 비대화형 인증 환경 변수를 적용했다.
- 사용자 승인에 따라 공개 발행은 한 건만 진행했다. WP27과 같은 상품·계획·사진 29장, 블로그만 선택, 전체공개, 문장 다듬기·글 끝 문구·링크 카드 모두 꺼짐을 앱에서 대조했다.
- 게시·삭제 실행 코드는 병합된 main 그대로다. WP27의 `c9cc185` 목록 안정화 수정에서 **새로 만든 글의 첫 삭제**를 시험했다. 이번 변경은 설치 게이트·빌드 검사·시험·문서다.
- 설치 전과 입력 중 기기 화면 켜짐·잠금 해제·골투오토 전면을 확인했다. 깨우기·잠금 해제·설정 변경·로그인 입력은 하지 않았다. 설치는 `adb install -r` 한 번이다. 밴드 탐색·로그인 확인·입력은 0회다.

## 내장 Node 호환성 원인과 설치 게이트

기존 `runtime-compatibility.test.ts`는 `packages/sites/src` 전체를 재귀 검사하므로 문제 파일인 `band/posted.ts`도 포함한다. WP27에서 문제가 된 정규식 구문을 원래 경로와 엔진 번들 이름으로 다시 검사하는 회귀시험을 추가했다. 기존 AST 검사 조건도 이 구문을 검출함을 확인했다. **문제 파일이 빠진 것이 아니라, 해당 변경의 전체 시험 완료를 설치의 선행조건으로 강제하지 않은 것이 당시 유출 원인이다.** WP27 보고서에는 중간 전체 시험 중단과 첫 수정 APK의 시작 실패가 구분돼 있다. 나중의 통과 결과를 그 첫 APK의 사전 검사로 간주하지 않는다.

별도의 공백도 닫았다. 기존 검사는 core/sites/surface의 TypeScript 정규식 리터럴만 검사했고, Android bridge·api-client·번들에 들어오는 의존성·실제 APK 자산은 검사하지 않았다.

- 소스 검사 범위에 bridge와 api-client를 추가했다. 공통 검사기는 리터럴뿐 아니라 문자열·템플릿에 담긴 Unicode 속성 정규식도 거부한다.
- `build-core.mjs`는 완성된 `core.cjs`와 `engine.cjs`의 CJS 문법 및 해당 비호환 패턴을 검사하고, manifest에 전체 소스 커밋을 넣는다.
- `scripts/check-apk-compat.ps1`은 APK ZIP **안의** 두 번들을 추출해 검사한다. 파일 누락·중복 또는 manifest 커밋 불일치는 거부한다. 정상 ZIP, 과거 오류 리터럴, 생성자 패턴, 다른 커밋의 ZIP으로 실제 검사 진입점을 시험했다.
- 문서화한 `scripts/install-device.ps1`은 깨끗한 HEAD에서 의존성 설치 → 타입 검사 → 전체 시험 → 소스 호환성 검사 → 번들 빌드 → debug APK 빌드 → APK 내부 검사를 순서대로 실행한다. 시험 결과에서 건너뜀·TODO 0개와 런타임 시험의 포함·통과도 확인한다.
- 각 단계와 설치 직전에 HEAD·로컬 변경을 다시 확인한다. 검사한 APK 사본의 해시를 설치 직전에도 대조하며, 그 동일 사본만 `install -r`로 설치한다. 기기가 잠겼거나 꺼졌거나 앱이 전면이 아니면 설치하지 않는다. `-VerifyOnly`도 전체 게이트를 실행한다.

호환성 검사는 CJS 문법과 이번 ICU 없는 런타임의 정규식 비호환을 차단하는 검사다. 모든 내장 VM 기능의 에뮬레이션이라고 주장하지 않는다. 설치 후 실제 내장 런타임의 기동과 전체 게시·삭제 경로도 별도로 확인했다.

두 번째 차단은 이번에 추가한 게이트 자체의 JSON 판독 결함이다. Node의 명시적 UTF-8 JSON 판독으로 바꾸고 한글·따옴표·역슬래시를 담은 결과 파일의 실제 CLI 판독과 실패·건너뜀·TODO·런타임 시험 누락 거부를 시험했다. 두 중간 차단에서 기기 설치는 0회였으며, 최종 수정 커밋의 전체 검사를 다시 끝낸 뒤에만 설치했다.

## 실제 한 건 왕복

1. 앱의 최종 확인 화면에서 블로그 한 곳·전체공개를 확인하고 발행 확인을 한 번 눌렀다. 원래 발행 job은 **단일 terminal `succeeded`**, 앱은 **발행했습니다**다. 발행 요청 허용은 정확히 한 번이며 실제 작업 로그의 실행 커밋도 위 설치 커밋과 일치한다.
2. 등록 기록의 이번 글 주소·상품·제목을 대조한 뒤 실제 글을 새로 열었다. 제목·본문 99문단·본문 순서·굵기 구간·링크 두 개의 표시 글자와 href·사진 29장의 순서와 전체 로드·태그가 계획과 일치했다. 모바일 같은 글의 제목·주소와 `openType=2`도 확인했다.
3. 표는 native table 0개이며 셀을 ` | `로 잇는 일반 텍스트 세 줄로 정확히 일치했다. 미리보기 본문 폭은 약 314.6 CSS px, 실제 사진 폭은 500 CSS px다. 미리보기 링크는 14px/22.4px, 실제 링크는 15px/27px와 밑줄로 블로그 스킨을 따른다. 문구를 바꾸지 않았다.
4. 삭제 가능한 기록 중 이번 주소와 상품·제목이 일치하는 유일한 기록만 골라 **앱 등록 기록 → 글 삭제 → 삭제**를 한 번 확인했다. 삭제 job은 **한 개, terminal `succeeded` 한 줄**이며 소요 시간은 62,156ms다. 실패 job·복구 job·추가 서비스 삭제 요청은 없다.
5. 실제 `/PostDelete.naver` POST 허용은 한 번이다. 원래 주소의 삭제 안내를 읽고, 새 목록의 문서 완료·해당 블로그 링크·주소와 제목 부재를 안정화했다. 2,028ms 시점에 목록 준비 1/1, 링크 12개(최소 1개 조건), 대상 부재 0/0, 안정성 2/2를 확인했다. WP27의 `BLOG_POST_DELETE_LIST_UNCONFIRMED`는 발생하지 않았다.
6. 삭제 링크가 native 확인창을 여는 순간의 `SURFACE_DIALOG_PENDING` 입력 흔적은 기존 처리 경로가 받아 확인창의 메시지와 주소를 검증한 뒤 처리했다. 이것은 별도 실패 job이나 재시도가 아니며, 같은 삭제 job의 최종 결과는 위 단일 성공이다.
7. 기록 API를 다시 읽어 이번 기록의 `BLOG_POST_DELETED`·빈 글 주소를 확인했다. 화면에서도 이번 작업 시각의 정확한 행이 **블로그 삭제함**이며 글 보기·글 삭제 버튼이 없다. 별도로 새로 연 목록에서도 12회 연속 이번 주소·제목·제목 링크가 없었다.
8. 이번 새 임시글 1개는 발행에서 소모됐다. 읽기 전용 임시저장함에서 기존 같은 제목 글이 전후 각 1개임을 확인했으며 이번 잔여는 0개다. 기존 임시글이나 다른 글을 선택·수정·삭제하지 않았다. 마지막 앱 화면은 등록 기록이다.

저장소 밖 `../runs/blog-shots/`에 `f5-result-success.png`, `f5-history-deleted.png`, 확인·미리보기·작업 로그 캡처, `wp28-log.txt`, `wp28-summary.txt`와 원본 증거를 보관했다. 두 필수 캡처를 직접 열어 확인했다. 계정 이름·블로그 식별자·글 주소·상품 원문은 이 보고서나 커밋·PR에 넣지 않는다. 로그 추출은 `scripts/pull-logs.ps1`을 사용했고 salt는 추출하지 않았다.

이번 검증은 debug APK·기존 로그인 상태의 이 상품 한 건에 대한 실제 첫 왕복이다. 다른 상품·계정·release APK·다른 기기의 실서비스 왕복은 시험하지 않았다. 추가 공개 발행이나 삭제 복구는 필요하지 않았다.

다음 검토에는 설치 게이트의 커밋·APK 대조와 정적 호환성 검사의 범위, 보존한 첫 삭제 성공 증거를 넘긴다. WP27에서 미검증으로 남았던 새 글 첫 삭제는 이번 한 건으로 확인했다.

# WP20 작업 로그와 밴드 미리보기

**이번 시험 글은 앱의 첫 삭제 시도에서 삭제됐다. 현재 남아 있지 않다. 생성 제출 1회, 삭제 요청 1회다. 다만 복구 없는 게시 성공 조건은 충족하지 못했다.**

브랜치는 지시대로 PR #23의 `codex/band-real-test`에서 만든 `codex/job-logs`다. 실제 계정·밴드·글·상품의 식별정보와 원시 증거는 저장소 밖에만 보관한다.

## A. 영구 작업 로그

- 디버그·릴리스 공통으로 블로그 임시저장/발행/삭제, 미완료 정리, 밴드 게시/삭제, 로그인 확인, 밴드 목록의 작업별 JSONL과 색인을 추가했다. 단계 경계, 예외, 재시도, 입력 문단·사진 진행, 요청 검사, 화면 이동·확인창·선택자 누락과 검증 개수를 기록한다. 앱·소스 커밋·WebView·기기 모델을 작업 시작에 남긴다.
- 공통 surface의 타입 있는 기록 API와 core의 허용 목록 재구성을 쓴다. 자유 문장이나 호출자 객체를 직렬화하지 않는다. 요청은 허용된 필드 이름만, 경로 식별값은 자리표시자만, 기록 연관은 기기별 소금으로 만든 짧은 해시만 남긴다. 악의적인 런타임 호출과 종료 사유까지 시험해 JSONL과 색인에 값이 새지 않음을 확인했다.
- 매 줄 append/fsync, 종료 줄 1개, 부분 쓰기와 첫 줄 이전 강제 종료 복구, 재시작 interrupted, 30일/50MB 보관을 구현했다. 진행 중 작업 자체가 용량을 채우면 종료 공간을 남기고 멈추며 제출 가능성이 생긴 뒤라면 확인 필요로 남긴다. 서버 업로드는 없다.
- 로그인 화면의 후속 읽기와 닫은 뒤 재확인도 별도 작업으로 남긴다. 삭제 확인 불일치·취소·앱 종료는 대기 작업을 종료하고, 삭제 결과 기록만 재시도할 때는 새 로그를 연다. 재시작 색인에서도 실행기 실패 단계를 복원한다.
- 블로그/밴드 실행기, 삭제, 로그인/목록, 요청 차단기, CDP/surface와 native 호출에 연결했다. 기존 `wp19` 차단/삭제 진단과 중복 응답 형태 파일 쓰기를 대체했다. 기존 시험 도구의 입력·복구 문맥은 작업 로그로 가장하지 않는다.
- 설정 → 작업 로그의 단순 목록, 한국어 실패 단계·사유, 실패/확인 필요 등록 기록 안내를 추가했다. 공용 ZIP 내보내기는 FileProvider로 공유하며 인증 파일·소금은 제외한다. PC 추출 스크립트와 사용법은 `scripts/pull-logs.ps1`, `docs/job-logs.md`다.
- 각 작업 종류의 가짜 편집기 성공 순서와 단일 종료를 검증하고, 실행기 단계 실패 주입·잘못된 요청·읽기 불일치·기록 실패·복구 거절을 시험했다. 실제 네이버 조작은 0회다.

## B. 실제 밴드 한 번의 생성과 삭제

1. 켜짐·잠금 해제·앱 전면 상태를 읽기로 확인했다. 깨우기·잠금 해제·설정 변경·다른 앱 조작은 하지 않았다. 기존 앱 전용 밴드 프로필에서 대상과 잔여 시험 글 부재를 확인했다. 지정된 이전 상품과 앱 계획의 일치를 확인하고 선택 옵션은 모두 껐다.
2. 제출 직전 일회 허용 파일을 한 번 만들었다. 새 로그에 실제 생성 허용 1회와 성공 응답 1회가 있다. 사진 29장 입력 후 생성은 성공했으나, 상세 화면의 다른 DOM 구조를 기존 읽기 경로가 인식하지 못해 게시 작업은 `uncertain:BAND_POST_UNCONFIRMED`로 끝났다. 앱 성공·즉시 링크 저장·게시됨 화면을 입증하지 못했으므로 무복구 왕복 성공으로 세지 않는다. 재제출하지 않았다.
3. 실제 상세 화면을 읽어 본문 정규화 일치, 줄바꿈 158개, 사진 29장, 태그 2개와 링크 2개를 확인했다. 입력 전 사진 순서 검사는 통과했지만 **게시 후 전체 사진 순서의 자동 검증 성공 로그는 이번 실행에서 얻지 못했다.** 두 상세 구조를 지원하도록 수정하고 가짜 화면 회귀시험을 추가했다. 기기에 설치했으나 새 글로 재시험하지 않았다.
4. 원래 실행에는 주소가 저장되지 않아, 디버그 전용 연결 도구로 삭제 대상 링크만 원래 실패 기록에 연결했다. 원래 작업 로그의 단일 생성 성공 응답, 저장된 기록·상품 해시·제목·소유·본문·생성 시각이 모두 일치할 때만 허용한다. `failed/BAND_POST_UNCONFIRMED`는 유지하고 게시 성공으로 바꾸지 않는다. 릴리스에는 이 도구가 포함되지 않는다. 향후에는 독립 읽기로 확인한 생성 신원을 확인 필요 기록에 보존한다.
5. 등록 기록 → 글 삭제 → 삭제 확인을 **한 번** 눌렀다. 삭제 작업 로그의 `REQUEST_ALLOWED`, `RESPONSE_OK`, `FEED_ABSENT`, `URL_ABSENT`, `DELETED`, 기록 저장, terminal `succeeded`를 확인했다. 기록은 `stopped/BAND_POST_DELETED`, 주소 비움이며 화면은 ‘밴드 삭제함’이다. ‘이미 삭제됨’ 재조정 상태가 아니다. 이전 시험의 다른 기록은 바꾸지 않았다.

시각은 KST 기준 생성 응답 약 03:07, 앱 삭제 확인 03:22, 삭제 검증·기록 완료 03:23이다. 실제 게시·삭제 로그 발췌는 외부 `../runs/band-shots/wp20-sample-log.txt`에 110개 원문 JSON 줄로 보관했다. 반복 줄만 줄였고 게시의 확인 필요 종료와 삭제 성공 종료는 그대로다. `scripts/pull-logs.ps1`의 실제 추출도 성공했다. 추출 검사 대상인 11개 로그 62,140줄은 종료 줄이 각각 1개이고, 알려진 실제 식별정보·콘텐츠 후보 70개와의 대조에서 일치 0개다. 실제 계정·대상 정보를 포함해 후보를 늘렸으며 서비스의 일반 표시 문구는 식별정보로 세지 않았다.

## C. 실제 모습의 밴드 미리보기

전체 본문 뒤에 29장 사진을 원래 순서로 전체 폭 세로 배치한다. 태그와 URL은 각각 누를 수 있는 모양으로 표시한다. ‘목록에서는 이렇게 보입니다’ 표본은 앞 115자, 더보기, 사진 3칸과 나머지 수 겹침 표시다. 본문 문구와 입력 계획은 바꾸지 않았다. 디자인 참고·UI 시험을 갱신했다.

기기에서 텍스트와 줄바꿈 158개·사진 29장·태그 2개·링크 2개, 사진 전체 폭, 3칸과 `+26`을 확인했다. 앱 캡처는 외부 `i-preview-band-folded.png`, `i-preview-links-photos.png`, `i-preview-stacked-photos.png`다. 로그 화면·삭제 확인·삭제 후 피드·기록 캡처도 같은 폴더의 `i-*.png`로 보관했다.

## 확인 명령과 결과

- `pnpm install`: 성공, 잠금 파일 변경 없음.
- `pnpm typecheck`: 워크스페이스 `pnpm -r typecheck`와 Android bridge 타입 검사 성공.
- `pnpm test`: 최종 소스 고정 실행에서 **77개 파일, 932개 시험 통과, 실패 0, 건너뜀 0**. 03:38:30 KST 시작, 639.59초.
- `apps/android/gradlew.bat assembleDebug testDebugUnitTest`: 최종 실행 성공. Android 단위 시험 5개, 실패/건너뜀 0.
- `adb install -r`: 최종 검증 APK 설치와 자체 앱 시작 성공. 재시작 후 원래 기록이 앱 삭제 완료이며 주소가 비어 있음을 다시 확인했다.
- 허용 목록·손상 복구·용량 제한·정리 연결·릴리스 빌드 집중 시험 59개 성공. 최종 전체 시험과 별도로 실행했다.
- 후속 로그인·삭제 대기 종료·재시작 단계 복원과 UI 집중 시험 113개 성공.
- 최종 APK의 작업 로그 화면에서 과거 확인 필요 작업도 ‘게시와 게시 확인’으로 표시됨을 `i-final-job-logs.png`로 확인했다.

초기 설치에서 내장 Node의 ICU 없는 정규식 지원 차이로 시작 오류가 있었다. 엔진의 Unicode 속성 정규식을 제거하고 AST 호환성 시험을 추가했다. 이후 실제 앱 시작과 게시·삭제를 수행했다. 전체 시험 도중 소스를 수정했던 중간 실행과 후속 로그 보완 전 중단한 실행은 최종 통과로 쓰지 않는다.

## 미확인과 인계

- B의 ‘복구 없이 자체 게시 성공’ 조건은 미달이다. 새 실제 제출은 소유자의 새 승인 없이 하지 않는다. 다음 승인 시험에서는 두 상세 구조의 게시 후 전체 읽기, 즉시 기록 링크, 결과 화면과 사진 순서를 새 로그로 입증해야 한다.
- 실제 네이버 임시저장/발행/삭제는 하지 않았다. 네이버 경로의 근거는 네트워크를 가짜 편집기로 가로챈 자동 시험이다.
- 릴리스 번들의 오프라인 시작·로그 경로 포함·디버그 도구 제외, ZIP 내용과 Android 단위 시험은 확인했다. 서명된 릴리스 실기기 설치와 공유창에서 다른 앱으로 전달하는 시험은 하지 않았다. 외부 앱 입력 없이 앱 화면·PC 추출까지만 실기기로 확인했다.
- 실기기 로그의 수만 건 CDP 단계 기록 때문에 작업별 파일이 커질 수 있다. 내용은 개인정보 없이 유지하고 보관 한도로 제어한다. 단계 삭제로 원인을 다시 숨기지 않는다.
- 실행 코드 최종 커밋은 `61b5fb3`이며 해당 APK를 기기에서 확인했다. 뒤의 보고서 커밋은 실행 코드를 바꾸지 않는다. PR #23이 열려 있는 것을 확인했으므로 초안 PR의 대상 브랜치는 `codex/band-real-test`다.

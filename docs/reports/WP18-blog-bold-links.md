# WP18 — 블로그 굵기·링크 입력과 저장 검증

## 지금 제공하는 것

변환 계획의 문구와 `runs`를 그대로 블로그 입력 엔진에 전달한다. 각 run은 기존 `Surface.typeText`의 입력 속도로 쓰고, 굵기는 키보드 단축키와 툴바 상태를 대조한다. 링크는 문단 입력을 마친 뒤 키보드로 표시 글자를 선택하고 편집기의 주소 대화상자로 적용한다. 주소를 본문에 덧붙이는 대체 경로는 없다. 공통 surface 계약을 확장하지 않았다.

키보드 선택은 매 이동 후 실제 UTF-16 위치를 읽는다. 글자 수로 왼쪽 키 횟수를 추측하지 않으므로 한글 자모·variation selector·피부색 modifier·ZWJ 이모지 경계를 확인할 수 있다. DOM setter, HTML 주입, 스크립트 Selection 변경은 제품 코드에 없다. 합성 편집기만 자신의 입력·서식·대화상자 DOM을 관리한다.

저장 전, 저장 직후 같은 편집기, 새 편집기에서 정확한 임시글을 다시 연 뒤, 그리고 합성 발행 결과에서 텍스트·굵기·href·순서를 대조한다. semantic `strong`/`b`와 computed font-weight를 읽으며 동일 서식의 인접 run만 합친다. 공백·주소·숫자·이모지 문자를 삭제하거나 주소를 정규화해서 일치시키지 않는다. 기존 제목·사진 수와 순서·표·태그·가격/날짜·임시글 신원·자동저장 차단 검증도 유지한다.

확인된 입력 prefix와 서식이 같으면 이어 쓰고 이미 적용한 링크는 다시 적용하지 않는다. 부분 전송 결과나 내용이 불확실하면 기존 복구 동의를 요구한다. 주소 대화상자 안에서 멈춘 작업은 재개 시 아무 키도 보내지 않고 확인 필요로 멈춘다. 저장 후 발견한 서식 실패는 해당 실행에서 성공으로 바뀌거나 재저장·발행되지 않는다.

진행 화면은 실제 읽어서 확인한 run만 표시한다. 링크 대화상자에서 확인되기 전에는 계획의 링크를 미리 표시하지 않는다. 결과와 등록 기록은 `확인 필요`와 1부터 시작하는 문단 번호를 표시한다. 저장 뒤 실패한 작업은 기존 `draft_unverified` 경로로 처리하며 이유에는 고정 오류 종류와 문단 번호만 기록한다.

변환 문구, Band 입력/변환/일회 게시 게이트, API 및 서버/DB는 변경하지 않았다. 공용 채널 runner에는 블로그 서식 오류를 기존 기록 경로로 전달하는 분기만 추가했다. 요청대로 기존 `codex/blog-rich-text` 브랜치에서 작업했다.

## 합성 자료 검증표

아래는 실제 상품이나 계정 자료가 아닌 loopback 편집기에서 확인한 결과다. 첫 문단은 정규화한 run 5개, 굵은 run 2개, 링크 2개다. 굵은 두 run은 링크 경계 때문에 나뉘며 시각적으로는 연속된 굵기 범위 1개다.

| 항목 | 계획 | 입력 후 / 저장 전 | 저장 직후 | 새 편집기 재개방 |
| --- | --- | --- | --- | --- |
| 본문 문단 | 1 | 1 | 1 | 1 |
| 정규화 run | 5 | 5, 순서 일치 | 5, 순서 일치 | 5, 순서 일치 |
| 굵은 run / 연속 굵기 범위 | 2 / 1 | 2 / 1, 위치 일치 | 2 / 1, 위치 일치 | 2 / 1, 위치 일치 |
| 링크 표시 글자와 href | 2 | 2, 정확히 일치 | 2, 정확히 일치 | 2, 정확히 일치 |
| 공백·한글 자모·이모지 | 원문 그대로 | 문자 단위 일치 | 문자 단위 일치 | 문자 단위 일치 |

- 두 문단으로 나뉜 run, 부분 입력 후 재개, 이미 적용된 링크 뒤에서 재개, 불확실한 부분 전송 뒤 복구 동의를 확인했다.
- 굵기 상태 전환 실패, 대화상자 취소, 잘못된 링크, 선택 키가 작동하지 않는 상황, 주소칸 입력 도중 중단, 2번 문단 오류를 각각 저장 전에 차단했다.
- 저장 직후 및 새 편집기 재개방 때 굵기·링크가 유실된 경우를 각각 검출했고 재저장과 발행을 차단했다. 두 runner 모두 문단 번호를 기록했다.
- 합성 발행 결과의 굵기·링크가 유지되면 검증 완료, 유실되면 `확인 필요`이며 제출은 한 번뿐이다. 실제 서비스 발행 시험을 뜻하지 않는다.
- 합성 편집기는 공백 보존 CSS(`white-space: pre-wrap`)를 사용한다. 읽기 전용 평가가 거부하는 `Element.closest` 대신 읽기만 하는 조상 순회를 사용한다. 실제 서비스의 공백 표현·대화상자 구조가 다르면 엄격 비교에서 멈춘다.
- 기존 시험의 이모지 경계용 합성 문구를 바꾸는 한 곳은 `text`와 해당 `runs`를 함께 갱신했다. 기존 assertion, timeout, skip 조건은 완화하지 않았다.

## 실제 편집기와 Phase B

실제 편집기의 툴바·단축키·주소 대화상자는 아직 관측하지 않았다. 관련 선택자와 키는 `packages/sites/src/naver-blog/rich-text.ts`의 `WP18 REAL-EDITOR ADAPTER` 블록에 모았다. `button[data-name="bold"]`의 `aria-pressed`, Ctrl+B, `button[data-name="link"]`, `.se-popup-link`, 주소 input, 확인 버튼, 선택 후 재초점 동작은 합성 fixture에서만 검증된 계약이다. 실제 에디터에서 작동한다고 주장하지 않는다.

Phase A 완료 직후 읽기 전용 두 신호 점검을 수행했다. 첫 점검과 10분 13초 뒤의 두 번째 점검 모두 화면이 깨어 있지 않고 앱이 사용 가능한 전면 상태라는 증거도 없어 Phase B를 시작하지 않았다. 두 번의 점검에서 기기는 연결되어 있었으며 읽기 전용 system 상태만 확인했다.

| 점검 (KST, 2026-11-16) | 깨어 있음 | 앱 전면·초점·잠금 해제 증거 | Phase B 허용 |
| --- | --- | --- | --- |
| 1차 12:24:39 | 아니오 | 확인되지 않음 | 아니오 |
| 2차 12:34:52 | 아니오 | 확인되지 않음 | 아니오 |

Phase B는 실행하지 않았으며 pending으로 남긴다. 실제 임시저장은 0/3회, 실제 발행은 0회이며 Band는 조작하지 않았다. 깨우기·잠금 해제·앱 실행·로그인 페이지 열기·자격 증명 입력을 수행하지 않았다. debug APK는 빌드만 했고 휴대폰에는 설치하지 않았다. 저장소 밖 `../runs/wp18-shots/summary.txt`에 식별 정보 없는 짧은 상태를 남겼다. Phase B를 실행하지 않아 실기기 진행/결과 캡처는 없다. 이 작업으로 네이버 작성기나 저장되지 않은 글을 새로 만들지 않았다.

# WP18 — 블로그 굵기·링크 입력과 저장 검증

## 지금 제공하는 것

변환 계획의 문구와 `runs`를 그대로 블로그 입력 엔진에 전달한다. 각 run은 기존 `Surface.typeText`의 입력 속도로 쓰고, 굵기는 키보드 단축키와 툴바 상태를 대조한다. 링크는 문단 입력을 마친 뒤 키보드로 표시 글자를 선택하고 편집기의 주소 대화상자로 적용한다. 주소를 본문에 덧붙이는 대체 경로는 없다. 공통 surface 계약을 확장하지 않았다.

키보드 선택은 매 이동 후 실제 UTF-16 위치를 읽는다. 글자 수로 왼쪽 키 횟수를 추측하지 않으므로 한글 자모·variation selector·피부색 modifier·ZWJ 이모지 경계를 확인할 수 있다. DOM setter, HTML 주입, 스크립트 Selection 변경은 제품 코드에 없다. 합성 편집기만 자신의 입력·서식·대화상자 DOM을 관리한다.

저장 전, 저장 직후 같은 편집기, 새 편집기에서 정확한 임시글을 다시 연 뒤, 그리고 합성 발행 결과에서 텍스트·굵기·href·순서를 대조한다. semantic `strong`/`b`와 computed font-weight를 읽으며 동일 서식의 인접 run만 합친다. 공백·주소·숫자·이모지 문자를 삭제하거나 주소를 정규화해서 일치시키지 않는다. 기존 제목·사진 수와 순서·표·태그·가격/날짜·임시글 신원·자동저장 차단 검증도 유지한다.

확인된 입력 prefix와 서식이 같으면 이어 쓰고 이미 적용한 링크는 다시 적용하지 않는다. 부분 전송 결과나 내용이 불확실하면 기존 복구 동의를 요구한다. 주소 대화상자 안에서 멈춘 작업은 재개 시 아무 키도 보내지 않고 확인 필요로 멈춘다. 저장 후 발견한 서식 실패는 해당 실행에서 성공으로 바뀌거나 재저장·발행되지 않는다.

진행 화면은 실제 읽어서 확인한 run만 표시한다. 링크 대화상자에서 확인되기 전에는 계획의 링크를 미리 표시하지 않는다. 결과와 등록 기록은 `확인 필요`와 1부터 시작하는 문단 번호를 표시한다. 저장 뒤 실패한 작업은 기존 `draft_unverified` 경로로 처리하며 이유에는 고정 오류 종류와 문단 번호만 기록한다.

변환 문구, Band 입력/변환/일회 게시 게이트, API 및 서버/DB는 변경하지 않았다. 공용 채널 runner에는 블로그 서식 오류를 기존 기록 경로로 전달하는 분기만 추가했다. 요청대로 기존 `codex/blog-rich-text` 브랜치에서 작업했다.

## 합성 자료 검증표

아래는 실제 상품이나 계정 자료가 아닌 loopback 편집기에서 확인한 결과다. 첫 문단은 정규화한 run 5개, 굵은 run 2개, 링크 2개다. 굵은 두 run은 링크 경계 때문에 나뉘며 시각적으로는 연속된 굵기 범위 1개다.

| 항목 | 계획 | 입력 후 / 저장 전 | 저장 직후 | 새 편집기 재개방 |
| --- | --- | --- | --- | --- |
| 본문 문단 | 1 | 1 | 1 | 1 |
| 정규화 run | 5 | 5, 순서 일치 | 5, 순서 일치 | 5, 순서 일치 |
| 굵은 run / 연속 굵기 범위 | 2 / 1 | 2 / 1, 위치 일치 | 2 / 1, 위치 일치 | 2 / 1, 위치 일치 |
| 링크 표시 글자와 href | 2 | 2, 정확히 일치 | 2, 정확히 일치 | 2, 정확히 일치 |
| 공백·한글 자모·이모지 | 원문 그대로 | 문자 단위 일치 | 문자 단위 일치 | 문자 단위 일치 |

- 두 문단으로 나뉜 run, 부분 입력 후 재개, 이미 적용된 링크 뒤에서 재개, 불확실한 부분 전송 뒤 복구 동의를 확인했다.
- 굵기 상태 전환 실패, 대화상자 취소, 잘못된 링크, 선택 키가 작동하지 않는 상황, 주소칸 입력 도중 중단, 2번 문단 오류를 각각 저장 전에 차단했다.
- 저장 직후 및 새 편집기 재개방 때 굵기·링크가 유실된 경우를 각각 검출했고 재저장과 발행을 차단했다. 두 runner 모두 문단 번호를 기록했다.
- 합성 발행 결과의 굵기·링크가 유지되면 검증 완료, 유실되면 `확인 필요`이며 제출은 한 번뿐이다. 실제 서비스 발행 시험을 뜻하지 않는다.
- 합성 편집기는 공백 보존 CSS(`white-space: pre-wrap`)를 사용한다. 읽기 전용 평가가 거부하는 `Element.closest` 대신 읽기만 하는 조상 순회를 사용한다. 실제 서비스의 공백 표현·대화상자 구조가 다르면 엄격 비교에서 멈춘다.
- 기존 시험의 이모지 경계용 합성 문구를 바꾸는 한 곳은 `text`와 해당 `runs`를 함께 갱신했다. 기존 assertion, timeout, skip 조건은 완화하지 않았다.

## 실제 편집기와 Phase B

초기 Phase A에서는 실제 편집기의 툴바·단축키·주소 대화상자를 관측하지 않았다. 이후 관측과 adapter 변경은 이 보고서의 최신 재점검 절에 구분했다. 초기 관련 선택자와 키는 `packages/sites/src/naver-blog/rich-text.ts`의 `WP18 REAL-EDITOR ADAPTER` 블록에 모았다. `button[data-name="bold"]`의 `aria-pressed`, Ctrl+B, `button[data-name="link"]`, `.se-popup-link`, 주소 input, 확인 버튼, 선택 후 재초점 동작은 합성 fixture에서만 검증된 계약이다. 실제 에디터에서 작동한다고 주장하지 않는다.

Phase A 완료 직후 읽기 전용 두 신호 점검을 수행했다. 첫 점검과 10분 13초 뒤의 두 번째 점검 모두 화면이 깨어 있지 않고 앱이 사용 가능한 전면 상태라는 증거도 없어 Phase B를 시작하지 않았다. 두 번의 점검에서 기기는 연결되어 있었으며 읽기 전용 system 상태만 확인했다.

### 후속 기기 점검 (2026-11-16)

소유자가 화면을 켜고 잠금을 해제한 뒤 읽기 전용 두 신호로 화면 켜짐과 `kr.goltou.auto`의 foreground/focus를 확인했다. 같은 브랜치 APK를 다시 빌드하고, 매 기기 단계 전에 조건을 확인하며 `adb install -r`로 설치한 다음 이 앱만 실행했다. 화면 깨우기·잠금 해제·휴대폰 설정 변경은 하지 않았다.

앱이 골투 로그인 화면에 머물러 상품 목록으로 진행할 수 없었다. 로그인 필드의 값을 읽거나 입력하지 않았고 로그인 버튼을 누르지 않았다. 판매 중이며 굵기와 링크가 있는 상품을 확인할 수 없어 WP18 Phase B의 실제 편집기 열기·읽기 전용 probe·입력·임시저장을 시작하지 않았다. 실제 편집기 선택자와 단축키를 관측하지 못했으므로 `WP18 REAL-EDITOR ADAPTER`를 추측으로 변경하지 않았다.

## 첫 후속 점검 당시 남은 확인과 다음 작업

실제 편집기의 선택자·단축키·굵기 상태·주소 대화상자·재초점·공백 표현, 실제 저장 글의 run 일치, Android에서 진행/결과/기록 화면은 Phase B에서 확인해야 한다. APK 설치는 완료됐지만 수동 골투 로그인 필요 상태로 Phase B가 차단됐다. 로그인 후에도 화면 켜짐과 앱 전면 조건을 매 단계 확인하고 실제 편집기를 먼저 읽기 전용으로 관측해 표시된 adapter 블록만 사실에 맞게 조정해야 한다. 실제 임시저장 예산은 3회 모두 남아 있다. 초안 PR은 `main`을 대상으로 하며 PR #21이 병합될 때까지 WP17 커밋도 함께 표시된다.


## 수동 로그인 후 Phase B 재점검 (2026-11-16, 최신 결과)

소유자가 골투에 수동 로그인한 상태에서 시작했다. WP17 화면 점검을 마친 뒤 별도 숨김 네이버 WebView로 작성기를 열어 읽기만 했다. 상태 확인용 surface에서 작성기 탐색을 시도한 첫 경로는 navigation 정책에 막혀 중단했고 원래 상태 확인 페이지로 복원했다. 이후 로그인 관리 surface를 재사용하지 않는 debug 읽기 점검을 추가했다. 이 점검은 생성한 자신의 surface만 닫으며 기존 로그인 surface나 다른 실험 창을 닫지 않는다. 입력·사진 첨부·저장 기능은 호출하지 않는다.

읽기 점검에는 작성기 열기 전에 실제 발행·수정·자동저장·임시저장 endpoint 차단과 `nid.naver.com` 요청 차단을 설치한다. 따라서 로그인이 필요해져도 로그인 페이지를 새로 열지 않는다. 일반 설정에는 debug 빌드에서만 점검 열기/닫기 두 동작을 제공한다. 공통 surface 계약과 서버 코드는 바꾸지 않았다.

실제 작성기에서 기존 작성 중 글의 복구 안내를 발견했다. 이 실행은 네이버에 아무 글자도 입력하지 않았고 저장도 하지 않았으므로 기존 내용으로 취급했다. 소유자에게 직접 정리 여부를 물었고 응답 전에는 취소·확인을 누르거나 기존 글을 버리지 않았다. 읽기 점검 창만 닫았으며 마지막에는 작성기 target이 없음을 확인했다. 새 미저장 내용은 만들지 않았고, 기존 자동저장 내용은 그대로 남아 있을 수 있다. 이 상태에서 Phase B 저장 시험은 보류다.

### 골투 로그인 화면으로 돌아간 원인 조사 (읽기 전용)

`../goltou-hybrid`의 규칙을 읽고 로컬 `/auto` 구현과 앱의 복원 경로만 조사했다. 서버·DB에는 연결하지 않았으며 저장된 토큰·암호·쿠키 값을 읽거나 비교하지 않았다. 서버 코드는 변경하지 않았다.

- 세션은 로그인 시 **30일**로 발급되고, 인증에 성공한 요청마다 `expires_at`을 현재 UTC 시각 + 30일로 연장한다. 고정 30일 만료가 아니라 마지막 인증 성공 이후 30일의 유휴 만료다. `last_used_at`도 함께 갱신된다.
- 만료·이미 철회된 세션·해당 session row 부재·형식이 잘못된 bearer는 `auth`다. 현재 회원 삭제/비활성/등급 하락/정지 조건은 `forbidden`이다. `/auto/logout`은 현재 세션의 `revoked_at`을 설정한다. 새 로그인에서 다른 세션을 자동 철회하는 코드는 없다.
- 앱 `initialize()`는 저장값이 있으면 `/auto/me`를 단 한 번 호출한다. 이 복원이 네트워크/timeout/server 오류로 실패해도 초기 사용자 상태는 null이고 UI는 로그인 화면에 남는다. 실패한 초기화 Promise도 캐시되므로 같은 프로세스에서 자동 재시도하지 않는다. 이때 저장된 세션이 남아 있어도 사용자에게는 로그아웃처럼 보일 수 있다.
- 앱의 API wrapper는 `auth`뿐 아니라 **모든 `forbidden`** 응답에서도 저장 세션을 지운다. 계정 상태 거절 외에 기록 소유권·권한 거절도 이 경로에 들어갈 수 있다. 일반 연결 오류는 저장 세션을 지우지 않는다.
- native 저장소에는 별도의 시간 만료나 재부팅 시 삭제 규칙이 없다. 복호화 예외가 생기면 암호화 저장소를 비우는 경로는 있다. 이번 추가 설치 두 번에서는 수동 로그인한 세션이 모두 복원됐다.

**가장 의심되는 경로는 앱 시작 때 `/auto/me` 복원 실패로 로그인 화면에 남은 경우이며, `auth/forbidden`에 따른 자동 초기화도 가능하다.** 단기간 사용 중이었다면 30일 유휴 만료는 설명력이 낮다. 당시 오류 종류나 서버 session metadata를 확인하지 않았으므로 실제 만료·철회·권한 거절·일시적 복원 실패 중 하나로 확정하지 않는다. 토큰 저장 코드가 그대로이고 재부팅이 없었다는 사실만으로 세션 유효성이나 복원 성공을 보장할 수 없다. 이 조사는 읽기 전용이므로 복원·세션 처리 코드는 수정하지 않았다.

## 미리보기 사진·기록 후속 수정 (2026-11-16, 최신)

### 사진 실패의 확인된 원인과 수정

이전 contact-2/contact-5와 같은 두 상품을 검색으로 다시 골랐다. 23장 상품은 첫 사진 1장이 골투 HTTPS 호스트, 나머지 22장이 `coresos-phinf.pstatic.net`의 HTTPS 원본이었다. 수정 전 기기에서는 첫 사진만 정상이고 나머지는 img 요청 자체가 만들어지지 않았다. `ProductPhoto.photoSource`가 공용 `goltouPhotoUrl`의 골투 전용 호스트 제한으로 거절했다. UI CSP와 Android `UiPhotoPolicy`에도 같은 제한이 있었다. UI/CSP를 수정한 뒤 첫 기기 재시험에서 네이티브 필터의 추가 차단을 확인하고 그 필터도 고쳤다.

실제 원본 23개를 credentials/referrer 없이 GET한 결과 모두 redirect 없는 HTTP 200 `image/jpeg`였다. 각 파일은 3,290~276,235 bytes였고, 수정한 기기 WebView에서 23개 모두 디코딩됐다. 이 상품의 실패는 mixed content, hotlink/referrer 요구, redirect, 파일 크기/디코더 한도, 동시 요청/timeout 또는 proxy 때문이 아니었다. 별도 사진 proxy는 사용하지 않는다.

추가 허용은 관측한 CDN의 **정확한 HTTPS 호스트 하나**뿐이다. 공용 URL 정책과 CSP의 호스트 목록을 함께 관리하고, Android subresource 필터에도 반영했다. 원본 URL·순서·변환 내용은 그대로이며 credentials, 임의 호스트, HTTP, 비표준 포트, 위장 접미/하위 호스트는 계속 거절한다. 네이티브 UI의 외부 페이지 탐색 차단도 유지한다.

Android 게시 준비 downloader도 같은 공용 정책을 쓰므로 수정 전에는 이 원본을 `PHOTO_HOST_NOT_ALLOWED`로 거절했을 것이다. 새 bundle의 실제 `downloadPhotos` 함수로 이 상품의 API 사진 목록을 download-only 검사했다. 23/23개의 비어 있지 않은 원본, 순서 일치, 총 3,815,545 bytes를 확인했다. 이 검사는 메모리 저장소만 사용했고 작업 시작·편집기 열기·첨부·저장·발행은 호출하지 않았다.

이번 23개 중 실제로 가져오지 못하는 사진은 없다. 앞으로 API 목록에 없는 URL이나 허용하지 않은 호스트는 내려받기 전에 거절한다. 비정상 HTTP 응답(redirect 포함), 30초 timeout, 빈 파일은 전체 준비를 실패시키고 batch를 정리한다. 사진을 조용히 빼고 게시를 진행하지 않는다. 실서비스 업로드까지 확인했다는 뜻은 아니다.

### 실제 편집기 원인과 수정

- 실제 문단은 `contenteditable`이 아니며 포커스는 `input_buffer`와 숫자로 이루어진 iframe의 editable body에 있다. 본문 포커스를 이 정확한 입력 수신기와 함께 확인한다. 빈 문단 안내 글자는 본문 run이나 커서 offset에 포함하지 않는다.
- `.se-native-selection-hidden`인 편집기는 기본 DOM Selection을 문단 시작에 접어 둔다. 입력 후와 실제 Ctrl+End/선택 키 뒤에도 0으로 남았다. 실제 선택은 별도로 문단·unit·component·텍스트 노드 ID와 offset을 갖는다.
- 편집기의 `getSelection()`은 observable getter를 거쳐 `throwOnSideEffect`에서 거절됐다. 이 제한을 풀지 않았다. 현재 선택 저장소의 plain backing endpoint 값만 읽고, 각 ID가 실제 본문 DOM의 올바른 조상/문단/`__se-node`를 가리키는지와 offset 범위를 모두 대조한다. 알 수 없는 구조, 없는 노드, 다른 문단 또는 잘못된 offset이면 중단한다. 편집기 메서드 호출, DOM setter와 Selection 변경은 없다.
- 이모지 입력·줄바꿈·서식 전환은 빈 `__se-node` span을 남긴다. 문단 전체가 비어 있지 않아도 이 노드가 실제 커서일 수 있다. 해당 노드 안의 실제 텍스트 자식들을 순서대로 읽어 UTF-16 위치를 환산하며 임의로 본문 끝이라고 가정하지 않는다.
- 실제 Ctrl+B는 툴바의 `se-is-selected`를 꺼짐→켜짐→꺼짐으로 바꿨다. 입력된 본문은 실제 `b` 요소로 굵게 표시됐다.
- 실제 작성 중 링크는 `span.se-link.__se-node[data-href]`다. 이 정확한 renderer와 `a[href]`를 모두 읽으며 표시 글자, raw 주소와 순서를 바꾸지 않고 대조한다. 임의의 `data-href`는 링크로 인정하지 않는다.
- 링크 주소 계층 열기, 주소 입력, 적용, 입력 iframe으로의 재초점은 실제 작동했다. 적용 뒤 선택 범위가 남고 Ctrl+End가 이를 접거나 문단 끝으로 옮기지 않았다. 오른쪽 방향키는 선택 끝으로 접고 이후 실제 offset을 앞으로 옮겼다. 입력기는 매 키 뒤 이동량과 같은 문단 여부를 확인해 정확한 문단 끝에 도달한 뒤에만 진행한다.

이 발견 과정에서 저장 전 중단된 실행들은 완료로 바꾸지 않았다. 원문·계획·사진·가격/날짜·태그 비교와 저장 후 재개방 검증을 완화하지 않았다. 새 브라우저 회귀 시험은 입력 iframe/가상 선택/없는 노드/한글·이모지/빈 텍스트 노드/중첩 서식을 다룬다. 기존 저장·재개방 성공 시험을 Ctrl+End가 선택을 유지하는 fixture에도 그대로 적용했고, 방향키로 선택을 접지 못하면 저장·발행 0회로 중단하는 시험을 추가했다.

### 현재 실제 결과와 차단 사항

**저장된 네이버 임시글의 서식 검증은 아직 완료하지 못했다. 실제 임시저장 0/3회, 공개·비공개 발행 0회다.** 총 8개 입력 실행이 모두 저장 전에 멈췄다. 마지막 실행은 본문 전체를 입력하고 실제 문서의 텍스트·굵기·raw href·순서 비교에서 차이가 없었지만 태그 확인에서 멈췄다. 이 결과를 저장·재개방 성공으로 기록하지 않았다.

| 항목 | 계획 | 입력된 실제 문서 | 저장 후 재개방 |
| --- | --- | --- | --- |
| 비교 문단(표 행 포함) | 99 | 99, 정확한 문구·순서 일치 | 미검증 |
| 연속 굵기 범위 / 굵은 run | 1 / 1 | 1 / 1, 위치 일치 | 미검증 |
| 링크 표시 글자·raw href·순서 | 2 | 2, 정확히 일치 | 미검증 |
| 사진 | 29 | 29장 입력됨 | 최종 수·순서 검증 미실행 |
| 표 행 | 3 | 문단 비교에서 3행 원문 일치 | 최종 검증 미실행 |
| 태그 | 1 | **2, 불일치로 중단** | 미검증 |

태그 원인은 실제 계층과 로드된 static 코드에서 확인했다. 네이버는 발행 설정 계층을 열 때 편집기 본문의 해시태그를 추출해 명시적으로 입력한 태그와 합친다. 이 상품의 원래 링크 표시 글자에 들어 있던 해시태그가 추가돼 계획 1개와 실제 2개가 됐다. 따라서 기존의 엄격한 태그 확인이 `OBSERVATION_TIMEOUT`으로 중단됐다. 원문 글자를 빼거나 태그를 삭제하지 않았고, 추가 태그를 무시하거나 관측값에 맞춰 계획을 고치지도 않았다. 이 자동 합침의 제품 정책은 별도 작업으로 남긴다. 현재 작업에서는 자동 태그 충돌 없이 굵기와 링크를 함께 가진 다른 판매 상품을 조회하던 중 아래 기기 조건이 해제됐다.

마지막 전체 입력 작업의 실제 경과 시간은 **11분 9초**(복구 동의 대기 3.56초 포함)이며, 저장·재개방 시간은 존재하지 않는다. 저장되지 않은 편집기를 앱의 그만두기로 닫았으나 서버 자동저장 잔여 내용의 재점검·정리는 아직 못 했다. 재개 시 앱에서 새 임시저장 작업을 시작하고 소유자가 승인한 복구 sheet 경로로만 정리해야 한다. 저장된 임시글·게시글 삭제는 하지 않았다.

휴대폰의 화면 켜짐·잠금 해제는 유지됐지만 앱 전면 상태가 두 번 해제됐다. 자신의 앱만 다시 전면으로 연 뒤에도 같은 조건이 반복돼 기기 입력을 중단하고 소유자에게 전면 유지를 요청했다. 이후 읽기 전용 재점검도 전면·초점 없음이었다. 화면 깨우기·잠금 해제·설정 변경은 하지 않았다. Band 입력·게시·삭제 및 기기 일회 게시 허용 파일 생성도 0회다.

`b-live-bold.png`는 굵기가 보이는 실제 입력 진행 화면이며 `b-try8-result.png`는 중단 결과다. 실행별 진행·결과, 문서 run 판독과 태그 계층 증거는 모두 저장소 밖 `../runs/wp18-shots/`에만 있다. 저장된 임시글이 없으므로 저장 글 근접 사진과 성공 기록 행은 아직 없다. `summary.txt`는 현재 상태를 적은 33줄 plain text다.

# WP21 밴드 게시 자체 확정

생성은 성공했지만 상세 본문을 찾지 못하는 선택자를 반복 읽고, 링크 저장도 전체 확인 뒤로 미뤄 30초 후 확인 필요로 끝난 것이 확인된 원인이다.

브랜치는 지시대로 `codex/job-logs`를 계속 사용한다. PR #24는 초안으로 유지한다. 이번 작업에서 실제 밴드 생성·삭제, 실기기의 게시 허용 파일 생성, 네이버 조작은 모두 하지 않았다. 휴대전화는 APK 덮어쓰기 설치만 한다. 실제 식별정보와 원시 증거는 저장소 밖 `../runs/`에 둔다.

## 기존 증거와 코드의 대조

- 외부 `g-create-result.json`은 23:39:59 KST의 HTTP 200, `result_code=1`, `postKey=null`을 기록한다. 이 파일을 만든 관찰 코드는 `result_data.post_key`만 추출했다. **생성 응답의 나머지 필드 이름이나 원문은 보관하지 않았다.** `g-read-response-shape.json`의 `post_no`, `web_url`은 후속 피드 응답 필드이며 생성 응답 필드라는 증거가 아니다. 실제 생성 응답이 다른 ID 필드를 줬다고 단정하지 않는다.
- 외부 WP20 원본 게시 JSONL에는 생성 허용 1회, 03:07:34 KST의 성공 응답 1회, `www.band.us` 상세 이동, 상세 읽기 95회, `OBSERVATION_TIMEOUT` 30,031ms, 최종 `uncertain/BAND_POST_UNCONFIRMED`가 있다. 상세 읽기는 예외 없이 `null`을 반환해서 각 호출 자체는 `ok`로 찍혔다. `i-job-private.json`도 동일한 확인 필요 상태와 즉시 링크 부재를 보인다. 성공 응답이나 닫힌 편집기만으로 작업 성공이 되지 않는 구조였다.
- `g-detail-dom-proof.json`의 실제 확장 상세는 `.postsDetailArea ._contentListRegion` 아래 `.postTextBox > .postText._postTxt`다. 기존 본문 선택자는 이를 포함하지 않았다. WP20 상세 증거에는 `.postWrap.-postDetailPage .cContentsCard .postBody .dPostTextView > .postText`도 있다. 고정된 한 상세 구조나 편집기의 `.postView` 가정으로는 두 화면을 모두 확인할 수 없다.
- 실제 전체 읽기 증거 `i-actual-full-proof.json`은 본문 정규화 일치, 줄바꿈 158개, 사진 29장, 태그 2개, 링크 2개다. 이는 해당 글의 존재와 내용을 입증하며, 당시 앱 작업의 성공 종료나 전체 사진 순서 검증 성공을 입증하지는 않는다.
- 기존 `detectPublished`는 성공 응답을 받은 뒤에도 별도 피드 이벤트의 후보가 먼저 있어야 상세로 넘어갔다. 응답은 `post_key`만 읽었고, 신원을 얻어도 실행기 안에만 보관했다. runner는 `publish()`가 반환하거나 마지막 실패 처리를 할 때 주소를 붙였으며, AppCore 기록기도 `running` 상태의 밴드 주소를 버렸다. 피드·응답 도착 순서와 상세 DOM 실패가 링크 저장까지 막는 구조였다.

## 차단기가 원인인지

- 원본 03시 게시 작업에서 생성 허용 뒤 차단된 네트워크 줄은 `POST/[other]` 10개다. 사유는 `ORIGIN_BLOCKED` 7개, `ROUTE_BLOCKED` 3개이며, 필요한 API·BAPI 호스트의 요청 차단은 없다. 상세 문서 GET은 허용됐다. `INSPECTOR_DENIED` 줄은 게시 전에도 있고 별도 삭제 작업에도 있지만, 삭제 후 API GET 차단을 게시 확인 실패의 원인으로 섞지 않았다.
- `g-request-shapes.jsonl`에서 실제 수집 요청 `nlog.band.us/event`를 확인했다. `[other]`로 가려진 모든 요청을 수집 요청이라고 추정하지 않는다. 알려진 수집 경로만 `blocked_expected`로 분류하며, 일반 미지 호스트나 생성·상세 읽기 차단은 계속 실패로 남긴다.
- 기존 기록 복구가 쓰는 피드 GET, 모바일 세션 부트스트랩 GET, 정확한 두 GET으로 구성된 상세 BAPI POST는 기존 읽기 정책으로 통과한다. 전체 작업 재생에서도 상세 BAPI가 허용돼야 본문이 나타나도록 구성했다. 쓰기 허용 범위를 넓히지 않았다.

## 수정

1. 허용된 한 생성 응답의 성공과 명시적 식별 필드를 읽는다. `post_key`, `post_no`, `post.post_no`를 지원하되 값이 충돌하거나 대상이 다르면 ID를 추정하지 않는다. 숫자 정밀도가 손실된 ID도 거절한다. 이 별칭 지원은 합성 응답으로 검증했으며 실서비스의 다른 생성 필드가 입증됐다는 뜻은 아니다.
2. 응답 식별자를 관찰한 즉시 같은 작업의 기록 저장을 시작한다. 상세 열기 전에 저장 완료를 기다린다. 확인 중 `running` 상태에도 주소를 보존하며, 내용 검증 실패 뒤에도 지우지 않는다. 응답 콜백에서는 요청을 붙잡은 채 비동기 기록 완료를 기다리지 않는다.
3. ID가 없거나 응답 관찰이 누락되면 `openRecordedBandFeed`와 `parseRecordedBandFeed`의 기존 복구 읽기 경로를 같은 작업에서 사용한다. 소유 작성자(`author.me`), 제출 전 5초부터 응답 시각 후 5초까지의 고정 창, 정규화 본문 해시와 본문 전체 동등성, 업로드된 사진 경로의 순서 있는 접두부가 모두 맞는 후보 하나만 허용한다. 피드의 사진 접두부를 전체 사진 검증으로 세지 않는다. 늦은 피드는 제한 시간 안에서 다시 읽는다.
4. 두 실제 상세 구조를 다시 열고 본문, 줄바꿈, 사진 전체 수·순서, 태그 내용, 링크 실제 목적지를 비교한다. 전부 맞아야 `published`와 작업 로그 `succeeded`로 끝난다. 밴드만 선택한 성공 화면은 ‘게시했습니다’다.
5. 읽기 전용 CDP의 `throwOnSideEffect`에서 `Element.closest()`가 `Possible side-effect in debug-evaluate`로 거절되는 별도 잠복 문제도 오프라인에서 재현했다. 이를 범위가 한정된 선택자와 부모 읽기로 대체했다. 기존 상세 회귀시험의 일반 `page.evaluate`를 실제와 같은 읽기 전용 CDP 검사로 바꿨다. 당시 원본 로그의 95회 `null`과 이 별도 잠복 문제는 구분한다.
6. 신원 없음·읽기 실패·후보 중복은 각각 `BAND_POST_UNCONFIRMED:IDENTITY_NOT_FOUND`, `:IDENTITY_READ_FAILED`, `:IDENTITY_AMBIGUOUS`와 한국어 안내로 확인 필요를 남긴다. 신원이 확정된 글의 내용 불일치·상세 읽기 불가는 별도의 검증 실패이며 주소를 보존한다. 명시적 생성 거절도 별도 실패다. 어느 경우에도 같은 작업을 재제출하지 않는다.
7. 응답, 피드 후보·재읽기, 링크 기록, 상세 검증을 WP20 로그의 독립 단계로 기록한다. 알려진 수집 요청의 차단은 `blocked_expected`이며 실제 실패 단계를 덮지 않는다. 네트워크 차단 한 건당 한 번만 집계해 색인에 보존하고 재시작 때 복원한다. 값·본문·사진 경로를 로그에 넣지 않는다.

## 검증과 한계

- `pnpm install`: 성공, 잠금 파일 변경 없음.
- `pnpm -r typecheck`: 모든 워크스페이스 성공. `pnpm exec tsc -p apps/android/bridge/tsconfig.json`도 성공.
- `pnpm test`: 최종 소스에서 **80개 파일, 957개 시험 통과, 실패 0, 건너뜀 0**. 04:43:12 KST 시작, 741.67초. 새 전체 작업 재생 6개도 이 실행에서 전부 통과했다.
- `apps/android/gradlew.bat assembleDebug testDebugUnitTest --console=plain`: 최종 실행 성공. 기존 Android 단위 시험 5개는 유효한 캐시를 재사용했으며 XML의 실패·건너뜀은 0개다.
- `adb install -r apps/android/app/build/outputs/apk/debug/app-debug.apk`: `Success`. 설치 뒤 앱을 시작하지 않았다. 휴대전화 깨우기·잠금 해제·다른 앱 조작·추가 화면 검사는 하지 않았다.
- 실제와 같은 읽기 전용 CDP에서 158개 줄바꿈·29장 전체 사진·태그·링크 목적지를 읽는 집중 시험을 통과했다. 사진 순서, 태그 내용, 링크 목적지를 바꾼 불일치 사례도 거절했다. AppCore의 실제 기록 경로로 진행 중 주소 저장과 이후 실패 때의 주소 보존도 시험했다.
- 최종 변경 파일 22개를 외부 실제 증거에서 추출한 식별정보·본문 후보 13개와 대조해 일치 0개였다. 이 후보 대조를 모든 종류의 개인정보 탐지 보증으로 과장하지 않는다. 원시 증거·응답·사진 경로는 커밋하지 않았다.

실행 코드 커밋은 `624209c`다. 이 커밋에서 최종 APK를 빌드하고 덮어쓰기 설치했다. 뒤의 보고서 커밋은 실행 코드를 바꾸지 않는다. `../runs/band-shots/wp21-summary.txt`는 30줄 이내의 요약이며 명령별 출력도 같은 외부 폴더에 보관했다.

중간 전체 실행에서는 공용 피드 읽기의 쿼리 검사를 기존 기록 읽기에도 적용한 호환성 회귀와, 새 합성 상세 HTML의 UTF-8 선언 누락을 발견했다. 쿼리 검사는 신원 미확정 탐색에만 적용하도록 제한했고, 기존 기록 읽기는 응답 본문의 정확한 신원을 검사하는 계약을 유지했다. 관련 읽기·복구·가짜 삭제 37개 시험이 다시 통과했다. 합성 상세의 문자 인코딩도 바로잡았다. 실패한 중간 실행과 필터를 건 부분 시험은 최종 전체 통과로 세지 않는다.

회귀시험은 명시적 응답 ID, ID 없는 성공 응답과 작업 내 피드 읽기, 지연 피드, 생성 거절, 내용 불일치, 양쪽 신원 확인 실패를 포함한다. 응답과 피드의 도착 순서를 바꾼 시험, 상세 응답을 보류한 동안 링크가 먼저 기록되는 시험, 실제 AppCore 기록 경로의 진행 중 주소 저장 시험을 포함한다. 전체 작업 재생은 요청을 전부 가로챈 합성 페이지이며 외부 전달은 0건이다. 합성 응답과 실제 DOM 구조의 재생은 실서비스의 새 성공을 대신하지 않는다.

다음 한 번의 별도 승인된 실제 게시에서는 새 허용·생성 요청 각 1회, 응답 식별 경로 또는 작업 내 피드 신원 확정, 복구 도구 없는 즉시 링크 저장, 본문과 158개 줄바꿈·29장 전체 순서·태그·실제 링크 검증, 단일 `succeeded` 종료, ‘게시했습니다’ 화면과 등록 기록 링크를 모두 보여야 한다. 생성 응답에 ID가 있다면 어떤 허용 필드였는지도 값 없이 확인해야 한다. 이번에는 실제 제출로 이를 확인하지 않았다.

## 블로그 코드·fixture 검토만 한 결과

블로그 `BlogExecution.publish`도 30초 안에 결과 화면 또는 같은 출처 프레임이 실제 글 주소를 갖고 `.se-documentTitle .se-text-paragraph` 제목을 정확히 하나 노출한다고 가정한다. 응답 ID가 있어도 이 제목 화면을 못 읽으면 확인이 끝나지 않는다. 이후 `verifyPublished`는 해당 URL의 본문·사진 토큰, 제한된 PageDown으로 지연 사진 읽기, 비공개일 때 정해진 표시 선택자까지 필요하다. 응답 파서가 아는 `logNo`/URL과 실제 응답 형태, 새 창·다른 결과 경로·제목 DOM·지연 렌더링이 달라지는 위험은 합성 fixture만으로 해소되지 않는다. 실제 네이버는 실행하지 않았고 동작을 변경하지 않았다.

# WP31 릴리스 연결 확인 복구

2026-11-17. PR #30 병합 main `5726f4b`에서 `codex/release-connect-fix`를 만들었다.
[지시서](../wp/WP31-release-connect.md)의 범위다. 기기 앱 삭제/초기화/debug 설치 금지,
네이버 저장·발행·밴드 게시·삭제 예산은 모두 0이다.

## 원인과 수정

기기 켜짐·잠금 해제·정식 앱 전면을 읽기만 하여 확인하고 1.0.0 (3)의 오류를 재현했다.
승인된 adb WebView 채널에서 비밀 없는 문서 이동과 오류만 관찰했다.

1. 밴드 확인은 `band.us/` → `www.band.us/` HTTP 200까지 성공했다.
2. 페이지가 scriptInitiated로 `www.band.us/about/kr/intro`로 이동하려 했다.
3. 공통 로그인 navigation policy의 숨김 landing 목록에 이 주소가 없어 Kotlin
   `shouldOverrideUrlLoading`이 이동을 거부했다. 관찰한 문서 오류는 `net::ERR_ABORTED`였고,
   앱은 로딩 시간 초과를 일반 인터넷 오류로 표시했다.

R8/리소스 축소는 이미 false였다. DEBUG와 독립된 WebView 제어 채널은 WebView/Node 생성 전에
활성화됐고 실제 CDP 접속도 됐다. release/debug은 같은 native 프로필·network security·이동 정책을
쓴다. 따라서 release 전용 최적화 결함이 아니라 **새 비로그인 프로필에서만 지나가는 경로 누락**이다.
이전 debug 세션이 인증 상태였기 때문에 드러나지 않았다는 설명은 정황에 따른 추정이며,
삭제된 이전 debug 앱의 private 데이터는 읽지 않았다.

- 관찰한 정확한 `/about/kr/intro`만 숨김 landing에 추가했다. 로그인 화면으로 표시하지 않으며
  편집기·피드·다른 소개 경로 차단을 유지한다. 계정별 naver/band 프로필은 바꾸지 않는다.
- release에도 `GOLTOU-CONNECT` native logcat을 남긴다. 생성/이동 시작·완료/정책 차단/
  WebView 네트워크·HTTP 오류/표시·숨김/renderer 종료와 서비스·허용 host/path·숫자 코드만 쓴다.
  query·fragment·raw 예외·페이지 내용·계정·쿠키·인증 헤더는 출력하지 않는다.
- 코어의 연결 확인(check) 로그는 실제 실패 사유를 terminal까지 보존한다. 비로그인 판독은 정상 완료로 기록하고
  `LOGIN_REQUIRED`를 남긴다. 모든 실패를 인터넷 오류라고 단정하는 배너를 일반 재확인 안내로 바꿨다.
  기존 로그 내보내기도 유지한다.
- 버전을 1.0.0 (4)로 올렸다. 서명 키와 설정은 저장소 밖 기존 파일을 사용한다.

네이버 Blog 로그인 버튼은 수정 전 1.0.0 (3)에서도 실제 네이버의 빈 로그인 폼이 표시됐다.
아이디·비밀번호·앱 열기·서비스 로그인 버튼은 누르지 않고 앱의 돌아가기/취소로 복귀했다.
소유자의 이전 일시적 Blog 오류는 같은 원인이라고 단정하지 않는다.

## 검증

- 새 release 컴파일/Chromium 회귀시험: 새 Band 프로필의 홈페이지 → 소개 페이지 script 이동을
  재현하고 native와 같은 allowed/landing 경계를 적용한다. `expired` 판독·밴드 로그인 화면·
  네이버 로그인 화면을 검증한다. DNS를 차단하고 모든 서비스 응답은 로컬 대역으로 공급한다.
- TypeScript 단위시험: 소개 경로는 landing, 하위·다른 경로는 차단; 실패 사유 보존과 비로그인 완료.
- Android debug/release 단위시험: 로그 query·식별자 제거와 범위 밖 코드 제거, 숨김 landing 경계.

실행 코드/빌드/설치 커밋은 **`2ab2b18e87d74862b6ae8102a760611f64f79d08`**이다.
이후 커밋은 이 보고서만 보완하며 실행 코드는 바꾸지 않는다. 전체 suite는 설치 게이트에서 **1회** 실행했다.

초기 Android 검사 명령은 작업 디렉터리에 맞지 않는 상대 서명 경로 때문에 실패했고 경로를 고쳐 통과했다.
새 브라우저 fixture도 초기 302 후속 요청의 대역 적용 누락을 발견해 script 이동과 DNS 차단으로 고친 뒤
통과했다. 이 초기 실패들은 위 최종 통과 결과로 세지 않는다.

원래 main 정책과 수정 정책을 별도로 컴파일해 같은 주소를 판정한 증거도 외부에 남겼다.
소개 페이지는 `blocked` → `landing`, 편집기 주소는 양쪽 모두 `blocked`다.

## 실기기 결과

- 설치 버전은 **1.0.0 (4)**, DEBUGGABLE 플래그 없음. 최초 설치 시각은 업데이트 전후 동일했다.
  같은 서명의 `install -r` 1회만 실행했다. 앱 삭제·데이터 초기화·debug 설치는 0회다.
- 부팅 후 골투 로그인 화면을 거치지 않고 기존 로그인 상태의 상품 화면이 열렸다.
  프로세스를 재시작한 뒤에도 같았다. 골투 세션·쿠키·저장소·인증 헤더는 읽지 않았다.
- 계정 연결의 밴드는 **로그인 필요 + 로그인 + 다시 확인**으로 표시됐다. 다시 확인도 같은 상태로
  끝났고 기존 인터넷 오류 배너가 없어졌다. native release logcat에서
  `CONNECTION_STARTED`와 `CONNECTION_FINISHED`, `service=band`, `host=www.band.us`,
  `path=/about/kr/intro`를 확인했다.
- Blog 로그인 버튼은 실제 네이버의 빈 로그인 폼을 표시했다.
  `CONNECTION_FINISHED service=naver host=nid.naver.com path=/nidlogin.login`와
  `CONNECTION_SHOWN service=naver`가 남았다. 로그인 정보를 입력하거나 서비스의 로그인/앱 열기
  버튼을 누르지 않고 앱의 돌아가기/취소로 계정 연결 화면에 복귀했다.
- 업데이트 직후 이미 자동으로 복원된 Activity에 확인용 `am start`를 다시 보내 화면이 두 개가 됐다.
  그 상태의 첫 Blog 표시 확인은 `NATIVE_OP_FAILED`와 빈 wrapper로 실패했다. 데이터 삭제 없이
  `am force-stop` 후 앱을 한 번만 실행해 Activity 하나를 확인했고, 위 Blog 폼 표시가 통과했다.
  중복 Activity와 단일 Node/native 연결의 수명 관리는 후속 검토 항목이다. 소유자가 처음 보았던
  Blog 오류와 같은 원인이라고 단정하지 않는다.

스크린샷은 저장소 밖 `../runs/blog-shots/r3-connect-fixed.png`, `r3-blog-login-page.png`다.
후자는 빈 로그인 폼 부분만 잘랐으며 식별자와 상품 내용을 담지 않았다. 최종 앱은 계정 연결 화면이다.
외부 증거는 `wp31-release-gate.log`, `wp31-connect-logcat.txt`, `wp31-diagnosis.txt`,

## 확인하지 않은 것과 인계

소유자는 이제 앱의 계정 연결에서 네이버와 밴드에 직접 로그인하면 된다.
실제 로그인 완료·인증 후 계정 판독·임시저장·발행·밴드 게시·삭제는 이번에 시험하지 않았다.
네이버 저장·발행·밴드 게시·서비스 삭제는 각각 **0회**다. 운영 API/DB에 직접 접속하지 않았다.
실기기 로그 ZIP 공유 UI를 실행하지 않았으며, 새 진단은 release logcat과 PC 내보내기 로그 시험으로
확인했다. 게시 동작의 성공을 이번 연결 수정 결과로 추정하지 않는다.

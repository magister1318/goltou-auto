## 원인과 수정

1. 설정이 골투 로그인 뒤에만 있어 로그인 없는 진단을 할 수 없었다. 네이티브 디버그 플래그가 허용할 때만 로그인 화면에 설정 진입을 노출했다. 로그인 전 설정에는 진단과 실험만 표시한다. 디버그 기능을 제공하지 않는 코어는 실험 메시지를 거부한다.
2. Activity 재생성 때 UI·Surface·소켓을 함께 닫던 코드를 분리했다. 같은 ViewModel이 WebView와 CoreLink를 유지하고 MutableContextWrapper를 새 Activity로 연결한다. 영구 종료 때만 정리한다.
3. 숨김 데스크톱 크기와 실제 전면 크기의 충돌을 보이기/숨기기 전환에서 처리했다. 네이티브 뒤로/닫기에도 숨김 크기 복원을 알리는 이벤트를 연결했다. 돌아가기 줄은 그림자 없는 평면 모양으로 맞췄다.
4. 밴드는 자바스크립트로 다른 문서로 이동해 최초 loader의 load가 끝나지 않았다. 이전 문서를 성공으로 인정하지 않으면서, 새 주 문서의 load 완료를 인정하도록 고쳤다. 수정 전에는 30초 시간 초과, 최종 익명 상태 확인은 728ms였다.
5. 읽기 전용 DevTools 평가에서 `Element.matches`와 `new URL`이 부작용 검사에 막혔다. 태그 이름·속성·정규식으로 읽도록 바꿨다. 부작용 검사는 끄지 않았다.
6. 백그라운드에서 자동으로 자신을 다시 띄우려던 진단을 제거했다. 앱 밖을 조작하지 않고 명시적으로 이 앱에 복귀하는 방식으로 확인한다. 백그라운드 실패 시 캡처는 거부한다.

수정 전 실패 기록도 [pre-fix-failures.json](wp0/pre-fix-failures.json)에 남겼다. 당시 캡처 경로가 거부되거나 읽기 검사에 막힌 것은 `unavailable` 그대로 보존했다. 수정 뒤 별도 예제 진단으로 캡처·DOM 요약·추출 성공을 확인했다.

### 고친 내용

1. 네이버 로그인은 최상위 문서 경로만 보지 않고 편집기가 있는 같은 출처 iframe의 쓰기 경로를 읽는다. 두 서비스 모두 최대 15초 동안 로그인 판정 신호를 기다리며, 풀림이면 입력 없이 멈춘다. 로그인 복구·로그아웃·자격 증명 입력은 하지 않았다.
2. 네이버 실제 편집기의 `.se-content`와 기존 `.se-main-container`를 함께 지원하고, 제목·본문 안내 문구를 내용 개수에서 제외했다. 늦게 나타나는 자동복구 안내를 기다리고, 기존 글을 복구한 경우에는 무조건 `EXISTING_DRAFT_REQUIRES_EMPTY_EDITOR`로 입력 전에 중단한다. 기존 글을 버리는 버튼이나 삭제 버튼은 누르지 않는다.
3. 네이버 저장 제어는 실제 확인한 `button[data-click-area="tpb.save"]`로 좁혔다. 현재 화면의 표기는 `저장`이며 발행 제어와 별개다. **선택자만 고쳤고 실제 저장·재열람 성공을 확인하지 못했다.**
4. 밴드 목록은 `내 밴드` 영역의 `/band/…/post` 링크를 기다려 읽고, 광고·추천 항목을 선택 대상에서 제외한다. 모바일의 아이콘 글쓰기 버튼과 데스크톱 글쓰기 버튼을 구분해 기다린다. 모바일의 게시용 `완료` 버튼과 이름이 비슷한 클래스만으로 클릭하지 않는다.
5. 모바일 `textarea._postTextArea`, 사진 미리보기 `mediaImg`, 데스크톱 안내 문구 및 `band:attachment` 위젯을 구분한다. 사진 위젯의 안내 글자는 본문 대조에서 제외하고 사진은 별도로 센다.
6. 데스크톱은 제목이 정확히 `사진 올리기`이고 예시 항목이 5개인 창에서만 `첨부하기`를 한 번 누른다. 두 UA의 취소 확인 역시 정확한 문구·버튼 조합만 허용한다. 게시·발행 제어는 호출하지 않는다.

본문 입력은 글자당 60ms의 `Input` 명령과 Enter 키만 사용했다. 파일은 공통 `attachFiles`의 파일 입력 명령으로 전달했다. DOM 본문 수정, CKEditor setter, 합성 붙여넣기, 개인 사진첩·클립보드 조작은 하지 않았다. 공통 패키지에 Android API를 추가하지 않았다.

### 남은 실패와 밴드 제품 경로 권고

블로그의 장문 입력·사진·임시저장·재열람 검증은 **빈 편집기를 소유자가 직접 준비한 뒤 별도 실행이 필요하다.** 기존 자동복구 글을 보존하라는 제한 안에서 끝낼 수 없었으므로 완료로 표시하지 않는다. 본문·문단·사진 비교의 실제 성공도 주장하지 않는다.

**밴드 기본 경로는 모바일 UA + 파일 입력 5장 첨부 + 게시 전 멈춤을 권고한다.** 모바일은 textarea에서 원문 글자 수를 읽을 수 있고 중간 사진 확인창 없이 첨부된다. 데스크톱도 가능하지만 사진 창 확인과 위젯 텍스트 제외가 추가로 필요하다. 이번 UI에서는 임시저장을 확인하지 못했으므로 제품의 기본 임시저장 방식에서 밴드는 `작성 완료·게시 전 멈춤`으로 구분하고, 작성 화면을 보여 주며 보관해야 한다. 서버에 저장된 임시글처럼 `임시저장 완료`로 기록하면 안 된다. 이번 실험에서는 증거를 남긴 뒤 모든 밴드 작성 내용을 취소·폐기했다.

확인한 길이는 수용된 예시의 길이이며 최대 허용 길이가 아니다. 게시하지 않았으므로 게시 시 서버 검증·업로드 완료·게시 결과는 확인하지 않았다. 사진 붙여넣기는 미실험이다.

### 고친 내용과 회귀 확인

1. 자동복구 처리를 `prepareBlogEditor`로 분리했다. 기본은 `AUTO_RECOVER_CONSENT_REQUIRED`로 클릭 없이 중단한다. 앱에서 동의한 작업에만 `autoRecover: 'decline-with-user-consent'`를 넘기면 정확한 복구 안내의 `취소`를 선택한다. 동의 스위치는 기본 꺼짐이며 실험 시작 때 다시 꺼진다. 복구 안내를 닫아도 기존 내용이 있으면 `EDITOR_NOT_EMPTY`로 중단한다.
2. 예시 제목은 `[골투오토 실험]` 접두사를 붙인다. 본문은 글자당 60ms의 `Input.insertText`, 문단 구분은 Enter, 화면 이동은 PageDown을 쓴다. 최종 코드에는 32자 단위로 로그인·편집기 유지 여부를 다시 확인하는 보호도 추가했다. 입력 DOM을 고치거나 편집기 setter·합성 붙여넣기를 쓰지 않았다.
3. 사진 버튼·파일 입력 뒤 `.se-popup-image-type`의 `개별사진` 선택 단계를 처리한다. 배치 선택 제어와 사진 개수를 기다리고 원문·16문단을 대조한다. 개인 사진첩이나 시스템 파일 선택기를 조작하지 않았다.
4. 저장 전 제목·본문·정확한 문단 수·사진 수를 검사한다. 짧게 나타나는 저장 안내 문구 대신 새 고유 제목을 저장했을 때의 저장 개수 증가를 기다리도록 바꿨다. 이 새 대기 조건은 로컬 회귀 시험으로 확인했으며, 실제 기기에서는 기존 안내 대기 실패 후 추가 저장 없이 목록 재열람으로 저장을 입증했다.
5. 목록 열기는 `tpb*s.count`, 제목 선택은 `[aria-label="임시저장된 글"] > li button[data-click-area="tpb*s.tlist"] strong`으로 좁혔다. 버튼 전체에는 날짜 안내도 들어 있어 제목 노드만 정확히 비교하며, 일치 항목이 둘이면 중단한다.
6. 재열람된 화면 밖 사진의 `src`는 처음에 `data:image/svg+xml;base64` 자리 표시자다. 사진 요소 5개만으로 성공을 선언하지 않고, 본문을 클릭하고 PageDown을 보내 실제 파일명이 로드될 때까지 기다린다. 그 뒤 예시 번호 1~5와 앞선 문단 수를 읽는다. `Ctrl+End`만으로는 본문 스크롤이 이동하지 않았다. `compareDocumentPosition`은 읽기 전용 부작용 검사에 걸려 문서 순서대로 문단·사진을 세도록 바꿨다. 부작용 검사는 유지했다.
7. 로컬 브라우저 응답만 공급하는 회귀 시험에 동의 없는 복구 거절 금지, 동의 후 정확한 안내 취소, 기존 글 보호, 개별사진 선택, 안내 문구 없는 저장, 새 편집기·정확한 제목·중복 제목 차단, 자리 표시자 지연 로딩과 사진 위치·순서 대조를 추가했다. 실제 발행 제어의 클릭은 0회인지도 확인한다.

기기 실험은 PC의 임시 실행기가 **앱 전용 DevTools 연결 + 공통 Surface/sites 코드**를 호출해 수행했다. 안전한 단계 JSON은 앱 전용 `files/wp0`에도 기록했다. 최종 APK의 `blog.run` 전체를 다시 입력·저장하는 추가 실행은 하지 않았다. 수정한 재열람 함수는 기기에서 새 편집기·같은 저장 글로 두 번 통과했다. 최종 통합 APK 전체 경로가 재실행된 것처럼 해석하면 안 된다.

### 남은 제약과 WP5 권고

- 저장 안내 문구에만 의존하지 말고, 저장 시도를 한 번 했으면 모호한 응답에서 다시 저장하기 전에 정확한 제목으로 목록을 확인해야 한다. 이번 새 임시글의 개수 증가 조건은 기존 임시글 수정 저장을 다루는 일반 제품 규칙이 아니다.
- 원문 확인·저장 전 확인·새 편집기 재열람 확인을 나누고, 완료는 마지막 단계가 통과했을 때만 기록한다. 줄바꿈 포함 문자 수, 공백을 제외한 본문 값, 비어 있지 않은 문단 수, 사진 수·순서를 각각 비교한다.
- 실제 상품의 문단·사진 배치는 원문의 블록 순서를 따라 커서 위치를 잡아야 한다. 한 번에 5장을 넣으면 모두 마지막 문단 뒤로 들어갔다. 이번 예시 파일명 기반 검증은 WP0 전용이므로 실제 상품에는 개인정보를 기록하지 않는 별도 이미지 식별·대조 방식이 필요하다.
- 자동복구 안내는 기본 중단하고 사용자에게 선택을 받는다. 동의가 있는 해당 작업에서만 복구를 거절하며 저장 임시글 삭제나 기존 열린 글 덮어쓰기로 확장하지 않는다.
- Android 기본 JS 확인창은 숨김 WebView의 DOM이 아니었다. 현재 Surface의 CDP 확인 응답은 사용할 수 없었고 `run-as kr.goltou.auto`의 입력은 `INJECT_EVENTS` 권한 거부였다. 앱 밖의 입력 권한으로 우회하지 않았다. WP5에서는 이런 창이 나오면 사용자에게 보여 주고 이어갈 수 있어야 한다. 자동 확인을 기본값으로 넣지 않았다.
- 이번 임시 캡처 스크립트의 좌표·픽셀 배율·PNG 마스킹 그리기를 일치시키지 못해 편집기 전체 캡처는 채택하지 않았다. 이것을 앱 렌더링 자체의 오류로 단정하지 않는다. WP5에서 캡처 경로를 별도로 검증하고, 전체 본문·사진 순서에는 안전한 읽기 대조 결과도 함께 제시해야 한다.

### 밴드 제품 결정 (코드 변경 없음)

소유자 확정: **임시저장 모드에서는 앱이 밴드 작성기를 채운 뒤 게시 직전에 멈추고 작성기를 사용자에게 보여 준다. 게시 버튼은 사용자가 직접 누른다. 결과는 반드시 `게시 전 멈춤`으로 기록하며 저장된 임시글로 기록하지 않는다.** 이번 실행에서는 밴드 작성기를 열지 않았고, 이 결정을 구현하는 밴드 코드는 고치지 않았다.

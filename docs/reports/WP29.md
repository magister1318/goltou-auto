# WP29 블로그 실제 표 입력

## 구현

가격·출발일 표와 일반 텍스트 표를 실제 SmartEditor ONE 표로 옮기는 경로를 추가했다. 기존 일반 문단 입력과 같은 키보드 기반 굵기·링크 입력기를 셀 문단에도 적용한다. 행·열·빈 셀·셀 글자·셀 서식과 주변 문단·사진 순서를 독립 판독한다. HTML 표의 셀 run은 모델·계획·미리보기까지 보존하며 첫 행을 임의의 제목 행이나 굵게로 바꾸지 않는다.

`readBlogDocument`는 편집기와 게시 뷰어의 표를 하나의 `table` 토큰으로 읽는다. 저장 후 재개방과 게시 페이지는 두 번 연속 같은 live snapshot으로 안정화한 뒤 비교한다. `table` issue는 화면에서 **표**로 표시한다. 셀 글자는 공백을 지우고 비교하지 않는다. 기존 일반 본문·사진 식별/순서·숫자·태그·굵기·링크 검사도 유지한다.

도구 없음·크기 불일치·셀 불일치·표 밖 커서 이탈 실패는 고정 사유를 남긴다. 이번 삽입으로 확인된 유일한 표만 전체 셀 선택→삭제하고 원래 문서를 다시 읽어 대조한 뒤 기존 텍스트 행으로 옮긴다. 제거를 확인하지 못하면 저장하지 않는다. 폴백 행 안에서도 원래 셀의 굵기·링크·줄바꿈을 보존한다.

WP20 로그에 `table_insert_started`, `table_size`, `cells_filled`, `table_verified`/`table_fallback`과 고정 사유를 기록한다. 새 허용 필드는 숫자인 행·열·셀 수뿐이다. 결과와 등록 기록에는 “표를 넣지 못해 같은 내용을 글자 행으로 옮겼습니다.”를 표시한다. 기록의 폴백 여부는 별도 앱 내부 메타데이터에도 보관해 로그 보존 기간이 지난 뒤에도 유지한다. 기존 공개 범위 파일은 호환해서 읽는다. 셀 글자·상품 원문·계정·글 주소·인증값은 로그나 이 보고서에 넣지 않는다.

## 실제 편집기에서 관찰한 동작

설치 전, 기기의 골투오토 숨김 WebView에서 모든 저장·수정·발행·자동저장 요청을 차단하는 기존 점검창을 사용했다. DOM/편집기 모델/Selection setter 없이 마우스·키 입력과 읽기만 사용했고 임시저장은 하지 않았다.

- `button.se-table-toolbar-button[data-name="table"]`는 크기 선택창 없이 **3×3** `.se-component.se-table`을 즉시 만든다. 셀은 `tr` 아래 `td.__se-unit.se-cell`과 `.se-text-paragraph`다.
- `.se-cell-controlbar-column`의 마지막 선택 버튼→`.se-cell-context-menu-button.se-context-menu-button-delete`로 3×2가 됐다. 선택 버튼 중앙에는 `.se-cell-size-button`이 겹친다. 위쪽 1px 지점은 실제 선택 버튼에 적중해 메뉴가 열렸다. 행 선택은 같은 방식의 왼쪽 가장자리를 쓴다. 제품 코드는 누르기 직전 Surface의 읽기 전용 히트 대조를 한다.
- 셀을 하나씩 눌러 실제 텍스트를 입력하고, 셀을 한정한 기존 가상 선택 판독으로 커서를 확인했다. Ctrl+B와 기존 링크 적용 경로를 사용한다. 작성 중 링크는 `span.se-link.__se-node[data-href]`, 뷰어 링크는 `a[href]`다.
- 링크 입력창은 여는 동안 세로로 6px 이동했다. 표 편집 직후 잠시 나타난 `.se-toast-popup-message`가 입력창을 가리는 경우도 관찰했다. 위치 안정화와 실제 입력창 히트 대조 후 누르도록 보강하고 두 상황을 합성 회귀 fixture에 넣었다. 링크 주소나 선택 범위를 스크립트로 바꾸지 않는다.
- 실제 표에는 하단 edge 버튼이 없었다. 마지막 표 아래 12px의 기본 편집기 빈 영역을 누른 뒤 아래 키를 보내면 뒤에 빈 텍스트 컴포넌트가 생겼다. 이탈 후 표와 앞 내용이 그대로인지 다시 대조한다.
- 전체 셀 선택→셀 메뉴 삭제로 이번 점검창에서 만든 표만 제거되는 것을 확인했다. 여러 차례의 점검은 모든 저장 요청을 차단한 별도 창에서 했고 마지막에 그 창을 닫았다. 기존 임시글·게시글은 선택·수정·삭제하지 않았다.
- 최종 합성 기기 점검에서 **3행×2열, 6셀**의 빈 셀·굵기·링크·여러 줄이 계획과 정확히 같았고 `table_verified`로 끝났다. 이는 실상품 저장 성공을 대신하는 증거가 아니다.

WP18·WP25·WP28의 Ctrl+B, 가상 선택과 링크 renderer, rich-document 깊이 32, 사진 한 위치씩 입력, 저장 읽기에서 자동저장 차단 규칙을 확인했다. 게시 요청 검사 깊이나 공개 발행 게이트는 바꾸지 않았다.

## 사전 검사

합성 모델/읽기/미리보기/로그 시험 71개, 기존 변환·서식·내장 Node 호환성 시험 46개, 새 표 입력 브라우저 시험 6개, 게시 페이지 지연/불일치 표 시험 4개가 각 대상 실행에서 통과했다. 일부 겹치는 시험이 있으므로 합산한 전체 시험 수로 주장하지 않는다. 이후 추가한 여러 줄 폴백 시험과 안내 팝업 회귀시험도 통과했다. 전체 타입 검사는 통과했다.

전체 설치 게이트와 실상품 임시저장 결과는 아직 미확인이다. 다음 문서 갱신에서 실제 게이트 결과·실행 커밋·사용량·잔여 임시글·캡처를 기록한다.

## 실기기 예산 기준

기기는 읽기 전용으로 켜짐·잠금 해제·앱 전면을 확인했다. 깨우기·잠금 해제·설정 변경·자격 증명 입력은 하지 않았다. WP28과 같은 상품의 내용 식별값·제목·출발 배열·사진 29장을 앱 조회로 메모리에서 대조했다. 현재 저장 0회·공개 발행 클릭 0회·밴드 동작 0회다. 21:00 KST 이후 새 저장을 시작하지 않는다. 원문·개인 식별자와 캡처는 저장소 밖 `../runs/blog-shots/`에만 둔다.

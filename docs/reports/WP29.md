# WP29 블로그 실제 표 입력

실제 네이버 임시글에 **3행×2열의 표**가 저장됐고 재개방에서 **6셀 모두 정확**함을 확인했다. 본문 굵기 1구간·링크 2개·사진 29장과 순서도 유지됐다. 이번 실제 임시저장 1회·잔여 시험 임시글 1개, 공개 발행 클릭 0회·밴드 동작 0회다.

## 구현

가격·출발일 표와 일반 텍스트 표를 실제 SmartEditor ONE 표로 옮기는 경로를 추가했다. 기존 일반 문단 입력과 같은 키보드 기반 굵기·링크 입력기를 셀 문단에도 적용한다. 행·열·빈 셀·셀 글자·셀 서식과 주변 문단·사진 순서를 독립 판독한다. HTML 표의 셀 run은 모델·계획·미리보기까지 보존하며 첫 행을 임의의 제목 행이나 굵게로 바꾸지 않는다.

`readBlogDocument`는 편집기와 게시 뷰어의 표를 하나의 `table` 토큰으로 읽는다. 저장 후 재개방과 게시 페이지는 두 번 연속 같은 live snapshot으로 안정화한 뒤 비교한다. `table` issue는 화면에서 **표**로 표시한다. 셀 글자는 공백을 지우고 비교하지 않는다. 기존 일반 본문·사진 식별/순서·숫자·태그·굵기·링크 검사도 유지한다.

도구 없음·크기 불일치·셀 불일치·표 밖 커서 이탈 실패는 고정 사유를 남긴다. 이번 삽입으로 확인된 유일한 표만 전체 셀 선택→삭제하고 원래 문서를 다시 읽어 대조한 뒤 기존 텍스트 행으로 옮긴다. 제거를 확인하지 못하면 저장하지 않는다. 폴백 행 안에서도 원래 셀의 굵기·링크·줄바꿈을 보존한다.

WP20 로그에 `table_insert_started`, `table_size`, `cells_filled`, `table_verified`/`table_fallback`과 고정 사유를 기록한다. 새 허용 필드는 숫자인 행·열·셀 수뿐이다. 결과와 등록 기록에는 “표를 넣지 못해 같은 내용을 글자 행으로 옮겼습니다.”를 표시한다. 기록의 폴백 여부는 별도 앱 내부 메타데이터에도 보관해 로그 보존 기간이 지난 뒤에도 유지한다. 기존 공개 범위 파일은 호환해서 읽는다. 셀 글자·상품 원문·계정·글 주소·인증값은 로그나 이 보고서에 넣지 않는다.

## 실제 편집기에서 관찰한 동작

설치 전, 기기의 골투오토 숨김 WebView에서 모든 저장·수정·발행·자동저장 요청을 차단하는 기존 점검창을 사용했다. DOM/편집기 모델/Selection setter 없이 마우스·키 입력과 읽기만 사용했고 임시저장은 하지 않았다.

- `button.se-table-toolbar-button[data-name="table"]`는 크기 선택창 없이 **3×3** `.se-component.se-table`을 즉시 만든다. 셀은 `tr` 아래 `td.__se-unit.se-cell`과 `.se-text-paragraph`다.
- `.se-cell-controlbar-column`의 마지막 선택 버튼→`.se-cell-context-menu-button.se-context-menu-button-delete`로 3×2가 됐다. 선택 버튼 중앙에는 `.se-cell-size-button`이 겹친다. 위쪽 1px 지점은 실제 선택 버튼에 적중해 메뉴가 열렸다. 행 선택은 같은 방식의 왼쪽 가장자리를 쓴다. 제품 코드는 누르기 직전 Surface의 읽기 전용 히트 대조를 한다.
- 셀을 하나씩 눌러 실제 텍스트를 입력하고, 셀을 한정한 기존 가상 선택 판독으로 커서를 확인했다. Ctrl+B와 기존 링크 적용 경로를 사용한다. 작성 중 링크는 `span.se-link.__se-node[data-href]`, 뷰어 링크는 `a[href]`다.
- 링크 입력창은 여는 동안 세로로 6px 이동했다. 표 편집 직후 잠시 나타난 `.se-toast-popup-message`가 입력창을 가리는 경우도 관찰했다. 위치 안정화와 실제 입력창 히트 대조 후 누르도록 보강하고 두 상황을 합성 회귀 fixture에 넣었다. 링크 주소나 선택 범위를 스크립트로 바꾸지 않는다.
- 실제 표에는 하단 edge 버튼이 없었다. 마지막 표 아래 12px의 기본 편집기 빈 영역을 누른 뒤 아래 키를 보내면 뒤에 빈 텍스트 컴포넌트가 생겼다. 이탈 후 표와 앞 내용이 그대로인지 다시 대조한다.
- 전체 셀 선택→셀 메뉴 삭제로 이번 점검창에서 만든 표만 제거되는 것을 확인했다. 여러 차례의 점검은 모든 저장 요청을 차단한 별도 창에서 했고 마지막에 그 창을 닫았다. 기존 임시글·게시글은 선택·수정·삭제하지 않았다.
- 최종 합성 기기 점검에서 **3행×2열, 6셀**의 빈 셀·굵기·링크·여러 줄이 계획과 정확히 같았고 `table_verified`로 끝났다. 이는 실상품 저장 성공을 대신하는 증거가 아니다.

WP18·WP25·WP28의 Ctrl+B, 가상 선택과 링크 renderer, rich-document 깊이 32, 사진 한 위치씩 입력, 저장 읽기에서 자동저장 차단 규칙을 확인했다. 게시 요청 검사 깊이나 공개 발행 게이트는 바꾸지 않았다.

긴 실상품 문서의 저장 차단 점검에서는 마지막 사진 아래 12px가 `.se-content-guide`여서 입력 위치를 만들지 못했다. 그 아래 실제 `button.se-canvas-bottom-button.__edge-area`를 관찰했고, 직접 누른 뒤 빈 문단과 초점·마지막 컴포넌트·끝 위치가 모두 맞는 가상 커서를 확인했다. 표 내부 하단 버튼과는 다른 편집기 전체 하단 버튼이다. 이를 우선 사용하도록 고쳤고 정상 표 이탈과 사진 뒤 폴백 fixture 모두 해당 버튼을 실제로 눌렀는지 검사한다. `51401be`의 게이트는 이 추가 관찰을 반영하기 위해 설치 전에 중단했다.

이 버튼은 높이가 320px라 중앙이 떠 있는 하단 도구 모음에 가렸다. 버튼 위에서 20px 지점은 실제 버튼에 적중했다. 최종 저장 차단 점검에서 **3×2·6셀 원문 일치·native·table_verified**와 표 뒤 정상 커서를 확인했다. 합성 시험에는 중앙을 가리는 고정 도구 모음과 실제처럼 고정된 임시글 목록을 함께 재현한다. 점검 도중의 폴백과 최종 표는 이번 실행의 미완성 문서 안에만 있으며 저장하지 않았다. 저장 여부는 문서 입력 성공과 구분한다.

## 사전 검사

합성 모델/읽기/미리보기/로그 시험 71개, 기존 변환·서식·내장 Node 호환성 시험 46개, 새 표 입력 브라우저 시험 6개, 게시 페이지 지연/불일치 표 시험 4개가 각 대상 실행에서 통과했다. 일부 겹치는 시험이 있으므로 합산한 전체 시험 수로 주장하지 않는다. 이후 추가한 여러 줄 폴백 시험과 안내 팝업 회귀시험도 통과했다. 전체 타입 검사는 통과했다.

첫 설치 게이트(`c5d37af`)는 전체 **92개 파일·1,115개 중 1,108개 통과, 7개 실패**(1003.82초)로 설치 전에 중단했다. 실패는 합성 발행 경로의 시간 초과 6개와 기존 미리보기 시험의 제목 셀 기대 1개였다. 당시 APK 설치·실제 임시저장은 0회다.

합성 편집기의 일반 모드에는 행·열 조절 컨트롤이 없어 불필요한 표 폴백 대기가 누적됐다. 실제 관찰한 조절 버튼을 정상 fixture에도 구현하고 의도적인 `bad-table` 실패 모드만 그대로 유지했다. 표가 없는 작업에도 새 표 안정화 폴링을 무조건 추가했던 지연은 표가 있는 계획에만 적용하도록 고쳤다. 기존 비표 작업의 입력·사진·서식·저장·게시 검증은 유지한다. 기존 미리보기 시험은 첫 행을 임의의 제목/굵게로 보지 않는 이번 요구에 맞게 네 셀의 글자와 서식을 확인하도록 바꿨다.

대상 재검사에서는 제목 행 기대와 비표 서식 시간 초과가 해결됐다. 실제 표를 넣고 13장을 저장·재개방·게시 확인하는 합성 왕복은 삭제 없이 27.15초였고, 추가 삭제·별도 복구 확인까지 묶은 네 시험은 기존 30초 바깥 한도에 걸렸다. 관련 왕복 시험의 바깥 실행 한도만 45초, 별도 복구 두 번을 포함하는 시험은 60초로 맞췄다. 서비스 폴링 제한시간·원문 대조·공개 범위·한 번만 제출·삭제 신원/부재 검증 조건은 완화하지 않았다.

실패 대상 재검사는 **7개 통과**(선택 실행 밖 30개는 건너뜀)다. 삭제·복구까지 포함한 네 경로는 실제로 30.75~33.81초였으며, 제출 횟수·정확한 내용·삭제 신원과 부재 대조를 모두 통과했다. 이 선택 검사를 전체 시험 통과로 간주하지 않는다.

두 번째 설치 게이트(`b56d90e`)는 **92개 파일·1,115개 전부 통과, 건너뜀/실패 0개**(932.39초), 타입 검사·소스 Node 18 호환성(95개)·웹 빌드·Android assembleDebug·APK 안의 두 번들/커밋/해시 대조를 통과했다. 같은 APK를 게이트의 `adb install -r`로 설치했고 앱 부팅과 코어 응답을 확인했다.

첫 실상품 입력은 표의 첫 셀을 누르기 직전 히트 대조가 달라져 저장 전에 중단됐다. 표는 제거됐고 문단 96개·사진 29장이 보존됐으나 사진 뒤 빈 문단이 사라져 폴백 커서 확인도 실패했다. 임시저장 서비스 요청은 0회다. 현재 실행이 만든 미완성 내용만 다음 실행의 기존 복구 경로로 처리하며 소유자의 기존 임시글은 건드리지 않는다.

새 표가 마우스 이동 때 재배치되는 합성 fixture와 표 제거가 사진 뒤 빈 문단까지 소비하는 fixture를 추가했다. 누름 전 히트 대조가 거부한 경우에만 좌표를 다시 읽고, 누름 이후의 전송 오류는 재시도하지 않는다. 네이티브 입력으로 끝 문단을 복원하고 가상 커서의 초점·마지막 컴포넌트·축소 범위·끝 위치를 대조한다. 폴백 정리가 실패한 로그는 텍스트 행 성공 안내로 남기지 않는다. 관련 회귀 시험 **4개 통과**(선택 밖 112개 건너뜀)였다. 최종 전체 게이트와 실상품 결과는 아래에 기록한다.

## 실기기 예산 기준

기기는 읽기 전용으로 켜짐·잠금 해제·앱 전면을 확인했다. 깨우기·잠금 해제·설정 변경·자격 증명 입력은 하지 않았다. WP28과 같은 상품의 내용 식별값·제목·출발 배열·사진 29장을 앱 조회로 메모리에서 대조했다. 실제 저장은 20:05 KST에 시작해 21:00 제한 전이었다. 원문·개인 식별자와 캡처는 저장소 밖 `../runs/blog-shots/`에만 둔다.

## 실제 임시저장과 재개방 결과

1. 재설치 후 계획을 WP28 계획과 메모리에서 완전히 대조했다. 블로그만 선택, 임시저장 모드, 문장 다듬기·글 끝 문구·링크 카드 모두 꺼짐을 확인했다. 미리보기 표는 3×2이며 임의의 제목 셀이 없다.
2. 첫 입력 당시 빈 편집기였음을 확인했고 이후 이 실행만 작성한 미완성 내용이 복구 안내로 나타났다. 네이버 복구 내용을 복원해 조사하지 않았고 앱의 **버리고 새로 쓰기**로 이번 미완성 내용만 정리했다. 기존 임시저장함의 글은 선택·삭제하지 않았다. 이 시점까지 서비스 임시저장 요청은 0회다.
3. 실제 입력 로그는 `table_insert_started` → `table_size`(3, 2) → `cells_filled`(1~6) → `table_verified`(3, 2, 6)다. 폴백은 없었다. 임시저장 POST 허용은 네트워크 형태가 있는 로그 기준 **1회**, 성공 응답 1회이며 별도 Network 관찰도 1회였다. 공개 발행 요청은 0회다. 허용 판정의 사유 줄과 요청 형태 줄을 두 요청으로 세지 않았다.
4. 앱의 단일 최종 로그는 terminal **succeeded**이며 결과 화면은 **블로그에 임시저장했습니다**다. 등록 기록도 새 블로그 임시저장 성공 1행이며 텍스트 폴백 표시가 없다. 표 판독은 예상/관찰 1/1, 같은 live snapshot 2/2에서 안정화됐고 최초 표 안정화 완료는 1,895ms였다.
5. 모든 저장·발행·자동저장 요청을 막은 앱의 별도 점검창에서 임시글 목록을 다시 읽었다. 이전 목록보다 **1개 증가**했으며 기존 4개 항목의 제목·시각·서비스 식별 증거는 모두 그대로였다. 제목만으로 고르지 않고 목록 변화에서 유일한 새 항목을 확인해 재개방했다.
6. 실제 `table` 토큰 1개, **3행·2열·6셀**의 글자·셀 서식과 컴포넌트 순서가 계획과 정확했다. 굵기 **1/1**, 링크 **2/2**(글자·주소 포함), 사진 **29/29**(순서·식별, 29개 로드 관찰)다. 이전 WP28 판독의 일반 텍스트 99개 중 표 행 3개만 표 토큰으로 바뀌어 일반 텍스트는 96개다. 표를 비교용으로만 원래 세 행으로 투영한 문단 배열은 이전 배열과 완전히 같았다.

실제 저장은 **1/2회**만 사용했다. 이번 시험 임시글은 네이버 임시저장함에 **1개** 남겼고 기존 글은 건드리지 않았다. 별도 재개방 점검창은 저장하지 않고 닫았다.

캡처는 저장소 밖 `../runs/blog-shots/g6-preview-table.png`(3×2 미리보기)와 `g6-result-draft.png`(실제 성공 화면)를 보관하고 눈으로 확인했다. 재개방한 표의 위치와 셀을 다시 대조한 뒤 `g6-editor-table.png`를 시도했으나 숨김 WebView의 CDP 비트맵은 흰색이었다. 빈 이미지는 증거에서 제거했다. 앱의 `draft.show`는 비활성화돼 있고 네이티브 표시 경로는 로그인 Surface로 한정되므로 편집기 표의 시각 캡처는 확보하지 못했다. 표 자체의 DOM 구조·셀·서식·순서 검증은 위와 같이 완료했다.

## 미확인과 후속 검토

- 실제 공개 페이지의 새 표는 발행 예산 0회이므로 시험하지 않았다. 게시 페이지의 표 지연·누락·셀·순서 비교는 합성 fixture에서 확인했다.
- 재개방한 실제 표의 시각 캡처는 미확보다. 미리보기와 성공 화면 캡처는 확인했다.
- 다른 상품·계정·기기·release APK의 실서비스 왕복, 병합 셀이나 복합 이미지 표의 새 지원은 이번 범위가 아니다. 단순 직사각형으로 확인하지 못하는 표는 명시적 폴백 대상이다.
- 기존 단일 블로그 runner의 성공 후 보조 `job.creationState`가 `uncertain`으로 남는 동기화 흔적을 관찰했다. 네이버 성공 응답·저장 후 재개방·등록 기록·terminal succeeded는 모두 확인했다. 이 성공 상태 동기화는 기존 성공 경로이며 이번 표 작업에서 범위를 넓혀 고치지 않았다. 후속 검토에 넘긴다.

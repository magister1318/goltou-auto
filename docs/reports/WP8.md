## 구현

- 블로그의 사진 묶음을 원문 순서대로 한 장씩 파일 입력에 전달하고, 사진 개수 확인과 다음 본문 커서 복원까지 마친 뒤 `사진 n/N`을 갱신한다. 사진·원본 바이트·본문 순서·문자당 60ms 입력 간격을 유지한다. 사진을 줄이거나 글을 나누지 않는다.
- 블로그·밴드 실행기가 완료한 각 사진의 입력 구간만 측정한다. 내려받기·본문 입력·사용자 선택 대기·저장·재열람은 사진 시간에서 제외한다. 밴드는 기존 한 장씩 첨부와 500ms 이상 슬롯 안정화 확인을 그대로 사용한다.
- 사진 3장 완료 전에는 예상 시간을 숨긴다. 이후 `관측 사진 시간 합계 / 완료 장수 × 남은 장수 + 남은 글자 수 × 0.06초`를 올림해 **남은 입력 시간 약 n초 (추정)**로 표시한다. 저장·대조까지의 전체 잔여 시간이라는 뜻은 아니다. 채널 전환과 새 입력에서 이전 추정을 지운다. UI는 기존 글 중심 구조를 유지한다.
- 재열람에서 사진 식별자가 비어 있으면, 태그 레이어를 닫은 상태에서 보이는 본문/제목 문단을 클릭하고 Ctrl+Home → PageDown으로 위에서 아래로 읽는다. 중간 사진을 지나치지 않으며 내용 입력·DOM 수정은 없다. 사진 수에 따라 읽기 제한을 `max(30초, 장수 × 2초)`로 두고, 본문과 사진 순서 대조는 그대로 수행한다. 읽기 시간·사진 수·키 횟수만 수집한다.
- 변환 점검에 `struckNumericCharacters`를 추가했다. `del`/`s`/`strike` 아래 텍스트의 ASCII 숫자 글자 수만 세고 중첩 태그는 중복 집계하지 않는다. script 등 제외 요소의 숫자는 세지 않는다. 취소선 본문이나 숫자 값은 남기지 않으며 기존 글자 보존 정책은 바꾸지 않았다.
- WP7의 발행 방지 a 초점·실제 클릭 대상 검사, b 태그 레이어 닫힘 독립 확인, c 탐색 전 발행·수정 요청 차단을 유지했다. `/RabbitWrite.naver`·`/RabbitUpdate.naver` 차단을 약화시키지 않았다. 실제 발행 제어는 누르거나 시험하지 않았다. 디버그의 실험 제목과 실행기 수명 중 저장 1회 제한도 유지했다.

### 사전 확인과 설치

화면은 `dumpsys power`의 `mWakefulness=Awake`와 `dumpsys display`의 `Display State=ON`·`mCommittedState=ON`, 앱 전면은 `dumpsys window`의 현재 초점과 `dumpsys activity`의 최상위 재개 액티비티가 각각 `kr.goltou.auto`인지 교차 확인했다. 설치 전·등록 시작 전·입력 관측 중·버리기 전에도 읽기 전용으로 검사했다. 깨우기·잠금 해제·외부 앱 입력은 없었다.

설치본 SHA-256은 이전 `f4b16181…2939c4`, 로컬 최종 APK는 `4c2b1330…0f0d86`으로 달라 `adb install -r`로 한 번 교체하고 이 패키지만 다시 열었다. 설치 직후 16:13:10.223에는 초점 신호가 확인되지 않아 입력 없이 기다렸고, 16:13:20.682에 두 전면 신호가 모두 회복됐다(읽기 전용 대기 10.459초, 상한 2분). 이후 등록 시도 중 전면·화면 조건 상실은 없었다. 설치 후 기기의 APK 해시는 최종 APK와 일치했다. 로그인은 유지됐으며 자격 증명·쿠키·토큰을 읽거나 입력·추출하지 않았다.

## 검토 반영 1차

검토에서 확인한 밴드 실패 원인은 운영 `/auto/posts/update`가 `stopped_before_post`를 아직 받지 않아 `invalid`를 응답한 것이다. 서버 수정은 별도 작업이며, 이번에는 앱의 오류 처리와 계약·시험만 고쳤다.

- 밴드·블로그 실행기에서 API 기록 실패를 사이트 실패와 분리했다. 검증된 채널 결과를 유지하고 `기록하지 못함`, `RECORD_FAILED:<API 코드>`, 한국어 API 안내를 표시한다. 상품 제목·본문·토큰을 되비추는 응답이나 임의 예외는 고정 한국어 안내로 바꾸고 실패 화면에 상품 제목을 표시하지 않는다.
- 밴드 입력·대조 후 기록만 실패해도 `밴드 화면 보기`·`버리기`를 유지한다. 폐기 확인창의 취소·확인도 처리한다. 자동 재요청은 하지 않고 `기록 다시 시도`만 동일 `postNo`·동일 갱신 본문을 다시 보낸다. 입력·사진 첨부·저장·게시·기록 시작을 반복하지 않으며 중복 재시도 입력을 차단한다. 계속할 단계가 남으면 기록 복구 뒤 사용자가 `이어하기`를 누른다.
- 가짜 API와 루프백 계약 서버의 `invalid`·연결 끊김을 밴드·블로그 두 실행기에서 시험했다. 로컬 밴드 편집기의 검증된 본문·사진 유지, 기록만 재시도, 폐기 및 확인창 처리를 확인했다. 계약·가짜 API에는 band 전용, 하루 한도 포함, `published | stopped | stopped_before_post` 전이와 같은 상태의 멱등 갱신, `running`·`draft_saved` 복귀 금지, `myPosts.band` 표시를 반영했다.
- 기기·운영 API·운영 DB 작업은 하지 않았다. 실제 서버의 새 상태 수용과 수정 APK의 실기기 확인은 미실시이며 다음 검토에 넘긴다. 앞선 실기기 관측 수치와 증거는 그대로 보존한다.

최종 확인: `pnpm install`(잠금 파일 변경 없음), `pnpm typecheck`, `pnpm test`(**24개 파일·199개 통과, 건너뜀 0개, 293.78초**), `pnpm build`, Android `./gradlew.bat assembleDebug --console=plain --no-daemon --offline`(**22초**, 저장소 `.gradle-cache`), `git diff --check` 모두 통과했다.

수정 APK는 **64,103,014바이트**, SHA-256 `eb478f73819c4c85ba2021bbdb5d870788332a457e0be243d5a01665e4346f46`이다. APK 안의 번들 1,004개 파일이 빌드 자산과 바이트 단위로 일치했다. APK는 설치하지 않았으며 생성 자산·APK·캐시·비밀 값은 커밋하지 않는다. 기존 브랜치에 커밋·푸시하고 PR #9는 초안으로 유지한다.

**사진 36장 상품 한 건의 밴드 입력·재읽기 대조·`stopped_before_post` 기록 수용을 확인했다. 앱 문구는 ‘게시 전 멈춤’이고 등록 기록과 상품 목록의 밴드 표시도 일치했다. 이후 앱의 버리기로 작성기·본문·사진을 없앴고 같은 기록이 `stopped`로 바뀌었다. 하루 한도 사용은 1→0건, 같은 밴드의 시작 버튼은 다시 활성화됐다. 두 번째 작업은 시작하지 않았다. 작성기 열기 1/3회, 밴드 게시 0회, 네이버 실행 0회다. 앞선 실행의 기록 수용 미확인은 이번 결과로 해소됐다.**

### 사전 확인·설치·선택

- 지정된 adb의 SM-S928N에서 `dumpsys power`의 `mWakefulness=Awake`, `dumpsys display`의 `Display State=ON`·`mCommittedState=ON`을 읽었다. 전면은 `dumpsys window`의 현재 초점과 `dumpsys activity`의 최상위 재개 액티비티가 모두 `kr.goltou.auto`인지 교차 확인했다. 자동 관측의 검사 94회도 수치로 남겼다. 깨우기·잠금 해제·앱 밖 입력은 없었다.
- `pnpm install`·`pnpm build`·Android 디버그 빌드 후 `adb install -r`로 교체하고 `kr.goltou.auto/.MainActivity`만 열었다. 설치 직후 18:22:15.071에는 초점 신호가 없어 입력하지 않고 기다렸다. 18:22:25.585에 두 전면 신호가 회복됐다(**10.514초**, 대기 상한 2분). 실행 중 화면·전면 조건 상실은 없었다.
- 설치 APK는 **64,103,014바이트**, SHA-256 `eb478f73819c4c85ba2021bbdb5d870788332a457e0be243d5a01665e4346f46`이며 기기에 설치된 APK 전체 해시와 일치했다. 골투 세션과 상품 목록이 복원됐다. 자격 증명 입력이나 쿠키·토큰 추출은 없었다.
- 정상 상품 목록 → 미리보기 → 밴드만 선택 → 임시저장으로 등록 시작을 사용했다. 사진 36장, 첫 밴드 한 곳, 선택 옵션 모두 꺼짐, 실험 제목 접두사, 원문 대조 일치를 확인했다. 밴드 목록의 첫 읽기는 `OBSERVATION_TIMEOUT`이었고 등록 시작 전 선택 스위치를 껐다 켜 정상 목록을 다시 읽었다. 이때 작성기를 열거나 등록 기록을 시작하지 않았다. 실제 등록 시작은 한 번이며 본문·사진 입력은 재시도 없이 한 차례 마쳤다.

### API 기록·표시·버리기·한도 반환

18:26:22.260에 앱의 정상 등록 기록 읽기로 이번 **기록 9번**의 `stopped_before_post`, 6단계, 새 글 주소 없음을 확인했다. 상품 목록의 `myPosts.band`도 같은 상태였다. 앱 안의 작성 화면이 표시된 것을 네이티브 돌아가기 제어로 확인한 뒤 앱의 뒤로 가기로 돌아왔다. 진행 화면의 **게시 전 멈춤**, 등록 기록의 **게시 전 멈춤 · 확인하고 게시**, 상품 목록의 밴드 날짜 표시를 실제 UI에서 확인하고 진행 화면으로 복귀했다(18:27:05.270). 게시 제어는 누르지 않았다.

앱의 **버리기**를 한 번 눌렀다. 18:27:12.092에 최종 `stopped` 알림, 18:27:13.380과 18:27:20.938의 별도 읽기에서 **작성기 없음·본문 0자·사진 0장·업로드 없음·새 글 주소 없음**을 확인했다. 확인창에서 추가 선택을 요구하지 않았으며 입력이나 작성기를 다시 열지 않았다. 앱 문구는 **작성을 버렸습니다**다.

18:27:23.192의 API 기록에서 같은 9번이 **`stopped`·7단계**로 바뀌고, 상품의 밴드 표시가 없어졌음을 확인했다. 설정의 하루 한도는 3건이며, 정상 기록 목록에서 같은 밴드의 오늘 기록 중 `failed`·`stopped`를 제외한 건수는 **버리기 전 1건 → 후 0건**이다. 같은 상품·같은 밴드·임시저장·옵션 꺼짐을 다시 선택했을 때 **임시저장으로 등록 시작** 버튼이 활성화됐고 이전 작업과 같은 대상인지도 확인했다. **시작 버튼은 누르지 않았다.** 등록 기록 UI의 **중단** 표시와 밴드 표시 제거까지 확인하고 상품 목록으로 돌아왔다.

한도 반환의 근거는 API의 동일 기록 상태 전이·한도 포함 건수 감소·동일 대상의 시작 버튼 활성화다. 한도 3건 경계의 `conflict` 응답이나 두 번째 `/auto/posts/start` 수락 자체는 시험하지 않았다. 작성기 열기는 전체 **1/3회**, 등록 시작 1회, 게시 0회, 네이버 실행 0회다.

근거: [설치·사전 검사·단계·사진 시간](wp8/band-recheck-run.json), [재읽기 대조·화면 표시·API 수용](wp8/band-recheck-verification.json), [버리기 두 번 읽기·중단 기록·한도·다시 시작 가능 상태](wp8/band-recheck-discard.json). 밴드 이름·식별키·계정 정보·상품 제목/본문/사진 주소는 증거와 보고서에 남기지 않았다.

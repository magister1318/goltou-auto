## 구현한 것

1. `sites/naver-blog/plan.ts`의 실제 실행기가 WP4 입력 계획과 준비된 파일 매핑을 받는다. 제목, 문단, Enter 줄바꿈, 사진 묶음, 표를 계획 순서대로 넣는다. 사진마다 본문 마지막 텍스트 컴포넌트의 커서를 읽어 확인한다. 사진 위치까지 포함한 전체 토큰 순서는 저장 전과 재열람 후 모두 대조한다.
2. 문자는 Surface의 입력 명령만 사용한다. 실제 기본 간격은 글자당 60ms이며, 최대 32자마다 로그인·편집기 유지와 중단 요청을 확인한다. 편집기에 DOM 쓰기, setter, 합성 붙여넣기를 사용하지 않는다. 로컬 시험만 입력 간격을 0ms로 줄였다.
3. 표 버튼으로 삽입한 표의 행·열 수를 읽고 셀을 클릭해 입력한다. 제어가 없으면 행별 `출발일 | 가격원` 글자 목록으로 넣는다. 삽입한 표의 크기가 맞지 않으면 Ctrl+Z 한 번 뒤 원래 내용과 일치하는지 확인하고 목록으로 바꾼다. 복원이 확인되지 않거나 셀 입력 도중 불안정해지면 멈춘다. 결과에 `native`/`text-list`를 남긴다.
4. 끝 문구, 태그 입력란, 링크 카드의 선택 경로를 연결했다. 링크 카드가 생기지 않으면 URL 글자를 유지하고 `url-text`로 기록한다. 기본 옵션과 예시 계정의 기본 해시태그는 꺼짐/빈 목록이다. 실제 네이버의 선택 옵션 제어는 이번에 검증하지 못했다.
5. 저장 전에 원문을 대조하고 저장 입력 시도를 먼저 표시한다. 저장 응답이나 전송 결과가 모호해도 재저장하지 않는다. 새 Surface의 빈 편집기에서 임시글 목록을 열어 정확한 제목이 한 건인지 확인한 뒤 다시 읽는다. 중복 제목은 중단한다. 공통 `compareDocuments`로 제목, 글자, 문단 내용·수, 사진 순서, 가격, 출발일, 골프장을 대조한 뒤에만 `draft_saved`로 기록한다.
6. 사진은 원본 바이트를 유지하면서 `goltou-내용해시16자리-순번.확장자` 이름으로 준비한다. 재열람한 사진에서 그 이름을 읽어 API 사진과 대응시킨다. 글자·사진의 교차 배치도 별도로 비교하며, 식별자가 없는 지연 로딩 사진은 PageDown 입력으로 읽는다. 네이버가 파일명을 바꿔 식별할 수 없으면 완료 처리하지 않는다. 예시 API의 사진 확장자도 번들 PNG와 맞췄다.
7. Android에 실제 블로그 실행기를 주입했다. 첫 단계에서 실제 편집기와 로그인을 확인하고, 사진 준비와 변환 뒤 작성·저장·재열람을 수행한다. 밴드가 선택된 작업은 시작 전에 거부하며 밴드 작성기를 열지 않는다. 실험 제목 접두사와 실행기 수명 전체의 저장 시도 상한 3회를 검사한다. 실제 네이버 발행은 차단한다. 발행 선택·확인 → 저장 검증 → 발행 → 글 주소 확인 경로는 명시적으로 허용한 `127.0.0.1` 가짜 편집기에서만 실행된다.
8. 로그인 풀림은 `login_paused`와 `로그인 풀림으로 멈춤`으로 남기고 해당 Surface를 보여 준다. 사용자가 돌아온 뒤 로그인 상태를 실제로 다시 읽는다. 입력 중 보관한 내용이 현재 편집기와 같으면 그 뒤부터 이어 쓴다. 다르면 새 편집기에서 처음부터 시작한다. 부분 표·사진 입력처럼 안전하게 이어갈 경계를 확정하지 못한 경우도 새 편집기를 사용한다.
9. 자동복구는 기본 중단하고 앱에서 명시적으로 동의한 경우에만 해당 안내를 거절한다. 미동의하면 그대로 둔다. WebChromeClient가 alert/confirm의 JsResult를 보관하고 Surface 상태·응답 연결로 앱에 전달한다. 자동 확인은 없다. 확인창 때문에 최초 Input 응답까지 막혀도 추가 입력 없이 사용자 선택을 기다린다. 사용자가 멈추거나 실패하면 편집기를 닫지 않는다.
10. 단계, 사진 수, 글자 %, 남은 시간 어림, 자동복구 선택, 확인창 선택 화면을 연결했다. 기록의 `확인하고 발행`은 이번 작업에서 검증한 기존 임시글 Surface를 보여 준다. 새 상품 등록이나 자동 발행을 시작하지 않는다. 실패 단계·안전한 오류 코드·캡처 파일명을 앱 전용 `files/wp5` JSON에 기록하도록 연결했다.
11. 캡처는 WebView.draw와 view.scale 조합 대신 CDP 화면을 메모리로 받아 마스킹한 뒤에만 PNG로 저장한다. 같은 CSS 뷰포트의 좌표를 PNG 폭·높이와 각각 대응시킨다. 텍스트, 입력, 이미지, CSS 배경 이미지, iframe 등을 가린다. 앱 전면 확인과 로그인 화면 보호를 유지한다. **실제 숨김 WebView의 수정 후 캡처 품질은 미검증이다.**

## 다음에 확인할 것

- 소유자가 기기 화면을 사용할 수 있을 때 새 APK를 설치하고, 이미 로그인된 앱·네이버 상태에서 실제 홈 → 완료 흐름을 확인해야 한다. 이번에는 로그인이나 소유자 확인 응답을 대신하지 않았다.
- 실제 네이버의 사진 삽입 후 커서, 업로드된 파일명 보존, 표 제어, 태그 칸, 링크 카드, 재열람 지연 로딩 선택자는 로컬 시험만 통과했다. 식별이나 대조가 되지 않으면 실패로 멈추며 임시저장 완료라고 주장하지 않는다.
- Android WebChromeClient의 사용자 선택 전달과 CSS/PNG 배율 마스킹은 빌드만 확인했다. 실기기에서 기본 확인창과 마스킹 결과를 검증해야 한다.
- 기록의 기존 임시글 열기는 현재 실행기에서 검증한 작업에 한정된다. 이전 프로세스·다른 기존 기록의 임시글을 찾는 영구 식별자는 이번에 추가하지 않았다. 앱 프로세스 종료 뒤 작성 이어하기도 미검증이다.
- 밴드 실제 실행은 WP6에 남겼다. 실제 네이버 발행은 계속 차단한다. 운영 반영과 main 푸시는 하지 않는다.

### 고친 것과 회귀 확인

- 최초 문서 load와 편집기 iframe 준비를 나누어 기다린다. 실제 로그인 화면이 확인되면 입력 전에 중단한다. 늦게 생성되는 iframe을 로컬 브라우저에서 재현했다.
- 디버그 검증에서만 합성 세션을 복원하며 기본 시작은 익명 상태를 유지한다. 자격 증명·로그인 호출 없이 시작하고 기본 가짜 API에서는 그 세션을 거부하는 시험을 추가했다.
- 통합 채널 실행기가 WP5의 실패 기록/캡처를 누락하던 연결을 복원했다. 저장 검증 및 밴드 게시 전/실패 시점에 마스킹 캡처도 연결했다.
- 접근 가능한 iframe은 자식의 실제 글자·이미지 좌표를 읽고, 접근할 수 없는 iframe은 전체를 가린다. 기존의 iframe 전체 검정 캡처는 개인정보는 가리지만 품질 확인용으로 부적합했다.
- 네이티브 밀도의 `fromSurface:false`는 CSS 좌표와 맞지 않음을 기기에서 확인해 채택하지 않았다. 최종 코드는 **compositor 캡처만** 사용하고, 첫 프레임 요청이 응답하지 않으면 읽기 캡처만 1회 재시도한다. 편집기 입력·저장은 재시도하지 않는다. iframe 좌표, 읽기 전용 평가, 무응답 캡처의 회귀시험을 추가했다.

### 남은 문제·최종 확인

실제 네이버 native 표 입력, 선택 옵션, 기본 확인창 전달, 프로세스 재시작 뒤 이전 임시글 연결은 이번에 완료했다고 주장하지 않는다. 저장 성공 뒤 추가 시도는 자동복구 동의가 없어 보존 중단했다. 밴드 사진 식별 실패는 WP6의 최신 실기기 절에 따로 적었다.

`pnpm install`, `pnpm typecheck`, `pnpm test`(**17개 파일·129개, 건너뜀 0개**), `pnpm build`, `apps/android`의 `./gradlew.bat assembleDebug --console=plain --no-daemon --offline`가 통과했다. 새 목록 대기식을 추가하면서 기존 표현식 시험의 모의 응답이 시간 초과한 것을 수정했고, 브라우저 통합 시험을 그대로 유지했다. 최종 전체 시험은 80.70초, 최종 Android 빌드는 14초다. APK는 설치 상태이며 최종 전면·화면 켜짐을 확인했다. [최종 APK·설치 근거](wp6/device-final.json)를 함께 참고한다.
